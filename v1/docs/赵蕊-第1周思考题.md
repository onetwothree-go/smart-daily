### 第 1 问 · 对照五大陷阱，分析你过去某个「AI 写的项目」失败在哪几条

**结论先说**：我过去用 AI 主要做环境配置和项目开发（给 Claude Code 接第三方模型、在 `D:\智慧景区` 项目上干活），对照第 1 章五大陷阱复盘，**五条全踩了**（本问正文与 `v1/docs/赵蕊-陷阱自查.md`（第 1 周任务交付物，300 字）同源，此处按题目原文重组）。

**第一，不可审查（踩得最深）。** AI 生成的 `ANTHROPIC_BASE_URL` 多写了一层 `/v1`，我没实测就落盘，跑起来报「模型不存在」，差点照着报错去换模型——逐层排查才发现请求被拼成了 `/v1/v1/messages`。当时只验收「能不能出字」，没有人审配置本身。AI 产物看起来能跑，不等于它写的就是你想要的。

**第二，需求蒸发。**「要在 Claude Code 里用上 100 万上下文」这条需求只活在一轮对话里，最后落成 `settings.json` 里的一个参数 `1000000`。为什么是这个数、对应哪个模型的能力，任何文档都没写，过两周连我自己都讲不清。

**第三，不可复现。** 为了绕过 Steam++ 对 github.com 的本地证书拦截，把它的根证书合并进本地 CA 包并写进了 git 全局配置——换台电脑或卸载 Steam++ 就报证书错误。改了什么、为什么改，没有留痕，要靠翻聊天记录还原。

**第四，上下文漂移。** 两个 GitHub 账号并行——提交作者是 A 号、登录推送是 B 号，PR 合并后贡献者列表里查不到自己，折腾半天才发现两个身份早已分叉。

**第五，不可维护。** `D:\智慧景区` 根目录混进 6 个无关的未跟踪文件，AI 一句 `git add .` 险些把无关文档推进组仓——项目边界全靠人肉记忆。

**所以**：五大陷阱的本质不是「AI 写得差」，而是**人把验收降级成了「能跑就行」**。第 1 周把 proposal、规范、AI 日志立起来之后，「能跑就行」就不够了——每条产出都要能指到规范条目和留痕记录上。

### 第 2 问 · proposal.md 中「不做什么」为什么比「做什么」更难写？

**结论先说**：「做什么」写的是愿望，「不做什么」写的是**承诺的边界**——每一条排除都要预判它未来会被谁、以什么理由要求加回来，并提前把拒绝的理由写死。愿望错了改需求就行，边界写含糊了会变成规范内部自相矛盾。

**第一，排除项是承诺，不是清单，每条都得给得出理由。** 指导书要求排除项至少 3 条且每条给理由，本组写了 9 条（N1–N9），没有一条能只写「不做」两个字。比如 N1（智能摘要 / NLP 归纳）的理由要连带解释 Q4/Q14 为什么不做语义过滤与跨源去重；N6（历史数据补采）的理由要落到「G1/C1 按当日条目数度量、SQLite 按（日期，成员）幂等」——排除一条功能，牵动的是数据模型和成功标准的定义。

**第二，真正的边界藏在反面，要靠追问才能长出来。** N5 最典型：表面写「不做实时刷新」，但本期其实**新增了** push 实时提醒——所以 N5 必须写成两层：「实时刷新日报内容、或把实时提醒算作日报条目」都不做，S9 的提醒只作告知、不进 G1 计数。这条边界是靠 Q16/Q17 的问答打磨出来的，不是一开始就想到的。N4 同理：「不允许事后改条目」之外还得补一句「推送前扫描、看明细决定重跑等系统外运维动作不算违反」，否则零手工会被读成连人工看一眼都违规。

**第三，「不做什么」写含糊的代价在本组真实发生过。** proposal C8 写「三源全失效必须抛明确异常」，README §2 早期却写成「采集失败返回空列表、不中断流程」——两条规范各自都「做了什么」说得通，放一起矛盾，最后靠架构师 issue #14 K1 裁定三分支语义才收口（出处见文末）。边界声明和功能声明打架，比功能缺失更难查。

**第四，排除项是会被时间检验的活承诺。** N3 写「考勤数据采集：涉及隐私数据处理，须先过合规评审｜计划：第 4 周变更涟漪演练时新增」——第 4 周教师变更单下发时，这条排除项按预告解除，proposal 差异版据此登记。证明「不做什么」不是一次性的话，每条都要能回答「什么时候、以什么条件重新纳入」，否则范围变更就没有锚点。

**所以**：「做什么」可以从愿望顺推，「不做什么」必须倒着预演——每一个被排除的功能，都要写清「为什么排除、排除到哪条线为止、将来怎么回来」。写它的时候没有功能可演示，全靠对未来的判断，这就是它更难的原因。
