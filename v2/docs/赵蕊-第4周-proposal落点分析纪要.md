## 1. 问题定义

变更单下发后，proposal 必须改（范围/功能需求/验收标准）。改在哪，有两个约束互相顶牛：

| 约束 | 原文 | 出处 |
| --- | --- | --- |
| **000③** | 对每条 v2 任务提交执行 `git diff 该提交~1 该提交 -- v1/` → **0 行**（v2 的提交不得改动 v1） | `v2/specs/tasks.md` L248 |
| **变更涟漪** | proposal → design → tasks → 代码 → 回归 自上而下同步，**任何一处规范与代码未同步都记缺陷** | 指导书 p20–21 |
| **零复制（G5）** | v2 禁复制 v1 全文 | `v2/README.md` §4、000② |

若直接改 `v1/specs/proposal.md`：该提交 `git diff -- v1/` 非零，000③ 的机械检查失败。
若新建 `v2/specs/proposal.md`：proposal 事实分裂两处，需防「两处不一致即缺陷」。

## 2. 仓库事实（先例与现状，逐条可复核）

1. `v2/specs/` 只有 `tasks.md`（559 行）；`v1/specs/` 有 proposal.md（256 行）、design.md（647 行，版本 0.6）、tasks.md、README.md。`ls v2/specs/ v1/specs/` 可复现。
2. **v2 阶段已有改 v1/specs 的先例**：`7d91e91`（2026-11-17 17:24，v2 于 11-16 启动之后）修改了 `v1/specs/design.md`（27 行，design 升 0.6）、`v1/specs/proposal.md`（13 行）、`v1/specs/tasks.md`（2 行）。该先例被组内沿用——`v2/specs/tasks.md` 有 3 处引用「design 0.6」（L381、L402、L544/U6），404 验收⑤ 直接引用「design 0.6 3.4 第 3 条」。
3. **000③ 的机械检查事实上从未严格归零**：`32c35ca`（TK-V2-401）等多个带 TK 编号的任务提交同时动了 `v1/docs/ai-usage-log.md`（当时 AI 日志放在 v1/docs，任务提交按纪律要追加日志行）。`git log --oneline f58ce4e..HEAD -- v1/` 可复现。即：000③ 的实际执行口径是「不得改 v1 的**代码**」，docs/specs 类改动未被机械拦截。
4. **U2 闭环先例（2026-11-23）**：实时提醒纳入 v2 时，组内对同类双轨冲突（notify.yml 归 v1 还是 v2）选了「**根目录只留一份**」的方案 B，明确理由是「规避 v1/v2 双通道与零复制冲突」。这是本组对「单一事实源优先」的第一次成文裁决。
5. 变更单截至 2026-11-24 尚未下发（全仓无考勤相关提交，开放 issue 仅 #19/#21/#22）。

## 3. 方案对比

### 方案 A：新建 `v2/specs/proposal.md`（差异版）

结构 = 「v2 基线声明（指向 `v1/specs/proposal.md` 的基线 commit 短号）+ 本次变更差异节（范围增量 / FR-考勤 / C11 / 变更记录）」，**不复制 v1 全文**。

| 维度 | 评价 |
| --- | --- |
| 000③ | ✅ 变更提交 `git diff -- v1/` = 0 行，零成本合规 |
| 零复制 G5 | ✅ 只写差异，不复制全文 |
| 单一事实源 | ⚠️ proposal 分裂两处：v1 = 冻结基线（0.4.2），v2 = 现行差异版；读者需合并阅读 |
| 「两处不一致」风险 | ⚠️ 转移为「**锚点漂移**」：若 v1 proposal 再被改动，基线 commit 失效；须纪律性冻结 v1 proposal |
| 评审负担 | ⚠️ 评审看差异，C11 与 C1–C10 编号跨文件，需对照 |
| 答辩追问 | 「现行版读哪份？」「基线之后 v1 又改了怎么办？」——答案都在基线声明节，可预答 |

### 方案 B：直接改 `v1/specs/proposal.md`（升 0.5）

| 维度 | 评价 |
| --- | --- |
| 000③ | ❌/⚠️ **取决于对「v2 任务提交」的读法**：宽读（v2 阶段一切提交）→ 直接违规；窄读（仅约束带 TK 编号的任务实现提交、意图是代码隔离）→ 规范同步豁免。原文括号「v2 的提交不得改动 v1」未写明豁免，需组内明文裁定 |
| 先例 | ✅ `7d91e91` 已改过 v1/specs（design 0.6），组内接受并引用至今 |
| 单一事实源 | ✅ proposal 仍只有一份，无锚点漂移 |
| 代价 | ⚠️ **必须同步修订 000③ 本身**（如：「`v1/` 下 `src/`、`tests/` 不得改动；specs/docs 变更同步豁免，提交 message 须带 `[变更单x]` 前缀」），否则 000③ 与仓库事实长期不符；000③ 是验收标准，改它本身又是一次规范变更，须全组评审 |
| 答辩追问 | 「000③ 怎么处理了？」「v1 冻结口径还成立吗？」——必须能出示 000③ 修订提交与评审记录 |

## 4. 推荐（一句话）

**推荐方案 A**：000③ 是白纸黑字的验收命令，方案 B 要先修订 000③（又是一次变更涟漪、又要全组评审），方案 A 零成本合规且与 U2「根目录只留一份」的裁决精神一致——但 `7d91e91` 先例如实附上，组内若倾向 B，须先过 000③ 修订，再动 proposal。

## 5. design.md 缺失对第 4 周架构师（方赫）的影响（一并决议）

1. 变更涟漪要求 design 同步（考勤采集的接口契约、数据模型、workflow 隔离）。**design 与 proposal 面临同一落点问题**，建议本次组内会一次裁定两份文件的口径，避免 proposal 走 A、design 走 B 的混合态。
2. `tasks.md` 已有 3 处引用「design 0.6」（401④、404⑤、U6），方赫出新版（0.7）时，若 3.4 送达判定口径被考勤变更触碰，**U6 的「未配置退回 len(groups)+1」裁定要复核**是否受影响。
3. 无论哪个方案，建议新 design 版本的变更记录节里注明「承接教师变更单 <编号>」，与 proposal 的变更记录对齐，评审时两份可互相印证。
