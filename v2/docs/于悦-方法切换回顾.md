阶段一（第 1–2 周）用的是 SDD：先定稿 proposal / design / tasks，再照规范写代码。我这两周先后任架构师、测试工程师 + 配置管理员，经手的是 `v1/docs/于悦-技术栈候选清单.md`、`于悦-同类竞品调研记录.md`（架构侧）和 `于悦-可测性评审意见.md`、`于悦-proposal成功标准逐条核对表.md`（测试侧）。**优势**：需求与设计白纸黑字，可追溯、可评审——我做的可测性评审就是把 proposal 的每条成功标准判成"可测 / 有条件可测 / 不可测"（15 条：可测 7 / 有条件可测 5 / 不可测 3），逐条对着原文给结论，这种"标准先分级、再动手"只有在规范固化的前提下才做得成。**局限**：文档重、改一处联动多份——proposal 从 0.4 改到 0.4.2 时，我那份逐条核对表跟着改了四处旧口径（G2/C6 改观察项、C7 恢复可测、G4 时间口径对齐），写规范时看不见真实代码，容易纸上谈兵。

阶段二（第 3 周）切到 Superpowers：用 `writing-plans` 写计划、TDD 红绿循环执行。我这周任需求分析师，产出是 `v2/specs/tasks.md`（36 条、七段链路、依赖图、并行组）和进度维护记录。**优势**：每条任务都能落到"一个可验证交付物 = 一次提交"，谁做哪条、依赖谁、能不能并行都标清楚，我维护的进度表能逐行对着提交号核状态，比 SDD 阶段"文档写完了事"扎实得多；code-review 互评也逼着我把验收标准逐条对照提交内容看，抓出了"用回执自身当 expected"这类规范与实现脱节的地方。**局限**：它假设计划已经想好，自身不做需求与设计——tasks.md 写"一条任务 = 一个可验证交付物"，但验收标准可不可测、契约定没定，Superpowers 不会替你判断，得靠人在写计划阶段补（我这周处理 U1 降级链口径冲突、K1–K8 裁定，就是在补 SDD 阶段本该定死的规范）；而且每一步都留证据，节奏偏慢，探索性的活不适用。

适用场景：需求模糊、要先把想法想清楚，用 brainstorming / SDD 把规范和成功标准定稿；需求明确、要存档评审、要逐条判可测性，用 SDD；计划已定、要高质量落地并有据可查，用 Superpowers 的 TDD 循环。两者不是替代关系——**我这两周的经验恰恰是：SDD 阶段把规范写扎实，Superpowers 阶段才有得执行**；规范没定死就跳进红绿循环，卡住的还是需求这一头。
