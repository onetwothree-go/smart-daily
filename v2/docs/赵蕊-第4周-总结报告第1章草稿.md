## 1.1 项目概述与两阶段路线

本项目为「智能日报生成器（Smart Daily Report Generator）」：聚合 GitHub 提交、飞书任务、飞书群消息等工作记录，按成员生成个人日报与团队日报，经多通道推送并落库。全组 4 人（杨佳莹、于悦、方赫、赵蕊）承担需求分析师、架构师、开发工程师、测试工程师、配置管理员五个角色，按周轮换（出处：`docs/小组角色分工与轮换表.md` §一）。

项目分两个阶段推进：

- **阶段一（v1，第 1–2 周，SDD 流程）**：走需求 → 设计 → 任务分解的规范路线，产出 proposal 0.4.2（2026-11-09 定稿，出处：`v1/specs/design.md` 文档头引用行）、design 0.6（含推送五态、退出码契约与 ADR-104，出处：`v1/specs/design.md` 文档头）、tasks 0.1.x，并完成 v1 实现。v1 复盘沉淀三个已知坑：采集器吞异常返回空列表、`pushed = any(ok)` 把部分送达判成功、身份映射大小写不同规（出处：`v2/README.md` §4）。
- **阶段二（v2，第 3 周起，Superpowers 流程）**：从零重写，只带设计结论不带 v1 代码（零复制红线，出处：TK-V2-000 验收②「全文无 v1 代码块」、验收④「`grep -r "import smart_daily" v2/` → 0 命中」），以 tasks.md 的 36 条任务驱动 TDD 红绿重构。工程基线四项决策为 ADR-101~104：httpx 直连无 ORM、sqlite3 + UNIQUE 约束幂等写入、异常驱动降级由编排层统一判定、Actions 触发的实时提醒契约（出处：`v2/README.md` §1）。截至 2026-11-24，v2 全量测试 267 passed（出处：`v2/docs/testing/证据/红绿循环/def05-red-20261124.txt`，当日为 issue #19 补红用例后实测）。

## 1.2 需求与范围演进

需求以 proposal 的成功标准 C1–C10 为验收骨架（出处：`v1/specs/proposal.md` L115–124），演进经历三轮：

1. **契约修订（issue #14，K1–K8）**：第 3 周开工前，架构师对 16 项接口契约做变更审核，出 8 条结论——K1 裁定维持「异常才降级、空列表即停止」（ADR-103 语义，空列表是合法结果非故障）；K2 裁定编排入口 `run()` 返回含 `push_status` 的 9 键并满足不变量 `pushed == (push_status == "ok")`；K6 裁定团队日报必须发教师邮箱，送达数由 5 改 6，全仓 26 处相反旧口径逐字回填；K8 补定义全失败异常类继承关系；K3/K4/K5 澄清、K7 待组内会（出处：`v2/docs/杨佳莹-第3周-接口契约变更审核记录.md`，经 2+1 轮复核）。
2. **范围外增补**：成员账号名到中文显示名的全链路映射、团队日报教师邮箱通道在 22:00 自动发送两项以「范围外」提交接入并显式标注（出处：`cc229fb`、`3de8afd` 提交 message 与 `v2/src/smart_daily_v2/orchestrator.py` 模块 docstring 的范围外声明）。
3. **变更单（待述）**：教师将下发需求变更单——新增飞书考勤数据采集模块（教材 7.5 节 v1.1 场景）。截至 2026-11-24 变更单未到达，proposal 落点方案对比已备好待组内拍板（出处：`v2/docs/赵蕊-第4周-proposal落点分析纪要.md`）。
