## 5.1 我的四个角色，本质上都在当"记录人"

四周轮换下来我发现，我拿到的四个角色有一个共同点：**都不是"做决定的人"，而是"把决定写下来的人"**。

第 3 周做测试+配置，我记录的是"这条红用例是不是按预期红、这条 CI run 对应哪条任务、合并前门禁是否真绿"（`v2/docs/赵蕊-CI门禁与静态扫描归档.md`、`赵蕊-合并控制记录.md`）；第 4 周做需求分析师，我记录的是"变更单落成了哪几条范围条目、哪几条口径还没裁决、谁该裁决"（`v2/specs/proposal.md` §7 开放问题 11 条）。

记录人的伦理比决策人更隐蔽：决策错了，会议纪要会留下反对意见；**记录错了，或者记录被自己的预期带偏，整条链上没人会发现**——因为后面所有人都在读你写的那份东西。所以这一章我只讲一件事：**记录必须跟着证据走，不能跟着预设走；签名必须落在自己名下，不能替别人落。**

## 5.2 诚信：预设错了就改预设，不改证据

**DEF-05 红步是我四周里最难受也最值钱的一次改口。** 我按 issue #19 的话术预设，认定失败原因是"无邮箱成员没有被记录"，红用例也照这个方向写。实测结果完全不同：成员被记录了、`push_status` 也正确判了 partial，真实缺口只是**回执里缺 `error="no_recipient"` 标记**（1 failed / 267 passed，出处：`v2/docs/testing/证据/红绿循环/def05-red-20261124.txt`）。

两条路摆在面前：把话术改一改让它继续成立，或者改话术去迁就证据。我选了后者，并在缺陷清单里写清"原预设错误"——因为如果按错的方向交出去，方赫会去改记录逻辑，红用例转绿了却测不出真问题，那才是真正的造假：**证据是真的，结论是假的**。这次之后我给自己定了一条：红步之后先问"失败点是不是我以为的那个"，再谈修什么。

**同一条纪律在 DEF-11 上第二次生效，而且打的是我自己的脸。** 我登记时把 CI 红定性为"个人日报考勤条目未按成员过滤（生成器缺陷）"。于悦修复后，`7db0172` 的 diff 证实：生成器没问题，是 904_02 用例构造时漏了 `group_by_member` 这一层。我在闭环回写时把定性改成"用例构造缺陷"，没有保留原判断去维护登记人的面子（出处：`v2/docs/赵蕊-缺陷清单与根因记录.md` DEF-11 条、`v2/docs/赵蕊-第4周周报告.md` 第三节第 5 条）。**缺陷登记人的记录跟着证据走，是这份清单唯一有价值的地方。**

- **tasks.md 状态列**：40 条任务里 34 条还是 ⬜、6 条 🟩 待核对，而代码早已 314 passed 全绿。状态列的维护权在于悦，我只在周报告里如实写"不代勾"，没有替她勾一条（`v2/docs/赵蕊-第4周周报告.md` §四遗留 1）。
- **思考题四份**：抬头一直是 `☐ 待本人核验签认`。11-26 我逐份核对了题目原文、出处与引用行号之后才改 ☑，其中第 1/2/3 周如实注明是**补交**、不倒填日期。
- **AI 使用日志 70 条 `☐ 待本人核验`**：这是本周最需要克制的一次。这份日志全组共用，历史条目没有逐条标操作者；把这 70 条批量改成 ☑ 只需要一次替换，但那等于我替三个人宣称"我们核过了"。我没改，只在日志末尾加了一段《核验范围说明》，写清本人名下哪几条签了、70 条为什么不改、各自归谁核验，并附机械核验结果（22 处引用 sha 全部可在仓库解析、101 处路径可追溯、3 处"非 sha"是 CI run id 与 unix 秒戳）。**指导书把"AI 日志缺失或造假"定为报告不计分的资格项——正因为它最容易被"看起来齐了"糊过去。**

还有一条是我主动给自己加的：**签认之前先核数字，签了就不能再说"当时没注意"。** 周报告签认前，我把它里面 5 处已经过时的事实逐条改掉（交付物 12 项→14 项、U13 双前置→实质解除、904 验收⑤→已闭环、0.1→0.5、AI 日志 165→173 条），因为签的是一份"能被抽查的报告"，不是一份"写得很顺的草稿"。

## 5.4 敬畏规范：不预拍，就是不在证据没到时先写结论

需求分析师最容易犯的规范错误不是写错，是**写得太早**。第 4 周第二层 5 个功能（S11–S15）落地时，我给自己的约束是"预写即预拍"：

- **只锁不变量，不写细分断言。** C12 验收门只写三条（C11 一字不改 / 聚合与明细 1:1 可对账 / 不突破 I30 隐私边界），具体断言留给 design 逐条细化（`v2/specs/proposal.md` §4 C12）。因为 #7 呈现形态还没裁，我现在写的任何断言，裁决一变就是废纸，还会诱导开发照着错的做。
- **开放问题只登记不拍板。** 11 条开放问题全部标注责任人：架构契约标"待方赫"、组内职权标"待组内"、需要老师输入的标"待老师确认"（§7）。其中 #1/#4 由组内 2026-11-25 裁决为 1A（考勤不计入 G1/C1）与 2A（仅出勤状态），我按裁决回填 0.3，并在变更记录里写明"由需求分析师记录、书面归档随评审会，不代全组签字"。
- **评审通过 ≠ 口径已定。** 11-26 评审通过后，我把 proposal 五处状态翻成"已评审"，但 #7–#11 的 ☐ 一个没动，还在 §7 加了一句"未裁决不影响条目通过"。这两件事分开写，才不会让下游误以为可以照着做了。

## 5.5 隐私：上限之内只能收紧，不能放宽

考勤模块给了我一次很具体的伦理判断。组内 2A 裁决的上限是"仅出勤状态"，实现上于悦做得比上限更严：日报正文只显示"已打卡"，出勤状态留在 `detail` 里只供 1:1 对账（`97a1ae3`）。我在 proposal 0.5 里把这个口径写成 FR-KQ1 输出②a「脱敏呈现」，约束① 精确到"只采集打卡时刻 / `record_id` / 出勤状态，定位、图像、WiFi、设备号不读取不落库"，另加约束⑤"程序只读、不代打卡"（`v2/specs/proposal.md` §3）。

写这段的时候我明确了一件事：**裁决给的是上限，不是配额。** 拿到"可以用出勤状态"不等于"必须把它显示出来"——少显示一个字段不会违反任何一条验收，多显示一个字段就多一次泄露风险。这条判断后来也写进了 I29（采集面 / 呈现面两分）。

## 5.6 团队伦理：把不确定公开，把结论留给该拍的人

- **缺陷清单是全组共用的账本，不是我的成绩单。** 四周累计 11 条（DEF-01~11），每条都写引入提交、复现方式、修复提交与核验证据；观察中的（CI 日志接口 403 取证受限）就写"观察中"，不硬凑成"已闭环"。
- **催办走公开渠道、说人话。** 第 4 周催方赫、催于悦的话术我都写成群里能直接发的一段话，不用公文腔；要谁做什么、卡在哪、什么时候要，三句说完（`v2/docs/赵蕊-第4周-proposal变更对照表.md` 评审预答部分）。
- **评审通知给判定规则，不给压力。** 评审通知里我写清"五个版本看点 + 对照表 §一–§八 索引 + +1 即过 + 期限"，让每个人知道看什么、怎么算过，而不是"大家看一下"。
