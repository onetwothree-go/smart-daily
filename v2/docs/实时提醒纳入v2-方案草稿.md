## 0. 一句话结论

根目录 `.github/workflows/notify.yml` 只留一份、内容从 v1 换成 v2：由 v2 从零新写的脚本接手"push → 飞书群恰 1 条提醒"，v1 的 `notify_push.py` 不再被任何 workflow 调用。这样既解决 Actions 只认根目录的落点冲突，又满足 C10"一次 push 恰 1 条"，且不违反目录隔离与零复制。

## 1. 接口契约（v2 实时提醒通道）

### 1.1 通道定位（边界，先划清）
- 这是**独立链路**：读 push 事件 → 发 1 条飞书群消息。
- **不写 SQLite、不生成日报条目、不进 G1 的 1:1 计数、不进 22:00 汇总日报**（S9 主链路隔离，C7 的六通道送达也不含它）。
- **不 import v1、不整文件复制 v1 源码**（零复制红线）。

### 1.2 输入（全部由 Actions 注入；不读 `.env`、不调 GitHub API、不需要 token）
| 变量 | 来源 | 用途 |
|---|---|---|
| `GITHUB_EVENT_PATH` | runner 自动注入 | push 事件 JSON，含 `commits[]` 与 `ref` |
| `ACTOR` | `${{ github.actor }}` | 触发者登录名（归属键） |
| `MEMBER_DISPLAY_NAMES` | 明文（公开信息） | 登录名 → 中文显示名映射 |
| `FEISHU_WEBHOOK_URL` | `${{ secrets.* }}` | 群机器人地址 |
| `FEISHU_WEBHOOK_SECRET` | `${{ secrets.* }}` | 签名密钥 |

### 1.3 处理规则
- 只处理 `main` / `dev` 的 push（由 workflow 的 `branches: [main, dev]` 过滤，feature 分支 0 次）。
- 一次 push 合并为 **恰好 1 条**消息，逐条列全 commit **原文**（不摘要、不改写）。
- 身份映射复用 v2 `identity.display_name(raw, mapping_raw)`（内部已按 strip + casefold 匹配，缺省读 `MEMBER_DISPLAY_NAMES`；**不用 v1 的 lower**）；未命中回落原账号名、不丢条目。归一化键用 `identity.normalize_key()`。
- 消息文本**必须含「日报」二字**（飞书自定义机器人关键词，缺了被 19024 拒收）；含中文显示名、分支、条数、提交链接、北京时间。
- 签名复用 v2 `notifiers/webhook.py::gen_sign(timestamp, secret)`，**不重写、不复制**。

### 1.4 输出与失败语义
- 飞书返回 `code=0` → `exit 0`。
- 任一环节失败（缺配置 / 事件解析失败 / 网络异常 / 非 JSON / `code≠0`）→ 打印可读原因并 `exit 1`，让 workflow **亮红灯**；不静默、不重试（Q21）。
- stdout 打印待发文本，便于 Actions 审计。

### 1.5 函数级接口（对齐 v2 现有风格）
```
load_event(path: str) -> dict
resolve_display_name(login: str, mapping: str) -> str   # 复用 identity.display_name()
build_text(actor: str, branch: str, commits: list[dict]) -> str
send(text: str, url: str, secret: str) -> int            # 调 gen_sign()
main() -> int
```
**落点**：`v2/src/smart_daily_v2/notify_push.py`（放包内，复用同包 identity / webhook）；入口 `python -m smart_daily_v2.notify_push`。

## 2. workflow 隔离方案

### 2.1 冲突点
GitHub Actions 只认仓库根 `.github/workflows/`，而该目录已被 v1 的 `notify.yml` 占用。v2 代码在 `v2/`。若两者都监听 main/dev 的 push，一次 push 会发 **两条**群消息（违反 C10）。

### 2.2 三个方案
| 方案 | 做法 | 判定 |
|---|---|---|
| A 并存 | 新增 `notify-v2.yml`，保留 v1 `notify.yml` | ❌ 一次 push 两条群消息；v1 通道仍在，与"走 v2、不用 v1"相悖 |
| **B 替换（推荐）** | 根目录**只留一份** `notify.yml`，内容整体改为 v2：触发仍是 main/dev push，`run` 指向 v2 脚本；v1 `notify_push.py` 不再被任何 workflow 调用 | ✅ 落点唯一、一次 push 恰 1 条、v2 真正拥有该通道、v1 旧通道自然停用 |
| C 合并 | 一个 workflow 但仍调 v1 脚本 | ❌ 实现仍是 v1，违反零复制与"从零重新实现" |

### 2.3 推荐方案 B 的落地要点
- 直接**改写现有 `notify.yml` 内容**（文件名可保留，减少重复触发面），文件头注明"已归属 v2 实时提醒通道"。
- `permissions: contents: read`（不调 API，无需 token）。
- 步骤：checkout → setup-python 3.13 → `pip install -e ./v2` → `python -m smart_daily_v2.notify_push`。
- `env` 注入同 §1.2 五个变量；Webhook 两项走 Secrets，不写死、不打印。
- 结果：根目录 workflow 仍唯一；v1 `notify_push.py` 文件可保留作 v1 历史资产，但**不再执行、不算 v2 成果**。

### 2.4 与"走 V2、停 V1"的一致性
本方案让 22:00 日报与 push 实时提醒两条链路都由 v2 承担；v1 的日报计划任务已在本机停用（另记），v1 的实时提醒 workflow 由本方案替换。两条线互不重复。
