## 一、规范守护检查点现状（CI 三道门，实测）

`.github/workflows/ci.yml`：`on.push.branches=[dev]` + `paths: [v2/**, .github/workflows/ci.yml]`，`permissions: contents: read`。两个 job 均为真实门禁：

| 检查点 | 实现 | 本次实测结果 | 证据命令 |
|---|---|---|---|
| ① 静态检查 | `uv run ruff check .`（规则 E/F/I/B，line-length 100） | `All checks passed!` | `cd v2 && uv run ruff check .` |
| ② 格式检查 | `uv run ruff format --check .` | `100 files already formatted` | `cd v2 && uv run ruff format --check .` |
| ③ 测试 + 覆盖率 | `uv run pytest -q --cov=smart_daily_v2 --cov-fail-under=80` | `273 passed`；覆盖率 **93.07%** ≥ 80% 门槛 | `cd v2 && uv run pytest -q --cov=smart_daily_v2 --cov-report=term-missing --cov-fail-under=80` |

**本检查点的作用**：这是当前实际生效的规范守护——它保证"代码可 lint、可格式、有测试且覆盖率达标"，属指导书所说的"脚本检查"一层。DEF-10（design 契约代码块被 `ruff format --check` 扫出、致 CI 红，已按甲案修复于 `1e5e970`）就是这道门真实拦下的一次"文档/规范与格式规范不一致"，可作为门禁有效性的实证。

## 二、"改了代码未改规范"自动检查：诚实登记为缺口（☐）

**结论：当前没有自动化检查能识别"代码改了、proposal/design/tasks 没同步"**。逐项核实：

- CI 仅覆盖 v2/ 目录的 lint / format / test，**没有**比对 `specs/`（proposal / design / tasks）与源码一致性的 step；
- 无 `.git/hooks/` 或 pre-commit 配置拦截"代码变更但 specs 未变"（`git config core.hooksPath` 未设置自定义路径）；
- 本轮变更涟漪（考勤采集）的规范同步靠**人工 review + 缺陷登记**兜底：赵蕊以 DEF-10 登记 design 格式问题、design §8-B 留 6 项同步义务、issue #23 催办，均非自动检查。

**这属于指导书任务 3 未完全达成项**，不粉饰。补强方向（☐ 待组内裁定，不擅自实现）：

1. 在 CI 加一步"specs 变更伴随检查"：PR 触及 `v2/src/**` 时要求 `v2/specs/**` 亦有变更，或显式豁免标签；
2. 或用 pre-commit hook 做同类检查；
3. 涉及门禁口径变更，**须按纪律经全组评审**，本侧只登记不实施。

| 项 | 检查 | 实测结论 | 证据 |
|---|---|---|---|
| **SQL 参数化** | 全部 SQL 是否用占位符、无字符串拼接 | ✅ 通过。`storage.py` 全文 SQL 均为 `?` 参数化：`WHERE report_date = ?`（L116）、`INSERT ... | **日志脱敏 / 令牌不落日志** | 凭证是否只从环境变量读取、日志是否打印密钥 | ✅ 通过。`config.py` 的 `github_token/feishu_app_secret/feishu_webhook_secret/smtp_password` 均为 env 注入的字段；`notifiers/email.py` 用 `environment.get("SMTP_PASSWORD")`、`webhook.py` 与 `notify_push.py` 用 `gen_sign()` 签名、不外泄 secret；全仓无打印明文令牌的日志语句 | `config.py` L8-L22、`notifiers/email.py` L31、`notifiers/webhook.py` L12/L46、`notify_push.py` L4/L86-L95 |
