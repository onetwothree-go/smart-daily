## 1. 要解决的问题（原话可复现）

design §4-2 登记：飞书打卡结果接口按 `employee_type` 返回 `user_id` / `employee_no`，
而 v2 现行成员键是 `normalize_key(sender_name / creator_name)` 的**姓名键**
（`sources/feishu_chat.py:167`、`sources/feishu_tasks.py:147`，归一化实现见 `identity.py:26` 的 strip + casefold）。
**两者不是同一标识，不得假定同名即同人。** 缺映射则考勤条目无法归并到四名成员，TK-V2-901–904 整组不勾销。

本方案只回答一件事：**把接口返回的标识，稳定、可复现地换成 v2 姓名键。**

## 2. 两个候选方案

| | 方案 A：配置表静态映射（推荐） | 方案 B：通讯录关联 |
|---|---|---|
| 做法 | 环境变量写死 4 条 `飞书标识:姓名`，采集时查表 | 按 `user_id` 调飞书通讯录接口取 `name` 再归一化 |
| 新增权限 | 无（沿用现有 app 凭证） | 需通讯录读取 scope，B#5 之外再开一项 |
| 新增网络调用 | 无 | 每条考勤多一次 API，失败要降级 |
| 可复现 / 可审计 | 高：映射是显式配置，逐条可核 | 中：依赖远端通讯录实时值，人员改名会漂移 |
| 规模匹配 | 4 人固定小组，一处配置即可 | 面向几十人动态组织才有价值 |
| 隐私面 | 最小：只存 4 条标识↔姓名 | 较大：多读一层通讯录字段 |

**推荐 A**：4 人固定小组、零新增权限、零新增接口调用，且映射可逐条核验，符合隐私最小化与"任何一处规范与代码未同步即缺陷"的稳健取向。方案 B 留给以后人员动态变化再走变更。

## 3. 方案 A 落地要点（供 901 实现参考，本稿不写码）

1. **配置项**：新增环境变量 `FEISHU_ATTENDANCE_MEMBER_MAP`，格式 `user_id:姓名,user_id:姓名`，
   在 `config.py` 的 `Config` 增字段、`load_config()` 按现有 `fields(Config)` 机制读入，零特殊分支。
2. **归一化**：映射值（姓名）必须过 `normalize_key()` 再作为 `WorkItem.member`，与
   `feishu_chat.py` / `feishu_tasks.py` 同源，避免大小写/空格不一致造成同一人被拆成两个成员。
3. **`employee_type` 选型**：建议用 `employee_id`（即 `user_id`），与本映射表的键一致、稳定不随工号调整变化；
   若组内选 `employee_no`，映射表键同步改为工号即可，方案不变。此项需与 901 实现者（于悦）对齐后定。
4. **查不到映射时**：**跳过该条考勤并留痕**（记 `record_id` + 未映射标识的脱敏前缀），
   不得猜测同名、不得落到"未知成员"分组——否则污染 C11 的 1:1 对账与团队日报分组。
5. **凭证边界**：映射表不含密钥；`user_id` 属可配置标识，仍按最小披露，不进 README 正文样例（用占位符）。
