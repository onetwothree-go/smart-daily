## 2.2 阶段一：SDD 规格先行的建立过程

第 1–2 周按 SDD（规格驱动开发）路线推进，过程顺序是"先把规格写清楚、再让实现跟着规格走"：

1. **先立规格骨架**：配置管理员建仓时同步建立 `specs/` 目录与分支规范（`docs/小组角色分工与轮换表.md` §二、§三）；需求分析师经多轮澄清产出 proposal（`v1/specs/proposal.md` 0.4.4，含 Q1–Q21 / I1–I28），架构师据此出 design 0.6（含推送五态、退出码契约与 ADR-101~104 的前身决策），再拆 tasks 0.1.x（出处：`v1/specs/` 三份文档头）。
2. **红队评审倒逼规格精确**：design 0.5→0.5.1 经红队 RT-01~09 整改（出处：`v1/specs/design.md` 文档头",docs/于悦-红队评审意见清单.md"）；这一步的过程价值在于——"规格里写不清的地方，会在评审里被打回"，例如空列表语义、送达判定、身份归并口径都是此时钉死的。
3. **学习与方法论沉淀并行**：第 1 周写 300 字陷阱自查（五大陷阱各举一例，实测 298 汉字，出处：`docs/方赫-陷阱自查.md` 与 11-12 工作记忆），第 2 周逐字核对附录 E 题目原文再作答——**先取原文再写答案、不凭记忆出题**，这一纪律贯穿后面几周的思考题与过程记录。

阶段一的过程教训（v1 复盘三坑：采集器吞异常返回空列表、`pushed = any(ok)` 把部分送达判成功、身份映射大小写不规）没有停留在口头，而是被写成阶段二的契约约束（出处：`v2/README.md` §4、`v2/specs/tasks.md` G3/G4），成为下一阶段"从零重写时第一件事就把坑堵上"的输入。

## 2.3 阶段二：从零重写与 TDD 红绿循环的落地

第 3 周进入 Superpowers 工作流驱动的 TDD 循环，过程上做了三个关键决定：

**第一，零复制、只带结论。** v2 不复制 v1 一行源码，只把设计结论以文字带入（G2 红线，出处：`v2/specs/tasks.md` TK-V2-000 验收②④）。过程上以 `grep -rnE "^from smart_daily import|^import smart_daily$" v2/src v2/tests` 为 0 命中作持续校验，本报告已重跑复现（见第 2.6 节）。这是"过程约束可机器验证"的一次实践。

**第二，一条任务 = 一个可验证交付物 = 一次提交。** 主编排、落库、历史查询、CLI 被拆成 501→502→503→504 四条串行任务，测试基线按 156→166→176→186→196 逐级抬升，每级都有具名失败用例（出处：`v2/docs/方赫-红绿循环记录-第3周.md`）。过程的粒度把握来自思考题的实证：任务过大则"红"只能写一个覆盖全流程的用例、失败无法定位；过小则交付物失去可验证性、共享文件被迫反复交接（出处：`v2/docs/方赫-第5章思考题.md` 第 6 章答案，与 11-22 工作记忆对附录 E 原文的核对）。

**第三，测试从验收标准生成，不从代码生成。** 605 从 C7「全部 ok 才算成功」导出六通道逐一失败、3 真 3 假、空 expected 判 False 三组用例，专门堵住 `all([]) == True` 的真空真陷阱（出处：`v2/docs/方赫-红绿循环记录-第3周.md` 105 行起）；803 从方案 B 的文字契约直接读出七条 workflow 断言，未动 workflow 时红 `2 failed / 5 passed`，暴露的是"规范未落地"而非脚本 bug（同记录 303 行起）。这条方法论在过程上的意义是：测试成为"规范有没有兑现"的检测器，而不是"代码有没有变"的确认器。

过程的第 3 周中段还有一次**工作流纠偏**：自 TK-V2-203 起，红 / 绿 / 收尾三阶段一律改回在普通 Claude Code 会话内用自定义命令（`/taskNNN → /taskNNNg → /taskNNNc`）执行，本人（经 WorkBuddy）只做只读核验、补 AI 日志与红绿记录、提交推 `dev`，不改源码/测试/lint、不代做收尾（出处：`v2/docs/方赫-方法切换回顾.md`、第 3 周周报告 §方法论）。纠偏的动因是职责边界：让"谁写代码、谁验收、谁记录"三者分离，AI 只做辅助，规范文件（specs/）和签字栏留给人。

## 2.4 第 4 周：变更涟漪的同步过程

第 4 周教师下发变更单"新增飞书考勤数据采集模块"，过程严格按指导书的顺序自上而下同步：

1. **proposal（需求侧）**：赵蕊建差异版 `v2/specs/proposal.md` 0.5-diff 0.1（方案 A：差异版、不复制 v1，出处：该文档头 + `v2/docs/赵蕊-第4周-proposal落点分析纪要.md` §7）。
2. **design（架构侧，本角色）**：本人起草 `v2/specs/design.md` 差异版，从 0.1 初稿→0.2 定稿→0.3 全组追认→0.4 本人拍定四项并签认；飞书接口按官方文档填实（选打卡结果接口、排除含定位的流水接口以守隐私最小化），A 组契约已追认、B 组余 6 项 ☐ 待裁定（出处：该文档变更记录与 §8-B、§10）。
3. **tasks / 代码 / 回归**：尚未开工——卡在配置侧的 scope 开通与 `user_id→成员键` 映射、组内四项裁定（出处：`v2/specs/design.md` §8-B、issue #23）。**这个过程状态如实呈现：规范侧已推进到可评审，代码侧因前置条件未齐而未动，不虚报"已全部同步"。**

同步过程中发现两处"规范与代码不一致"并均按缺陷处理：**DEF-05**（应送达集合分母偏小，`orchestrator.py` 改为独立构造 expected 并逐项回填 error，273 passed，出处 `2baf68d`）、**DEF-10**（design 代码块不符 ruff 格式致 CI 红，按甲案自改代码块，出处 `1e5e970`）。两例都走"发现→登记→修复→复跑门禁"的同一过程闭环，缺陷状态行由缺陷清单维护人（赵蕊）最终核销，本侧不越权。

## 2.5 质量守护与协作过程的常态化

- **CI 门禁常态化**：`.github/workflows/ci.yml` 对 `v2/**` 的 push 与 PR 跑 ruff check、ruff format --check、pytest + 覆盖率（≥80%），`permissions: contents: read`（出处：该文件）。第 4 周实测全绿、覆盖率 93.07%；DEF-10 就是门禁真实拦下一次"规范文档格式不一致"的实证（出处：《方赫-第4周-规范守护自检记录》§一）。
- **code-review 常态化**：每周互相评审，第 3 周本人回应 5 条 + 评他人 2 次（出处：`3e1e53e`、`v2/docs/方赫-第3周-code-review互评记录.md`）；评审意见与回应分别留痕，"对方回应/是否闭环"由对方本人回填，不代填不代勾。
- **AI 使用全程留痕**：四周 AI 使用日志连续登记（出处：`docs/ai-usage-log.md`），按四色清单分级；谁用 AI 做了什么、哪份产出经谁核验签认，逐条可查。全过程坚持"AI 产出须人工核验、规范文件与签字栏由人签"的边界。
- **变更与催办公开化**：第 4 周把待协同事项发到 issue #23（配置/需求/开发/组内会分组点名），用公开可追溯的方式推动，而不是口头催办。
