## 五、第 9 / 10 章思考题两问（附录 E，随周报告提交）

> 本节正文与 `v2/docs/赵蕊-第4周思考题.md` 逐字一致（该文件抬头注明「周报告定稿后逐字同步」，本报告定稿即同步）；出处逐条列于第七节。

### 第 1 问 · 规范守护 CI 应该设在哪三个检查点？

**结论先说**：三个检查点应该按**时点**切，而不是按工具切——①每次 push 即门禁（合并进 dev 前）；②红步期间的人工核验（CI 红不等于可放行）；③dev→main 合并前。工具（ruff、pytest、覆盖率）在三个时点复用，但每个时点回答的问题不同。本组第 3–4 周的真实红绿经历恰好把三个时点都验证了一遍。

**第一，push 即门禁：所有路径都要过，包括文档。** 本组 CI 在每次 push 到 dev 时跑 ruff check（规则 E/F/I/B、line-length 100）+ `ruff format --check` + 全量 pytest 带覆盖率。第 4 周 DEF-10 给了一个超出直觉的实证：`ruff format --check .` 连 **Markdown 里的 Python 代码块**都会扫——design 差异版里的接口契约代码块手工排版不符，整条门禁红（run 45319012581，修复 `1e5e970`）。这说明 push 门禁的覆盖面必须包含全部提交路径：文档类提交看似「无害」，但它承载的规范示例本身会误导实现。顺带的待议项是 paths-ignore：纯文档提交是否豁免重跑全量测试，属配置侧粒度问题，但**豁免不等于降低格式检查**——DEF-10 那条恰恰是文档提交红出来的。

**第二，红步期间：CI 红是预期，但「失败点=预期」必须人工核验。** TDD 红步故意让门禁红，这时 CI 的价值从「拦截」变成「定位」。我推红用例（`a4d3630`）后逐 step 核对：失败只允许出现在「运行测试并采集覆盖率」步、且失败的必须是那条红用例——当时本地复现 1 failed / 267 passed，CI 与本地一致才确认是预期红。几天后另一笔提交的红（同一 run 编号系）失败步却从测试换成了 Ruff 格式检查，正是这个「换位」暴露了 DEF-10。**如果红步期间不看失败点、只看红绿，红步会掩盖真正的意外失败。**所以第二个检查点是纪律性的人工动作：红步期间每次 run 都要回答「失败的是不是预期的那一个」。

**第三，dev→main 合并前：门禁绿是合并的充分条件之一，人工红线自查不可省。** 第 4 周仓库出现 `merge-dev-to-main` 分支、main 快速前进——dev 的 CI 门禁绿（当前 273 passed）是把 dev 合进 main 的前提，CI 红挡合并是纪律而不是负担。但 CI 查不了的东西要在第三个时点人工补：`701` 零复制与密钥红线自查（v1 代码零带入、`.env` 不入库、AI 日志不引用密钥原文）就是为合并前准备的**人工检查点**——工具扫得出格式，扫不出「这段逻辑是从 v1 复制的」这类语义级红线。

**所以**：三个检查点分别是「推就拦」「红要验」「合必绿」，CI 工具在三处复用，人要做的事各不相同——第一个信任工具，第二个核对失败点，第三个补上工具看不见的语义红线。

### 第 2 问 · AI 时代「工程素养重于编码能力」，你同意吗，给出你的证据

**结论先说**：同意。编码能力决定「写得多快」，工程素养决定「写的东西敢不敢签字」——在 AI 把编码成本降到接近零之后，**判断、留痕、诚实**这三样成了稀缺品。以下证据全部来自本组第 2–4 周仓库里真实发生的事。

**证据一：AI 能生成一切，只有人能生成「信用」。** 本组 AI 日志已累计 151 条，每条都标四色、标注「☐ 待本人核验」或签认状态——因为指导书把「AI 日志缺失或造假」定为报告不计分的资格项。AI 可以替我写日志的正文，但「这条是不是真的按我说的做了、我核验过没有」，AI 说了不算，签字栏只能人来签。第 4 周签字回填时，每处签字我都先做事实核对（README 第 21 行确实已补、CI 确实全绿）才落 ☑，遗留项（000④ 扫描命令、701① 基线选择、006② 规格差异）如实标注待复核而不掩盖——这套纪律没有任何工具能替代。

**证据二：发现「AI 给的证据和预设不符」并如实改口，靠素养不靠工具。** DEF-05 红步时，我最初按任务话术的预设认定失败原因是「无邮箱成员没被记录」，实测发现真实原因是「记录了但缺 `no_recipient` 标记」。预设是错的，证据是对的——**改话术迁就证据，而不是改证据迁就话术**。如果没有这个纠偏，方赫会按错误方向修，红用例转绿却测不出真问题。工具给不了这种判断，因为工具不知道自己被预设污染了。

**证据三：知道「该在哪设检查点、发现不一致找谁裁定」是素养的核心。** U1 降级链冲突（proposal C8 与 README §2 打架）不是任何一个人能拍的：登记进 tasks §8.2 U 行 → 提给架构师 → K1 裁定三分支语义 → 规范收紧 → 602 解锁。这条链上每一步都是「程序素养」：不悄悄拍板、不越过 specs 变更流程改规范、裁定后全组执行。同样，第 4 周 proposal/tasks 的开放问题清单里，凡属架构师职权（接口字段、条目时刻）就标「待方赫」，凡属组内职权（计数口径、隐私边界）就标「待组内」——**知道边界在哪，比能写出漂亮的判断更重要**。

**证据四：AI 越强，错误的杠杆越大，素养是唯一的刹车。** DEF-10 的教训很典型：AI 辅助起草的 design 文档里一段手工排版的代码块，让全组门禁红了一上午；AI 不会觉得自己「只是没按 ruff 风格写示例」。同样，我在第 3 周修 ruff 错误前用 `git worktree` 把修复前的原始输出留档——因为「修完就删红证据」会让不可复现的缺陷变成说不清的悬案。编码能力可以被 AI 放大成几乎免费，但「什么时候该留证据、什么时候该停下来问」，杠杆越大越考验人。

**所以**：素养不虚——它由可检验的具体动作组成：核对了再签字、证据与预设不符时改预设、不一致时走裁定流程、该留痕的地方留痕。编码能力在 AI 时代是杠杆，素养是握杠杆的手。
