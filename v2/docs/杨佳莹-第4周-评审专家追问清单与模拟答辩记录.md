## 二、架构决策类

**Q1（分层）**：v2 为什么拆成 sources / reports / notifiers / storage / orchestrator 这些模块？如果不拆、写成一个脚本会怎样？
- 要点：G3「一次提交对应一个任务」+ G8 并行判定。拆开后 201/202/203 三个采集器可并行（各自独立文件、互不改对方），红阶段失败能定位到具体层；写成一个脚本则一次红覆盖全流程、失败无法判断是哪一环，且破坏并行。
- 证据：`v2/specs/tasks.md` P2 并行说明、方赫第3周周报告「过大会让验收与定位同时失灵」。

**Q2（零复制）**：v2 是"从零重写"，怎么证明没有抄袭 v1、没有直接复制代码？
- 要点：零复制红线；`git diff` 对 v1 目录为空的留痕；源码静态禁词检查（无 `from smart_daily import`、无 v1 包名锚定）；v2 独立包 `smart_daily_v2`。
- 证据：红绿循环记录中每任务的「P6/零复制自查」、CI 静态扫描归档。

**Q3（ADR）**：SQLite 幂等为什么用 `UNIQUE(日期,成员)` + `ON CONFLICT DO UPDATE`，而不是先查后插？
- 要点：ADR-102；先查后插有竞态、两步非原子；UNIQUE 约束把幂等交给数据库保证，同日重跑只保留一行、内容覆盖更新。
- 证据：`v2/README.md` ADR-102、`test_storage.py::test_upsert_same_day_member_keeps_one_row`。

**Q4（推送量纲）**：为什么 `pushed` 必须用"应送达集合 + all"，不能用 `any`？
- 要点：`any` 让部分送达被判成功（DEF-02）；应送达 6 条（4 邮件+1 群+1 教师邮箱），任一失败都不算送达。
- 证据：`v2/README.md` §2、DEF-02 闭环记录、C7 用例。

## 三、测试与质量类

**Q5（可测性）**：C6 性能项为什么不算验收、不写计时用例？
- 要点：成功率需 fixture 注入 100 条 + 剥离真实网络 + 固定计时口径，当前不具备；按 TK-607 验收③降为观察项，恢复须组内评审。
- 证据：`acceptance_matrix.md` C6、`v1/specs/proposal.md` C6 行。

**Q6（回归生成）**：第4周要求"从验收标准生成回归测试"，你们怎么保证 C1–C10 每条都有用例兜住、而不是想到哪测到哪？
- 要点：验收矩阵把每条 C 的成功标准映射到 pytest nodeid；本次全量 267 passed、C1–C10 硬验收 9 条全绿（C6 观察项除外）；矩阵 v2.2 逐条判定附实测输出。
- 证据：`v2/tests/acceptance_matrix.md` v2.2、回归测试全量执行报告-第4周。

**Q7（覆盖率）**：覆盖率从 97% 变成 93%，是不是质量下降了？
- 要点：⚠️ 不是。分母（语句数）从 287 涨到 874，新模块大量落地、部分模块（notify_push 79%）尚有余量；按 G5 不跨时点拼数据，百分比不可直接比。`config.py`/`members.py` 已补到 100%。
- 证据：覆盖率报告 §8、回归执行报告 §2 版本差异说明。

**Q8（真绿）**：怎么证明你们的测试是真跑出来的、不是编的或改绿？
- 要点：本机实跑命令 + 输出时间戳 + CI run 号归档；红绿循环记录保留 RED→GREEN 两个提交；失败用例（如假 token 401）真造异常。
- 证据：`v2/docs/testing/证据/`、`方赫-红绿循环记录-第3周.md`、CI run `45033546323` 等。

- 证据：各任务「C1/G6 自查」、`赵蕊-第3周-零复制与密钥自查.md`。

- 证据：`docs/ai-usage-log.md`、AI 使用合规声明汇总（配置产出）。

## 五、异常处理与边界类

**Q12（两种空）**：当天没数据和三源全挂，处理方式一样吗？
- 要点：⚠️ 必须区分。合法空 → 显式「今日无工作记录」、团队日照发；三源全失效 → 抛 `AllSourcesUnavailableError`，禁止静默返回空日报（否则"假成功"）。
- 证据：C8 判定、`test_fallback.py`、`test_generator.py`。

**Q13（降级）**：假 token 注入后系统怎么反应？会不会崩？
- 要点：源抛 `SourceUnavailableError` → 降级链切下一源、主流程不中断、原因进 `reasons[]` 按序留痕；C2 已实测通过。
- 证据：`test_source_github.py::test_invalid_token_401_raises_source_unavailable`、`test_fallback.py`。

**Q14（身份）**：同一个人多个 GitHub 登录名怎么办？不同人会不会被合并？
- 要点：按归一化（大小写/空格变体）归并到一份；不同人不合并（`record_id` 互不相交）；未映射身份告警但不丢。C3 通过。
- 证据：`test_integration_identity.py`、`identity.py`。

## 六、并发与幂等类

**Q15（幂等）**：日报任务跑到一半崩了、重跑一次，会不会重复落库或重复推送？
- 要点：落库层 UNIQUE(日期,成员) 保证同日重跑只一行、覆盖更新；⚠️ 推送层幂等是另一回事，需分场景说明（见 Q16）。
- 证据：ADR-102、C5 用例。

**Q16（⚠️ 高风险·DEF-05）**：你说 6 条全 ok 才算送达，那如果某个成员根本没邮箱、压根不产生回执，分母怎么算？是不是会假成功？
- 要点：**如实承认这是未修 P0（DEF-05）**。当前编排层 `orchestrator.py` 第 91 行 `expected = set(results)`，应送达集合直接取自已产生回执的集合，分母偏小；纯函数 `all_delivered` 测试绿不代表端到端修复。落点 TK-V2-404/501/605，issue #19（第 3 周返工，方赫+赵蕊），尚未修。不得声称已解决。
- 证据：缺陷清单 §DEF-05、回归执行报告 §5 专项。

**Q17（范围变化）**：变更涟漪演练如果真要加考勤采集，哪些规范要跟着变？
- 要点：proposal（范围/成功标准）→ design（接口/数据）→ tasks（任务）→ 测试用例 → README 契约，逐层同步；且须先过合规评审。这是"变更涟漪"的核心考点。
- 证据：指导书第4周「对每类变更说明规范如何跟着变」、`v1/specs/proposal.md` N3。

**Q18（tag/发布）**：v2 的发布 tag `v2-superpowers` 打在哪、message 含什么？
- 要点：按 BRANCHING.md，里程碑 tag 只打在 `main` 的发布提交（dev 临时 tag 须 `-rc`）；message 含四项：日期 / 基线提交号 / 三份规范版本号 / 已知缺陷或限制（DEF-05 须列入）。⚠️ 当前门控未齐（任务未全勾销、main 未合并 v2、code review/release notes 未齐），tag 尚未打，属第4周配置产出、待门控满足后执行。

**Q20（实时提醒真实生效了吗）**：C10 说飞书群收到消息，你们真的往群里发过吗？
