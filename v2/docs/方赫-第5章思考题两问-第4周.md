### 第 1 问 · 规范守护 CI 应该设在哪三个检查点？

**结论先说**：本项目把规范守护 CI 设在「静态与格式 → 测试与覆盖率 → 规范与代码一致性」三个检查点上，分别守"写得规不规矩""跑得对不对全不全""规范和代码有没有脱节"。前两个已在本组落地并实测全绿，第三个目前是缺口、靠人工兜底——这个诚实的缺口本身就是答案的一部分：三检查点是目标形态，不是现状宣告。

**第一道：静态与格式检查——守住"代码写得规矩"。** 对应 `.github/workflows/ci.yml` 的 lint job：`uv run ruff check .`（规则 E/F/I/B、line-length 100）+ `uv run ruff format --check .`。2026-11-24 实测 `All checks passed!` / `100 files already formatted`（出处：`.github/workflows/ci.yml` lint job、《方赫-第4周-规范守护自检记录》§一）。这一道的价值在本周被真实验证了一次：DEF-10 正是 design 差异版里的 `collect()` 契约代码块手工排版不符 ruff 风格，被 `ruff format --check` 扫出致 CI 红，按甲案把代码块改成规范格式后恢复（出处：`1e5e970`、赵蕊缺陷清单）——**格式门禁连"文档里的代码示例"都管住了**，这说明第一检查点不只是洁癖，而是防止规范示例本身误导实现。

**第二道：测试与覆盖率检查——守住"行为对、覆盖全"。** 对应 test job：`uv run pytest -q --cov=smart_daily_v2 --cov-fail-under=80`，低于 80% 直接让 CI 失败。实测 `273 passed`、覆盖率 **93.07%**（出处：同上 CI 文件、《规范守护自检记录》§一）。覆盖率下限的意义是"没有测试保护的代码不许悄悄进主干"；本组 2026-11-23 曾用它兜住 C5 storage 落库缺口补测（20 passed）与 C10 通知 workflow 补测（9+7 passed），这些缺口若无人测，功能看着有、质量是空的（出处：`v2/tests/acceptance_matrix.md` v2.2 回写段）。

**第三道：规范与代码一致性检查——守住"改了代码没改规范"。** 这是变更涟漪的核心防线：PR 触及 `v2/src/**` 时，应检查 `v2/specs/**`（proposal/design/tasks）是否同步更新，或明确豁免。本组当前**尚未自动化这一道**——CI 只有 lint/format/test，没有比对 specs 与源码的 step，也没有 pre-commit hook（出处：《规范守护自检记录》§二：`git config core.hooksPath` 无自定义路径）。现在靠三层人工兜底：design §8-B 登记同步义务、DEF-05/DEF-10 缺陷登记、issue #23 催办。补强方向（CI 加 specs 伴随检查 / pre-commit hook）已登记 ☐ 待全组评审——**因为改门禁口径涉及全组纪律，架构师不能一个人加**。如实把它写成"待补的检查点"而不是假装已有，正是工程素养的体现（呼应第 2 问）。

**三道的关系**：前两道是"自动挡"，保证代码自身的基底质量；第三道是"规范护栏"，保证实现不偏离 SDD 的规格。少任何一道：缺第一道则风格漂移、缺陷难读；缺第二道则无测试保护、质量无底；缺第三道则代码与规范脱节——变更涟漪里最隐蔽的缺陷正是这一种（改了实现忘了改 design，或反过来），而它恰恰是 SDD 最不能丢的防线。

### 第 2 问 · AI 时代"工程素养重于编码能力"，你同意吗，给出你的证据。

**结论：同意，但要加上限定——不是编码能力不重要，而是当 AI 能把"写代码"这件事大规模代劳时，决定产出质量的瓶颈从"会不会写"转移到了"会不会判断写什么、写得对不对、该不该签"。** 本组四周实践里有四条一手证据支持这个判断。

**证据一：会用 AI 写代码，但如果规范没写清，AI 写得再快也是白写——判断力决定方向。** 第 3 周 red 阶段多次暴露：803 的 workflow 未动时红 `2 failed / 5 passed`，失败原因是 workflow 仍指向 v1 入口、仍用 `pip install httpx`，而不是脚本自身有 bug（出处：红绿记录 303 行起）；这要求写测试的人先读懂"方案 B 的文字契约"，才能判断红在哪里、该改什么。AI 能瞬间生成一段代码，但"这段实现有没有兑现契约"的判断，靠的是工程素养——读规格、对契约、定位偏差。

**证据二：最难的 bug 不是编码难，是照着代码写测试会漏掉规范陷阱——这靠"从标准出发"的素养。** 605 从 C7「全部 ok 才算成功」导出三组用例，专堵 `all([]) == True` 的真空真陷阱；若照着当时 `any()` 的实现写测试，"任一成功即送达"会被判通过，语义偏差永远发现不了（出处：红绿记录 105 行起）。503 的排序 bug 更典型：实现写 `member DESC`，原测试用中文名因 Unicode 码点巧合蒙对，补一条英文名断言才让 bug 以 `19 passed / 1 failed` 暴露（出处：红绿记录 188 行、第 5 章思考题第 3 周第 1 问）。这些不是"代码写不出来"，是"不按标准校验就看不出错"——AI 会顺着既有实现生成看起来合理的测试，恰恰缺从规范倒推的那一步。

**证据三：职责边界与留痕是 AI 替代不了的"人"的部分。** 本组自 TK-V2-203 起定下纪律：红 / 绿 / 收尾三阶段在 Claude Code 会话内跑，人（经 WorkBuddy）只做只读核验、补日志与记录、提交推 dev，不改源码/测试/lint、不代做收尾（出处：`v2/docs/方赫-方法切换回顾.md`、第 3 周周报告 §方法论）。为什么敢让 AI 写、却坚持人核验？因为**AI 产出必须有人签**：规范文件（specs/）与签字栏是"人类的领地"，四周 AI 使用日志连续登记、四色清单分级（出处：`docs/ai-usage-log.md`），每一份 AI 起草的文档都标 ☐ 待本人核验、由本人签认后才算数。签认这个动作承担的是责任，而责任无法外包给工具——这是工程素养的核心，不是编码技巧。

**证据四：AI 生成的规范草稿也会带缺陷，发现缺陷靠素养不靠工具。** 本周 DEF-10 就是 AI 辅助起草的 design 文档里的代码块触发 CI 红（出处：`1e5e970`）；本侧起草 design 时主动登记三处规范冲突（行格式、降级语义、#21 source 交叉影响）而非悄悄拍板（出处：`v2/specs/design.md` 变更记录与 §8-B）。还有 DEF-05：AI 备料漏写 `error` 契约导致实现侧少补标记、与赵蕊测试侧冲突——根因在备料（人的输入）不在 AI 执行（出处：AI 日志 DEF-05 补绿轮记录）。这些例子说明：工具越强，越需要人具备"看出哪里不对、该找谁裁定、如实登记不隐瞒"的素养。

**限定与反面**：我不同意把这句话推到极端——没有编码能力，连 AI 生成的代码都 review 不了、红绿输出都读不懂，工程素养就是空中楼阁。本组的实际分工是"AI 做实现草案、人逐行 review 后接受"（例如 `base.py` 的 K8 继承 / K5 keyword-only / 无平台字段三点由本人逐行核，出处：红绿记录 39–41 行）——**编码能力是门槛，工程素养是天花板**。AI 时代真正的变化是：前者可以借工具补足，后者只能靠对规范、责任与边界的持续坚守慢慢长出来。
