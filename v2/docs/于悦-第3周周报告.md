### 第 1 问 · 任务粒度过大和过小分别会出什么问题？

**结论先说**：我写 `v2/specs/tasks.md` 时定的尺子是第 8 行那句——「一条任务 = 一个可验证交付物 = 一次提交」。粒度过大，验收标准写不具体、可测性判不了，红绿循环退化成"跑一遍全量绿"；粒度过小，任务失去独立可验证的交付物，依赖图碎成一地、共享文件反复交接，只剩形式上的勾选。

**第一，过大首先毁的是验收标准的可测性——这是需求这端最直接的痛点。** 我在第 2 周做可测性评审时用的判定口径是「输入条件、观测输出、阈值/状态三要素齐备才叫可测」（15 条判成可测 7 / 有条件可测 5 / 不可测 3，见 `v1/docs/于悦-可测性评审意见.md`）。如果把一个大任务（比如把主编排、落库、历史查询、CLI 并成"实现编排层"），它的验收标准只能写成"能跑起来"——输入、输出、阈值三要素缺两个，根本没法判可测，更别说写失败测试。本组把它们拆成 501→502→503→504 四条串行，每条才有具名验收（如 503 的同日 `member` 升序、504 的退出码表），测试基线按 156→166→176→186→196 逐级抬升。粒度合适的第一条判据于是很清楚：**这条任务的验收标准能不能写全三要素**。

**第二，过小会让交付物失去可验证性，还制造共享文件冲突。** 若把 604「条目行格式与 1:1 计数」拆成"表头行""条目行""占比列"三个独立任务，任何一条单独都验收不了——它们共用 601 夹具和 304 生成器（604 依赖 601、304，见 tasks.md L136），按 G8「共享文件必须串行」三条只能排队，切分只增加交接成本。三个采集模块也是同理：P2 能并行是因为 `github.py` / `feishu_tasks.py` / `feishu_chat.py` 文件不重叠（tasks.md L226 记着 v1 曾把三个飞书功能塞进一个文件导致串行），粒度切到文件边界为止；再往下切没有意义。

**第三，粒度和可测性是同一件事的两面，标准没定死就先别谈拆任务。** 我审 15 条标准时，那 3 条"不可测"的共同症状就是表述模糊或依赖无法构造的条件——这跟"任务粒度过大/边界不清"是同一个病。U1 降级链口径冲突就是活例子：proposal C8 写「三源全失效必须抛明确异常」，v2 README §2 写「采集失败返回空列表、不中断流程」，两条规范打架；这时就算把任务拆得再细，也定不出验收标准，最后得靠架构师在 issue #14 用 K1 裁定"（未实现时）⏸、实现时返回空列表但记原因、全失效抛异常"，规范先收紧，任务才落得下去。

**所以**：判断粒度是否合适，我的三条尺子是——能否写出具名失败测试、能否对应一次独立提交、验收标准能否写全"输入/输出/阈值"三要素。本组 36 条按七段链路排布并标注依赖与并行组（tasks.md L101、L105–L144），正是把粒度卡在这三条的交集上。

### 第 2 问 · 从验收标准生成测试与从代码生成测试，哪种更能发现规范缺陷？

**结论先说**：更能发现规范缺陷的是**从验收标准生成测试**，而且前提是标准本身可测——这一步恰恰是需求这端的责任。从代码生成的测试只能证明实现与自己一致，规范的矛盾和漏洞会被实现的偶然行为填平、固化下来。

**第一，我做的可测性评审就是"先审标准、再谈测试"这道工序。** 15 条逐条判三档，不可测的给改写建议，就是不让含糊的标准溜进测试环节。如果照着代码生成测试，这些模糊标准会被实现"顺手"选的那个解释填上，规范到底有没有矛盾永远暴露不出来——测试全绿反而给了假安全感。

**第二，标准里的矛盾只有逐条对着规范看才能发现，从代码看不出。** U1 降级链那两处冲突（proposal C8「三源全失效抛明确异常」vs README §2「返回空列表不中断」，见 tasks.md §8.2 U1）就是靠逐条核对规范发现的——两条都对，但放一起矛盾。如果从代码生成测试，实现选了哪条，测试就把哪条当"正确预期"写死，冲突被掩盖。最后 K1 裁定后我才能把 tasks.md 里 104/602 的 ⏸ 解锁、状态改 ⬜（提交 `f92bcf0`）——**先有规范裁决，才有可测的验收标准，才有测试**，顺序不能反。

**第三，标准不可测时，得先补契约才能生成断言，这正是需求端的活。** C10 原文"日报显示中文名"没有 `MEMBER_DISPLAY_NAMES` 映射契约就无法生成断言，必须先补契约（后来由架构师出方案、804 落地），才能写测试。我在本周 code-review 提的 R1-01 也是同一类问题的反面：`test_dispatch.py` 用 `all_delivered(set(results), results)`，expected 直接取自回执自身——这就是"从结果/从实现生成测试"，只检查"已产生的回执是否都 True"，少发一路但没写回执的情形会被全放过（见 `v2/docs/于悦-第3周-code-review互评记录.md` R1-01）。从代码生成测试的盲区就在这里：它把现状合法化。

**第四，标准可测之后，从标准生成的测试还能照出实现哪里没落地。** 方赫本周的 503 排序 bug 是现成证据：契约（沿用 v1 的 `member` 升序）要求同日升序，实现写成 `member DESC`，原测试用中文名「甲乙丙丁」因 Unicode 码点巧合蒙对了 bug；按契约补一条英文名断言才让它以 `19 passed / 1 failed` 暴露。这是"标准 → 测试 → 发现实现偏离标准"，不是"代码 → 测试 → 确认代码没变"。

**落到我这一端**：需求的责任不是把标准写得漂亮，而是写到可测——三要素齐、没有自相矛盾、契约都定义清楚；测试从这样的标准生成，才有能力反过来指出实现哪里没落地、规范哪里还有洞。站在代码这边写测试，只会把现状当真理。
