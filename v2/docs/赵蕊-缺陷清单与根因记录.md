### DEF-01 采集器吞异常后跳过兜底，产出 0 条空日报

| 字段 | 内容 |
| --- | --- |
| **编号** | DEF-01 |
| **发现时间** | 2026-11-11（v1 修复提交 `130ccf7`，作者 yjy120，提交信息「fix: 降级原因与未映射账号补日志」） |
| **发现环节** | 评审 / v1 复盘（被 `v2/README.md` §4 收录为「坑」） |
| **现象** | 采集器吞掉数据源异常后返回空列表，调用方据此认为「成功但当天 0 条」，**不再走兜底数据源**，最终产出 0 条空日报。可复现命令：`git show 130ccf7 --stat`，改动落在 `src/smart_daily/collectors/base.py` 与 `src/smart_daily/push/members.py`。 |
| **根因** | **已确认**。`collect_with_fallback()` 用 `except SourceUnavailableError: continue` / `except Exception: continue` 静默吞掉异常，降级成功时 `errors` 列表不进异常消息、也不打印，于是「前一个源为什么挂」在日志里完全不可见。属于**可观测性缺失导致误判**：把「降级了」看成「没数据」。<br>证据：`git show 130ccf7 -- src/smart_daily/collectors/base.py` 显示新增两处 `print(f"[source] {src.name} 不可用：…")`；`git show 130ccf7 -- src/smart_daily/push/members.py` 显示新增 `print(f"[push] 身份未映射：…")`。 |
| **影响面** | 日报内容为空但流程「看起来成功」；用户拿不到任何「数据源异常」的信号，问题被推迟到很久以后才暴露。 |
| **v2 修复口径** | 依据 `v2/README.md` §1 **ADR-103**（异常驱动降级；采集器自身不重试，由上层 orchestrator 统一降级）与 §2 契约。**v0.2 更新**：§2 该句已于 2026-11-17 按 issue #14 K1 改写为「源抛 `SourceUnavailableError` → 切下一源；源返回空列表 → 停止降级并返回空结果（空列表 ≠ 失败）；全部源抛异常 → 抛 `AllSourcesUnavailableError`」（`58d4fec`）。<br>故 v2 的修复口径是**区分「异常」与「空列表」两种语义 + 强制降级原因可见**，而不是笼统地「降级返回空列表」。承接任务：`TK-V2-104`（降级链）、`TK-V2-602`（降级注入）。 |
| **验证方式** | `TC-104-01`～`TC-104-04`（降级链）、`TC-602-01`～`TC-602-03`（降级注入）、`TC-603-03`（「当天无数据」vs「三源全坏」两种输出必须不同）。 |
| **状态** | **已闭环**（v1 `130ccf7` 落地日志；v2 由 ADR-103 + `58d4fec` 契约承接） |

### DEF-02 `pushed = any(ok)`：部分送达被判成功

| 字段 | 内容 |
| --- | --- |
| **编号** | DEF-02 |
| **发现时间** | 2026-11-10 及以前（v1 修复提交 `3f2b3ee`，2026-11-10 18:19）；来源 `specs/tasks.md` 第 240 行 TK-707，评审编号 T-01 / RT-01 |
| **发现环节** | 评审（红队评审意见 RT-01 / RT-02 / RT-07 汇入 TK-707） |
| **现象** | 推送结果用 `any(r["ok"] for r in push_detail)` 汇总，只要**有一条**回执成功就把整体判成 `pushed=True`，邮箱缺失或通道失败的那些成员被掩盖。可复现：`git show 3f2b3ee -- src/smart_daily/orchestrator.py`，可见被替换的那一行 `- pushed = any(r["ok"] for r in push_detail)`。 |
| **根因** | **已确认**。判定用的量纲错了：`any` 回答的是「**是否存在**至少一次成功」，而「送达是否完成」需要问「**应送达的每一条**是否都成功」。另外 `all([])==True` 的防空语义也没处理，空回执列表会被判成功。 |
| **影响面** | CLI 退出码随之失真（`pushed=True` → 退出码 0），自动化流程无法感知部分失败；漏发成员的日报无人知晓。 |
| **v2 修复口径** | `v2/README.md` §4 第 2 条原文明确：「v2 必须用**应送达集合 + `all`**」。归属决策见 **ADR-103**（降级与失败由上层编排统一判定）。承接任务：`TK-V2-404`（分发规则与送达判定）、`TK-V2-605`（送达判定用例）。<br>**v0.2 补充**：按 issue #14 K6，应送达数量由 5（4 邮件 + 1 群）改为 6（+1 教师邮箱），只加通道不改计数会让 `all_delivered()` 永远判 False。 |
| **验证方式** | `TC-605-01`（6 条全 True → 判成功）、`TC-605-02`（任一 False → 失败且 `pushed=False`）、`TC-404-04` / `TC-404-05`。 |
| **状态** | **已闭环**（v1 `3f2b3ee` 改为 `bool(push_detail) and all(r["ok"] for r in push_detail)`）；**但分母问题未解决**，见 DEF-05 |

### DEF-03 身份映射大小写敏感，与实时通道 `.lower()` 不同规

| **影响面** | 提交被记到错误的人名下或落入「未映射」，个人日报缺项；两条链路对同一账号给出不同结论，难以对账。 |
