### 第 1 问 · 任务粒度过大和过小分别会出什么问题？

**结论先说**：粒度过大，任务无法被单个验收标准判死，红绿循环退化成"跑一遍全量绿"，失败定位、并行排期、小步提交三件事同时失效；粒度过小，任务失去独立可验证的交付物，依赖图碎成一地、共享文件被迫反复交接，最后只剩形式上的勾选。合适的尺子是 `v2/specs/tasks.md` 第 8 行定的那句——「一条任务 = 一个可验证交付物 = 一次提交」。

**第一，过大会让验收与定位同时失灵。** 全局约束 G3（L46）写「测试先于实现：先写失败测试（红）→ 最小实现（绿）→ 重构」，G4（L47）写「一次提交对应一个任务」。若把主编排、落库、历史查询、CLI 合成一个"实现编排层"的大任务，红阶段只能写一个覆盖全流程的用例，失败时无法判断是 `run()` 的降级链、`storage.save_report()` 的幂等，还是 CLI 的退出码；本组把它们拆成 501→502→503→504 四条串行，测试基线按 156→166→176→186→196 逐级抬升，每级都有具名失败用例（例如 503 的 `list_reports` 10 条红全是 `AttributeError: module 'smart_daily_v2.storage' has no attribute 'list_reports'`，见 `v2/docs/方赫-红绿循环记录-第3周.md` 183 行起）。大粒度还会破坏 G8 的并行判定：三个采集模块若像 v1 那样塞进一个文件（`tasks.md` L226 记「v1 曾把三个飞书功能塞进一个文件导致串行」），就没有 P2 并行可言。

**第二，过小会让交付物失去可验证性，还制造共享文件冲突。** 若把 604「条目行格式与 1:1 计数」拆成"表头行""条目行""占比列"三个独立任务，任何一条单独都无法验收——它们共用 `tests/test_integration_format.py` 与 601 夹具、304 生成器（604 依赖 601、304，见 tasks.md L136），按 G8「共享文件必须串行」三条只能排队，切分只增加交接成本；605 的 13 条执行项全部挂在一个 `delivery_harness` fixture 上，拆得更细会把"6 通道全真 / 单点假 / 空 expected 判 False"的对照关系拆散，反而测不出 C7「全部 ok 才算成功」的红线（红绿记录 105 行起）。

**第三，粒度要小到能承载一条针对性断言，但不能小到脱离契约。** 503 的排序 bug 是现成例子：实现写 `member DESC`，原测试用中文名「甲乙丙丁」，因 Unicode 码点甲(U+7532) > 乙(U+4E59)，DESC 恰好把甲排前，**蒙对了 bug**；按用户裁定的方案 1 只补一条英文名断言（`["Alice","Bob","Charlie"]`），红 `19 passed / 1 failed`，改回 member 升序后 `20 passed / 186 passed`（红绿记录 188 行）。这条断言值得单独立一个微型红绿，是因为它对应一条具体契约（沿用 v1 的 member 升序）；若再拆到"改一个字符串常量"这种粒度，就没有可验证产出可言了。

**所以**：判断粒度是否合适的尺子不是行数或工时，而是三条——能否写出具名失败测试、能否对应一次独立提交、能否在不冲突的前提下并行。本组 36 条任务按七段链路排布并标注依赖与并行组，正是把粒度卡在这三条的交集上。

### 第 2 问 · 从验收标准生成测试与从代码生成测试，哪种更能发现规范缺陷？

**结论先说**：更能发现规范缺陷的是**从验收标准生成测试**。从代码生成的测试只能证明实现与自己一致——实现的偶然行为会被写成"预期"，规范的漏洞恰好被固化下来。两者不是二选一：前者是验收基准，后者只适合做回归保护。

**第一，本周的 503 排序 bug 就是"从代码生成测试"会漏掉的那类。** 契约（沿用 v1 的 member 升序，见 `v2/specs/tasks.md` 503 条目与 `storage.py` docstring）要求同日按 member 升序，实现却写成 `member DESC`；测试若从代码导出，会把 DESC 当成正确预期而永远通过。实际做法是把 v1 契约当断言基准并补英文名断言消除中文码点的巧合，才让 bug 以 `19 passed / 1 failed` 暴露（红绿记录 188 行）。这是"标准 → 测试 → 发现实现偏离标准"，不是"代码 → 测试 → 确认代码没变"。

**第二，从标准生成的测试能直接照出规范的矛盾与遗漏。** 605 从 C7「全部 ok 才算成功」导出 6 个 scope 逐一 false、3 真 3 假、空 expected 判 False 三组用例，专门堵住 `all([]) == True` 的真空真陷阱；若照着当时的 `any()` 实现写测试，"任一成功即送达"会被判为通过，C7 的语义偏差永远发现不了（红绿记录 105 行起）。803 更直接：`v2/tests/test_notify_workflow.py` 从方案 B 的文字契约读出七条断言（只 main/dev、`notify*.yml` 单通道、`pip install -e ./v2`、`python -m smart_daily_v2.notify_push`、四个 env 键取自 secrets、Python 3.13、G2 零复制），workflow 未动时红 `2 failed / 5 passed`，正好是 workflow 仍指向 v1 入口和仍用 `pip install httpx` 两处**规范未落地**，而不是脚本自身的 bug（红绿记录 303 行起）。

**第三，从代码或桩生成测试有真实盲区，靠真实外联才补上。** 601 的 mock 夹具与既有 235 条用例全绿，但真实跑 GitHub 时才撞出两个 bug：`author=None` 被序列化成空串 `author=` 导致采 0 条，以及顶层 author 为 null 时 `commit["author"]["login"]` 崩溃（红绿记录 246 行起）——桩的"理想形态"覆盖不了规范没写到的真实形态。后续补的 `test_source_author_none.py` 与 `test_source_github_null_author.py` 也是从"契约应如何处理 null"倒推出的用例，而非从既有实现导出。

**第四，前提是标准本身可测，否则该先审标准。** 于悦的可测性评审意见（15 条：可测 7 / 有条件可测 5 / 不可测 3，见 `docs/ai-usage-log.md` 2026-11-09 条）就是先给标准分级；像 C10 原文"显示中文名"若无 `MEMBER_DISPLAY_NAMES` 映射契约就无法生成断言，必须先补契约。本组 803/804 先由架构师出方案 B 与 `notify_push.py` 契约、再写 workflow 契约测试，顺序正是"标准可测化 → 测试 → 实现"。

**落到我这周**：红阶段断言一律先按验收标准写，绿阶段才按实现补回归，最后用真实外联兜底标准未覆盖的形态。原因如上——只有站在标准这边，测试才有能力反过来指出规范哪里没落地、哪里自相矛盾；站在代码这边，测试只会把现状合法化。
