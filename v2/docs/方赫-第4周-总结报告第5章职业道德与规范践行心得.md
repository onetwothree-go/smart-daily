## 5.1 我理解的"职业道德与职业规范"在本项目里是什么

这门课讲职业规范，我起初以为是一堆抽象条文；四周做下来，它在我这里落成了**四条能拿证据验的行为**，而不是口号：

1. **诚信**——如实留痕，不虚报、不倒填、不伪造证据；做不到的事写"未做"，不写得很好看。
2. **责任**——谁产出谁签认；规范文件与签字栏是"人类的领地"，不替他人签、不替他人下结论。
3. **敬畏规范**——规格先行、契约约束、门禁当真；发现规范与代码不一致按缺陷处理，而不是绕过去。
4. **隐私最小化**——采集他人数据只取完成任务必需的最小集，不碰与需求无关的敏感字段。

下面四节按这四条交代我具体做了什么；§5.7 单列我没做到的，不藏。

## 5.2 诚信：让每一句结论都能回查

**体会最深的一次，是承认 bug 的根因在我这侧。** DEF-05（应送达集合分母偏小）最初表现为实现与测试对不上，赵蕊的测试侧红用例要求缺回执时补 `error="no_recipient"`。复盘时我没有把它记成"实现的偶发失误"，而是如实写清根因在**备料漏写 error 契约**——AI 是按我的输入执行的，输入缺了，实现自然少补标记（出处：`docs/ai-usage-log.md` DEF-05 补绿轮记录、《方赫-第4周-规范审计报告》§三）。把根因写回自己身上不舒服，但只有这样才能防止下次再漏；最终 `orchestrator.py` 改为独立构造 expected、按契约逐项回填，`2baf68d` 落地、273 passed 含测试侧用例。这件事让我确认：**职业诚信的第一条不是不说谎，是出错时肯把责任链往自己这边多追一步。**

**"如实"还体现在对未完成状态的诚实。** 变更涟漪 B 组余 6 项（配置 scope、`user_id` 映射、C11 用例落位、tasks 9xx、计数分母、迟到早退时长）我没有为了报告好看写成"已同步"，而是逐项标 ☐、发 issue #23 公开催办；`design.md` 里也如实写"规范侧已推进到可评审，代码侧因前置条件未齐而未动"（出处：`v2/specs/design.md` §8-B、issue #23、《第2章过程回顾》§2.4）。现场改造考核（15 分钟）与正式答辩尚未进行、模拟答辩真人演练待组织，这些我也留在"未完成"栏，没有假装已经练过。

**AI 使用全程留痕是诚信的制度化的样子。** 本组四周 AI 使用日志连续登记、按四色清单分级；我自己的每份 AI 起草产出都标 ☐ 待核验、经我逐句核对后才落签（出处：`docs/ai-usage-log.md`、第 4 章素材 §4.2）。日志里还记了一次三源核验"主动作废"——发现证据不够硬就废掉重来，而不是留着充数（出处：第 4 章素材 §4.1 说明、§4.5）。这些留痕的意义是：**让"我说的"和"仓库里能查到的"对得上**，没有对不上的地方。

## 5.3 责任与边界：签字栏是"人类的领地"

第 3 周中段我做了一个现在看来最符合职业边界的决定：**把红 / 绿 / 收尾三阶段的执行权交回 Claude Code 会话，我（经 WorkBuddy）只做只读核验、补日志与记录、提交推 dev，不改源码 / 测试 / lint、不代做收尾**（出处：`v2/docs/方赫-方法切换回顾.md`、第 3 周周报告 §方法论）。当时主要是为了职责分离，做完后才意识到这同时是一次职业伦理实践：**AI 可以写，但"谁对结果负责"不能跟着外包。**

由此形成三条我守得很紧的边界：

- **规范文件与签字栏由人签。** 四周里 AI 起草过大量文档（design、审计报告、过程回顾、思考题答案），但没有一份是"生成即生效"——每一份都标 ☐、经我核对、由我签认。是不是我亲手敲的每一行并不改变责任归属；签名承担的是"我核过、我负责"，这个动作外包给工具，责任就悬空了（呼应第 4 周思考题第 10 问：工程素养重于编码能力，出处：`v2/docs/方赫-第5章思考题两问-第4周.md` 证据三）。
- **不替他人维护的对象下结论。** 缺陷清单 DEF-05 / DEF-10 的状态行归赵蕊核销，tasks.md 状态列归由于悦维护，proposal 差异版归需求侧评审——我在《规范审计报告》§四里把它们逐项标成"归口正确、待维护人闭环 / 更新"，自己不勾、不代判（出处：同上审计报告 §四）。待裁定项一律写 ☐ 而不是替全组拍板，哪怕我很清楚倾向哪一个方案（A 组契约走的是全组追认流程，不是我一个人定，出处：`v2/specs/design.md` 变更记录）。
- **签认表述要干净。** 早期文档里出现过在签字栏解释签认来由、替签名附加免责说明的旧话术，我明确要求删除——签名就是签名，附加一堆说明反而让人分不清责任到底在谁。后来我清了 6 份文档的这类表述；盘点时发现第 3 周周报告与 code-review 互评记录里还有两处残留，已列入待清（见 §5.7）。**干净的签认 = 签的人、日期、范围清楚，不附加免责式说明。**

## 5.4 敬畏规范：把门禁当真

SDD 与 TDD 我一开始是按"老师要求"照做，四周下来变成了真信——因为门禁真的拦住过问题，而不是走形式：

- **测试从契约生成，不从代码生成。** 605 从 C7「全部 ok 才算成功」导出三组用例，专堵 `all([]) == True` 的真空真陷阱；如果照着当时 `any()` 的实现写测试，"任一成功即送达"会被判通过，语义偏差永远发现不了。503 的排序 bug 更典型：原测试用中文名因 Unicode 码点巧合蒙对，补一条英文名断言才让它以 `19 passed / 1 failed` 暴露（出处：`v2/docs/方赫-红绿循环记录-第3周.md` 105 行起、188 行起）。**这两件事教我的是：顺着实现写测试等于给 bug 盖章，规范才是测试的唯一源头。**
- **格式门禁连规范文档里的代码块都管。** DEF-10 是 `design.md` 里 `collect()` 契约代码块手工排版不符 ruff 风格，被 `ruff format --check` 扫出致 CI 红；我按甲案改代码块本身、没有去动门禁口径（出处：`1e5e970`、`v2/docs/方赫-第4周-规范守护自检记录.md` §一）。守规矩要先从自己写的规范示例守起，否则规范自己就是反例。
- **覆盖率与零复制是可复跑的红线。** CI 设 `pytest + --cov-fail-under=80`，实测 273 passed / 93.07%；v2 不复制 v1 一行源码，`grep -rnE "^from smart_daily import|^import smart_daily$" v2/src v2/tests` 持续 0 命中（出处：`.github/workflows/ci.yml`、`v2/tests/acceptance_matrix.md`、第 2 章 §2.3）。这些不是"做完就扔"的检查，是每次提交都要过的门。
- **主动登记规范冲突，而不是悄悄拍板。** 起草 `design.md` 差异版时，我把三处规范冲突（行格式、降级语义、#21 source 交叉影响）写进变更记录，而不是自己消掉；#21 的 504 口径确认也只记"现行四项、第五源落地后再同步"，没在留痕里预改结论（出处：`v2/specs/design.md` 变更记录与 §8-B、`v2/docs/方赫-第3周-TK-V2-504两处口径确认留痕.md`）。**规范与实现一旦脱节，最隐蔽也最伤——变更涟漪里最该防的就是"改了实现忘了改 design"。**

## 5.5 隐私最小化：考勤数据只取必需

教师变更单要新增飞书考勤采集，我在 design 里选了**打卡结果接口**（`POST /attendance/v1/user_tasks/query`），明确排除含定位信息的 `user_flows` 流水接口（出处：`v2/specs/design.md` §飞书接口段）。理由很直接：任务只需要"谁、哪天、上班 / 下班卡时间"，定位数据对日报毫无用处，采集了就是越界。同样地，飞书 `gen_sign()` 由 AI 参与生成但经我逐行 review、**无真实凭证入库**，密钥只登记可用性不记值；`user_id → 成员键` 映射归配置侧开通 scope 后提供，我不擅自拿测试数据顶替（出处：第 4 章素材 §4.2 红级、§4.5；`v2/specs/design.md` §8-B）。**这一节的体会是：职业伦理在代码里往往体现为一个"不做"的决定——不采那个字段、不存那个值、不用假数据糊过去。**

## 5.6 团队伦理：公开、可追溯、不越权催办

- **code-review 常态化。** 第 3 周我回应本人 5 条意见、评他人 2 次，评审意见与回应分别留痕；"对方回应 / 是否闭环"由对方本人回填，我不代填不代勾（出处：`3e1e53e`、`v2/docs/方赫-第3周-code-review互评记录.md`、第 2 章 §2.5）。
- **催办走公开渠道。** 第 4 周 B 组 6 项待裁定我没有私下口头催，而是发到 issue #23 按配置 / 需求 / 开发 / 组内会分组点名，公开可追溯（出处：issue #23）。组内同步话术我按"口语化、不像正式公文"的要求重写过——对外沟通也要考虑可读性，不是把规范文档原样甩过去。
- **全组共同决策的事情走全组。** design 0.3 经全组追认、0.4 才由我拍定；补"改代码未改规范"自动检查要改全组纪律，我只登记 ☐ 待评审，没有一个人加 hook（出处：`v2/specs/design.md` 变更记录、《规范守护自检记录》§二、第 4 周思考题第 9 问）。**架构师的权限是"提出并推进"，不是"自己说了算"。**

## 5.7 我还没做到的（如实登记）

写心得如果只写做得好的，就成了自我表扬。这三件是我明确没做到或还没做完的：

1. **"改代码未改规范"的自动检查还没建。** CI 只有 lint / format / test 三道门，没有比对 specs 与源码的 step，也没有 pre-commit hook；现在靠人工 review + 缺陷登记兜底，补强方案 ☐ 待全组裁定（出处：《规范守护自检记录》§二、《规范审计报告》§二）。这是我认为最该补的一道防线。
2. **现场环节还没经历。** 模拟答辩我只做了备料（20 题稿 + 三题 30 秒口述版），真人演练还没组织；现场改造考核（15 分钟）与正式答辩也未进行。备料齐不等于练过，我不能把"准备好了"写成"做完了"。
3. **两处早期签认话术残留待清。** 盘点发现第 3 周周报告 L80 与 code-review 互评记录 L109 还留着在签字栏解释签认来由的旧话术，与我后来"签认要干净"的要求冲突；已列入待清理，清理后再回写本节状态（出处：`v2/docs/方赫-第3周周报告.md`、`v2/docs/方赫-第3周-code-review互评记录.md`）。
