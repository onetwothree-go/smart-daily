## 五、问答原文逐轮记录

### 第 1 轮（2026-11-07）：数据源与时间窗

**Q1 数据源范围**
指导书默认的三类数据源是 GitHub 提交、飞书任务、飞书群消息。你们的日常痕迹是否都被它覆盖了？有没有还要补充的来源，比如本地 git 提交、GitLab、钉钉、邮件、Notion？另外，你们采集 GitHub 是所有仓库的提交都抓，还是只抓某个团队仓库、某个分支？
> 影响 S1–S3 的范围条目和采集层模块清单。

**回答（杨佳莹）**：
Q1:三处正式数据源就够：GitHub 提交、飞书任务、飞书群消息。我们日常痕迹全在这三处，代码在 GitHub、任务在飞书、讨论在群里，不新增别的来源。GitLab、钉钉、Notion 小组没用；邮件是 SMTP 推送通道，不是采集源，别混进来。
本地 git 提交有，但定位是降级兜底：GitHub token 失效或接口挂了才自动切过去，不算第四路正式源；mock 只用于演示和无数据日的样本数据，不是真实工作痕迹。
GitHub 只抓小组这一个仓库 onetwothree-go/smart-daily，不是各人所有仓库；抓的是默认分支 main 上的提交，dev 和 feature 分支上没合并的不计；时间窗内四个人的提交全抓，再按登录名映射归到具体成员。

**Q2 采集时间窗与推送时间**
一份日报统计的是哪一段时间：自然日 0:00–24:00、上一次日报到本次之间，还是实际工作时段（比如 9:00–18:00）？生成后计划几点推送给对方？是否要求"当天日报必须在当天送达"？如果推送时间设在 18:00，统计时段却覆盖到 24:00，18:00 之后还会有提交，这些你打算怎么算、怎么处理？
> 影响日报统计边界（自然日还是截止时间）的定义、"日报截止时间""推送频次"这两项规范，以及"时区归属"相关成功标准的写法。

**回答（杨佳莹）**：
Q2：统计窗按东八区本地自然日，从当天 0:00 到日报生成那一刻，不是 0:00-24:00，也不是 9:00-18:00 工作时段；跨时区提交按本地日历日归属，23:30 的提交算当天。
本期约定每天 22:00 生成并推送，当天 23:59 前送达。因为统计截止点就是生成那一刻，推送和统计是同一个时刻，不存在「18:00 就推、统计却覆盖到 24:00」的错位。本期由本机手动运行命令触发，不做自动定时，定时任务放到 v1.1。
22:00 之后的提交按日历日归属仍算当天，但不进当天已发的那份日报，也不回溯补采、不补发——这和「本期不做历史数据补采」是同一条范围决策，不额外加去重或补跑逻辑。

**Q3 日报有哪两种形态、给谁看**
个人日报只有本人能看，团队日报给组长和全员看，这两种形态的读者分别是谁？老师或助教是否也要收？两种日报的内容应该"完全相同，只是分别汇总"，还是团队日报里要有组长专属的内容（如全组统计、风险提示、明日安排）？
> 影响"两种日报形态"这一条范围、团队日报的字段设计，以及"两种形态分别推送"的推送策略。

**回答（杨佳莹）**：
Q3:个人日报每人一份，只发本人邮箱，别人看不到；团队日报一份，只发飞书群机器人，群里四人全员可见，不发邮件。老师助教不收，本期是组内用的课程作业工具，没有外部收件人；组里也没有单独设组长，团队日报对四人可见即可。
两份内容不完全相同，也不是简单「分别汇总」：个人日报只列该成员自己的条目，按提交/任务/消息分组，末尾统计「共 N 条，手工编写 0 条」；团队日报汇总全组，多一个自动生成的统计头「共 M 位成员、N 条记录」，成员按贡献条数降序排列，模板与个人日报一致。
不做「组长专属的风险提示、明日安排」：那需要主观判断或智能摘要，N1 已把智能摘要排除在外，也违背零手工、可追溯。组长零手工指的是自动汇总，不是再要一份人工判断报告。

### 第 2 轮（2026-11-07）：条目粒度、协作归属、无数据日

**Q4 条目粒度**
一条日报条目对应什么：一次 commit = 一条、一个飞书任务 = 一条、一条群消息 = 一条，还是按同一主题/同一时间块把多条聚合成一条？commit message 往往只有一行（"fix: xxx"），它要不要在日报里被改写成通顺描述，还是原样呈现？群消息里可能有大量"收到""好的"这类无信息量的内容，这类要不要算条目？
> 影响条目计数规则、"个人日报条目数 = 当日提交数 + 任务数 + 消息数"这条度量口径，以及"100 条提交""19 条记录"这类实测证据怎么算。

**回答（杨佳莹）**：
Q4:一条原始记录对应一条日报条目，1:1，不按主题或时间块聚合：一次 commit 一条、一个任务一条、一条群消息一条。这样「个人日报条目数 = 当日提交数 + 任务数 + 消息数」才测得准，漏一条就是采集缺陷，可以拿原始数据逐条对账。
commit message 原样呈现，不改写、不润色成通顺描述；只在详情里补客观信息（改了几个文件、增删多少行）。理由是智能摘要/NLP 归纳已在 N1 排除，原样呈现才可追溯。长消息标题取前 60 字，全文放详情。
「收到」「好的」这类群消息本期照算条目，不做语义过滤。判断「有没有信息量」是主观规则，一过滤就打破上面那条计数口径；要做的话得先定义规则并同步改 G1，放到 v1.1。

**Q5 协作成果自动归属**
两个人的协作成果（结对编程、互相 review、一起修一个缺陷）怎样自动归属到双方名下？你们实际能拿到哪些信号：GitHub commit 的 Co-authored-by 字段、飞书任务的协办人字段、群消息里的 @提及、同一条任务下的多负责人？如果这些信号一个都没有，这条成果算谁的，还是干脆只归属给提交人？同一条成果出现在两个人日报里算不算重复计数？
> 影响 S5 的范围表述、C3"跨成员关联提交"的成功标准如何定义与测试，以及"协作成果"术语的定义。

**回答（杨佳莹）**：
Q5:本期只做单一归属：提交归提交人、任务归创建人、群消息归发送人；一个信号都没有就归提交人，一条成果只进一个人的日报，不重复计数，团队日报的总条数按唯一记录数算。
能拿到的协作线索有飞书任务的协办人列表、群消息的 @提及列表，这些字段在统一数据模型里已经保留，但本期只作为可追溯线索，不拆成多个人的条目；Co-authored-by 目前没有解析。多人协作归属按代码注释留到第 2 周由关联规则补全，本期先保证单条记录完整、归属可核对。
要区分两件事：已经做到的是「身份归并」——同一个人有多个 GitHub 登录名时合并成一份日报（方赫三个账号实测合并成功）；「多人协作一条成果归双方」是另一件事，本期不做。

**Q6 无数据与缺勤日**
某成员当天没有任何提交、任务、消息（缺勤、纯开会、外出），系统怎么处理：显式标"今日无记录"、留空、继承昨日，还是允许手工补一条？如果允许手工补，手工条目和自动条目在日报里要不要有可见区分（如标注"手工"）？反过来，全组四人当天都零记录，团队日报还发不发、发出来长什么样？
> 影响 C8"边界"成功标准的写法、G1"手工新增条目数 = 0"这条目标的口径（零记录成员是否算违反），以及 mock 数据源在范围里的定位。

**回答（杨佳莹）**：
Q6:某成员当天零记录，就显式写「今日无工作记录」，不留空、不继承昨日。本期不允许手工补条目，N4 已排除日报编辑回溯，G1 要求手工新增条目数为 0，所以「手工条目要不要标注」这个情况根本不会发生；零记录成员也不算违反 G1，G1 约束的是不许手工加东西，不是要求必须有内容。
全组四人都零记录，团队日照发，内容是「共 4 位成员、0 条工作记录」加四位成员各自的零条小节。每天一份、格式统一，也才能把「今天确实没人干活」和「系统挂了」区分开。
注意 C8 说的是三路数据源全部不可用这种故障，那必须抛明确异常而不是静默返回空日报；「当天真的没有数据」是正常结果，两者不能混。mock 只用于演示和造可复现的测试样本，不能冒充真实工作数据发出去。

### 第 3 轮（2026-11-07）：隐私过滤、推送失败、数据存储

**Q7 隐私与过滤**
日报会原样呈现 commit message、飞书任务标题、群消息前 60 字。仓库、任务、群里是否会出现不能发进日报的内容，比如测试用的假 token、含密码的配置、只发给个别人的私聊性质内容、未合并分支的实验性表述？如果出现，谁来兜底：系统按规则过滤、写进红线文档靠人自觉、还是干脆不管？群消息采集是只抓团队群这一个群，还是所有群都抓？
> 影响采集层的过滤/范围边界、S3 的表述，以及是否需要一条"敏感信息不进日报"的规范条目。

**回答（杨佳莹）**：
Q7:群消息只抓团队群这一个群，由 FEISHU_CHAT_ID 指定（或用应用所在群列表的第一个），不抓所有群、不抓私聊。Q1 已经定了 GitHub 只抓 main 默认分支，所以未合并分支上的实验性提交根本不会进日报，这一类是天然规避的。
本期不做系统级的内容过滤或脱敏：判断「这是不是假 token / 密码 / 私聊性质」需要语义识别，N1 已排除 NLP 归纳，而且一过滤就打破 Q4 那条 1:1 计数口径。兜底靠三样：凭证一律从环境变量读、绝不写进代码和仓库，.env 由 .gitignore 保护；推送前跑敏感信息扫描（已有核查脚本）；群范围和凭证登记由配置管理员维护、组内不往群里发敏感内容靠人自觉。
需要在规范里加一条「敏感信息不进日报」的非功能红线，但自动过滤放到 v1.1。落地维护不是需求分析师本周的产出，这轮只是在定需求边界。

**Q8 推送失败与补发**
邮件和飞书群两个通道，如果其中一个失败（SMTP 拒绝、webhook 返回非 200、签名校验不通过、网络抖动），你们怎么处理：立即重试几次、间隔多久、失败后要不要告警给谁？一个通道成功一个失败，算这条日报"已送达"还算失败？失败后当天要不要人工重跑一遍命令，重跑会不会造成重复发送或 SQLite 重复记录？
> 影响推送层的重试与幂等策略、C7"截止时间前送达全员"的判定口径（部分成功怎么算），以及"幂等"这条成功标准的边界。

**回答（杨佳莹）**：

## 七、第 5 轮问答原文（2026-11-07 追加）

核对「今天这份全不全」靠三处对照：CLI 汇总（成员数、条目数、已保存、已推送，以及每个通道的 ok）、--list 查 SQLite 记录数、飞书群和邮箱实际收到的内容；再用 item_count 跟原始数据源逐条对账。这个验收由测试工程师按成功标准做，需求分析师核的是需求口径有没有跑偏。核对不通过时，由当天运行者看推送明细人工决定要不要重跑——Q8 已说明重跑会重复推送一次，所以必须人工确认，本期不自动重跑。运行与核对职责的规范写进第 2 周的 design.md / tasks.md，本周我只在 proposal 里写清「本期单机运行」这条范围边界。
