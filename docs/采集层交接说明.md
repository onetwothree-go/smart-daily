## 二、为什么要有「数据源可替换」这层抽象

指导书第 24 页 FAQ 原文：

> 「飞书应用 / 邮箱授权码申请不下来，或审核未通过——**不必阻塞进度**：先接 GitHub 数据源与
> 模拟数据源（mock 数据源），保证主流程可跑；凭证就绪后再切换真实接口。**这正是 design.md 中
> "数据源可替换"的设计要求——把它写进接口契约**。」

这正是现在的处境：小组 GitHub 仓库还没建、飞书应用卡在租户资质、邮箱授权码还没申请。所以：

- `WorkSource` 协议定义统一接口 —— `collect(since, until, author) -> list[RawRecord]`
- `collect_with_fallback()` 按优先级依次尝试，**任一源失败自动切下一个，主流程不中断**
- 四个采集器产出**三种记录类型**（`CommitEntry` / `MessageEntry` / `TaskEntry`），
  由 `normalize()` 统一压平成 `WorkItem` —— 生成层因此不必为每种数据源写一遍逻辑
- 小组仓库建好之后，只要在编排层把数据源列表换成 `GitHubCollector` 就完成切换 ——
  这就是「可替换」的含义，**上层代码一行都不用改**

### 三条经过实测固化的设计契约

| 契约 | 内容 | 为什么重要 |
|---|---|---|
| **空列表是合法返回值** | 源可用但窗口内无数据 → 返回 `[]`，不是失败 | 降级链遇到空列表应**停止**而非跳过。若采集器把「无数据」报成异常，会误触发降级 |
| **异常必须显式抛出** | 源不可用 → 抛 `SourceUnavailableError` | 反面教材：飞书采集器曾吞掉异常返回 `[]`，导致降级链误判成功、**跳过本地 Git 兜底源**，主流程产出 0 条空日报 |
| **日期按本地日历归属** | `local_date(ts)` 而非 `ts.date()` | 采集层拿到的都是 UTC 时间戳。直接取 `.date()` 在东八区会让日报标题**差一天**（已修复并加断言） |

## 四、写 design.md 时可以直接引用的接口契约

### 4.1 采集层协议

```python
class WorkSource(Protocol):
    name: str

    def collect(
        self,
        *,
        since: datetime | None = None,   # 起始时间（含）
        until: datetime | None = None,   # 截止时间（含）
        author: str | None = None,       # 只采该作者
    ) -> list[RawRecord]:                # RawRecord = CommitEntry | MessageEntry | TaskEntry
        ...
```

**可度量行为约束**（每条都有对应断言）：

| 约束 | 断言 |
|---|---|
| 返回记录按时间倒序 | [1][4] |
| 时间窗口为闭区间 | [1] |
| 无数据时返回空列表，不抛异常 | [8] |
| 不可用时抛 `SourceUnavailableError` | [2][5][10] |
| 降级链遇空列表**停止**，遇异常**继续** | [8][9] |
| 归一化对已是 `WorkItem` 的记录原样放行 | [6] |
| 三种记录类型都能取到事件时间 | [11] |
| 日期按本地日历归属 | [12] |

### 4.2 推送层协议

```python
class Notifier(Protocol):
    name: str

    def send(self, subject: str, body: str, recipients: list[str]) -> bool:
        ...   # 返回 False 表示失败，**不抛异常** —— 推送失败不阻断主流程
```

**分发规则**（重要，容易写错）：

| 日报类型 | 走哪些通道 | 说明 |
|---|---|---|
| **个人日报** | 仅邮件通道 | 每人只收到自己的那份，收件人由 `MEMBER_EMAILS` 映射决定 |
| **团队日报** | 群渠道（飞书 Webhook） | 邮件通道不参与团队日报分发 |

> 回归用例：旧实现给所有通道都传空收件人 `[]`，导致 `EmailNotifier`
> 永远走「无收件人，跳过」分支返回 False —— **邮件推送从未真正工作过**。
> 现已按上表拆分，并补 `scripts/check_email.py` 独立验证。

## 六、第 1 周可以直接拿去用的三个抓手

### 6.1 竞品调研的对照组

「开源日报机器人」这类方案，采集端几乎都是**单一数据源硬编码** ——
它们的痛点正好是本项目「数据源可替换」要解决的。调研时可以直接对比：

| 维度 | 典型开源日报机器人 | 本项目 |
|---|---|---|
| 数据源数量 | 1（通常只有 GitHub） | 4（GitHub / 飞书 / 本地 Git / mock），可任意替换 |
| 凭证未就绪 | 直接报错中断 | 自动降级，主流程不中断 |
| 新增数据源 | 改核心逻辑 | 实现一个协议即可，**上层零改动** |

### 6.2 「隐含需求」的现成素材

以下都是本项目**实际遇到并解决**的问题，可以直接写进 proposal.md 的隐含需求清单：

1. **空数据 ≠ 数据源故障** —— 降级链必须区分「源坏了」和「源没事但今天没活儿」
2. **凭证未就绪不能阻塞演示** —— 需要一个永不失败的兜底数据源（mock）
3. **日期归属要考虑时区** —— 用 UTC 日期会让日报标题差一天
4. **推送失败不能阻断日报生成** —— 推送是最后一环，失败了日报也得先存下来
5. **个人日报与团队日报分发对象不同** —— 前者按人发邮件，后者发群，不能混用通道
6. **同一平台可能有两条独立通道** —— 飞书的「推」和「读」资质要求完全不同
7. **协议声明的字段必须真实现** —— `Notifier.name` 声明了但实现漏了，是契约与实现脱节

### 6.3 边界场景（写成功标准时用）

| 场景 | 期望行为 | 有无断言 |
|---|---|---|
| 仓库地址未配置 | 判定源不可用，**不误打 API** | ✅ [3] |
| 仓库为空无提交 | 明确提示「仓库为空或尚无提交记录」 | ✅ [2] |
| 凭证未就绪 | 跳过该源，继续下一个 | ✅ [7] |
| 首选源失败 | 自动降级，主流程产出非空结果 | ✅ [4][8][9] |
| 全部源失败 | 抛明确异常，不静默产出空日报 | ✅ [5] |
| 无凭证环境 | mock 源独立跑通完整链路 | ✅ [11] |
