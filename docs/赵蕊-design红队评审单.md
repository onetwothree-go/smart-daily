# design.md 红队评审单

> 评审对象：`specs/design.md`（0.4，2026-11-09）
> 评审方式：**生成—评审对抗**——AI 以红队身份逐条挑错，架构（赵蕊）逐条判定「接受 / 部分接受 / 不成立」并给出处置
> 评审结论：**有条件通过**——架构整体成立，但存在 **2 项 P0、8 项 P1**，其中两项属于「文档与代码相反」「证据链断开」，须整改后方可作为 tasks.md 的输入
> 整改版本：`specs/design.md` **0.5**

---

## 一、评审方法

### 1.1 角色与规则

| 角色 | 由谁担任 | 职责 | 约束 |
| --- | --- | --- | --- |
| 红队 | AI | 只挑错，不提改进方案；每条必须给「位置 + 指控 + 证据」 | 不得评价文风、不得说"写得不错"；宁可误报也不漏报 |
| 架构 | 赵蕊 | 逐条判定，接受就改，不接受要给理由 | 不得用"后面会做"搪塞，必须落到本版或 tasks.md |

### 1.2 实际使用的结构化提示（可复现）

给 AI 的第一轮（挑错）：

```text
你是本项目的红队评审员。评审对象是 specs/design.md（智能日报生成器架构设计）。
任务：逐条找错，不给改进建议，不做文风评论。

必须核对的三类事实：
1) 文档内部一致性：章节之间、表格与正文之间是否自相矛盾；
2) 文档与代码一致性：文档声称的行为，去 src/、scripts/、.github/ 里核对，给出文件与行号；
3) 文档与可验证性：凡是出现「断言」「已实测」「可测」的地方，追查证据是否真的存在于仓库。

输出格式（每条一个表格行）：
编号 | 等级(P0阻断/P1重要/P2次要/P3建议) | 位置(章节+行号) | 一句话指控 | 证据(文件:行 或 引用原文)

硬性要求：
- 每条必须能被人独立复核，禁止"可能存在""建议考虑"这类模糊指控；
- 涉及外部平台规则的（如 GitHub 事件字段上限），必须注明出处，无法核实的标"待实测"，不得当作结论；
- 只列问题，不要列"做得好"的部分。
```

第二轮（反向质询，防红队自己误报）：

```text
现在换角色：你是被评审的架构师。对上一条清单里的每一条，判断
「成立 / 部分成立 / 不成立」，并说明依据（引用代码或文档原文）。
凡你认为"不成立"的，必须指出红队看漏了什么事实。
```

第三轮（收敛成处置）：

```text
把成立的条目按「本版可修（改文档）」/「本版不可修（改代码或补测试）」/「不修（记录理由）」三分类。
本版可修的，给出精确到行号的修改方案；不可修的，写成 tasks.md 能直接接的待办（含验收标准）。
```

### 1.3 为什么必须"三轮"而不是"一轮"

一轮只会得到一堆并列的问题，等级不分、真假混杂。三轮的价值在于：**第二轮专门用来杀红队的误报**（本次 18 条里降级 1 条、判不成立 0 条、部分成立 2 条），第三轮才产生可执行的处置。评审单如果只有问题清单没有判定，等于把判断责任又推回给读者。

## 四、逐条明细

### RT-01｜P0｜架构在默认分支上不可见

- **指控**：文档反复声明"落地在 `src/smart_daily/`"，但评审者打开仓库首页（默认分支 `main`）看不到设计文档本身，也看不到实时提醒的 workflow 与脚本。
- **证据**：
  - `git ls-tree -r origin/main | grep -E "^(\.github|scripts|tests)/"` → **空**
  - `git ls-tree origin/main | grep specs/` → 只有 `specs/README.md`、`specs/proposal.md`，**没有 design.md**
  - `GET /repos/...` → `default_branch = main`；`git rev-list --left-right --count origin/main...origin/dev` → `6 38`（双向分叉：main 独有 6 个提交，dev 独有 38 个）
- **回应**：**成立，且是本轮最严重的问题**。属流程问题不是文档问题：`BRANCHING.md` 规定 dev 稳定后由维护者合并到 main，而设计文档与实时提醒都还停在 dev。
- **处置**：**不在 0.5 修**（改文档无法解决）。列为 `T-03`：本轮收尾时执行一次 `dev → main` 的发布合并（PR，保留历史），并核对合并后 main 上同时存在 `specs/design.md`、`scripts/notify_push.py`、`.github/workflows/notify.yml`。

### RT-02｜P0｜C7 的"成功"定义与实现相反

- **指控**：1.4 表「送达」行写"4 封个人邮件 + 1 条群消息，**全部 ok 才算成功**（C7）"；实现是**任意一个成功即算推送成功**，与 C7 相反；且 CLI 无论如何都退出 0，外部无法判定送达是否完整。
- **证据**：
  - `src/smart_daily/orchestrator.py:215` → `pushed = any(r["ok"] for r in push_detail)`
  - `src/smart_daily/cli.py` → `main()` 各分支均 `return 0`，无失败退出码
  - 设计原文：`design.md` 1.4「送达」行、附录 A · C7
- **回应**：**成立，无争议**。这是"设计写了但没人按它写代码"的典型；更糟的是它**测不出来**——现有 34 项断言全在采集层，推送层没有一条断言约束"全部成功"。
- **处置**：**不可在文档层修**。0.5 在 1.4 该行加现状注记（标明实现与契约不符、待修），代码修复列 `T-01`：`pushed = all(...)`、`push_detail` 为空时视为未推送、CLI 在 `pushed=False` 时退出非 0；验收标准为"4 人场景下关掉 1 个邮箱凭证 → 退出码非 0 且明细标出失败项"。

### RT-03｜P1｜"34 项断言"的证据不存在于仓库

- **指控**：文档把"可验证性"整体押在 `scripts/verify_collectors.py` 的 34 项断言上，但该脚本不在仓库，任何人无法复核——所有"断言 [n]"都是不可追溯的编号。
- **证据**：
  - `design.md:199`「34 项断言（`scripts/verify_collectors.py`）可作证据」
  - `ls scripts/` → 只有 `notify_push.py`
  - `find /d -maxdepth 4 -name verify_collectors.py` → 无结果；仓库无 `tests/` 目录
  - 但 1.3、3.1 共 8 处引用断言编号（[1][2][3][4][5][8][9][10][12]）
- **回应**：**成立**。断言确实在采集层开发期跑过（1.3 记的两条真实 bug 就是它们抓到的），但脚本从未随骨架入库——"跑过"与"可复核"是两回事，评审现场要求复跑就会露馅。
- **处置**：0.5 把"可作证据"改为**如实说明**（脚本未入库、编号为开发期所用、待补），修复列 `T-02`：把断言脚本补进 `scripts/`，CI 加一步跑它。

### RT-04｜P1｜签名算法描述缺关键参数

- **指控**：3.3 把飞书签名写成 `base64(hmac_sha256(f"{timestamp}\n{secret}"))`，只写了待签名串，**没写 HMAC 的 key 和 msg**。飞书的实际算法是"以 `string_to_sign` 为 key、空消息为 msg"，照文档字面实现会得到完全不同的签名，且只在 19021 报错时才发现。
- **证据**：
  - 设计原文：`design.md` 3.3「签名算法（`gen_sign(timestamp, secret)`）」
  - 实现：`src/smart_daily/push/notifiers.py` → `hmac.new(string_to_sign.encode(), digestmod=hashlib.sha256).digest()`（key=待签名串，msg 省略即空）
- **回应**：**成立**。讽刺的是文档自己在 3.3 约束 2 里写"同一算法两处实现必然漂移"，而这段描述本身就是一处会漂移的"第二实现"。
- **处置**：**已修（0.5）**——补全为 `sign = base64(hmac_sha256(key=f"{ts}\n{secret}", msg=""))`，并注明"唯一权威实现是 `gen_sign()`，本文只作说明"。

### RT-05｜P1｜ADR-104 的结论还停在"未实测"，与 3.5 打架

- **指控**：ADR-104「后果」写"Actions runner 境外访问飞书开放平台的连通性**未实测**（技术栈清单证据缺口 5）"；而 3.5 已挂上 run `42587824934` 的实测证据（HTTP 200 / code=0）。同一份文档，一处说没测，一处说测了通过。
- **证据**：`design.md` ADR-104 后果行 vs 3.5「实测证据」段；Actions run `42587824934` success
- **回应**：**部分成立**。实测走的是**自定义机器人 Webhook 域名**，不是**开放平台 API 域名**（`open.feishu.cn`）；两者网络路径不同，严格说"Webhook 可达"不能推出"开放平台 API 可达"。但 ADR-104 写的是"飞书开放平台"，用词确实与实测对象不符，属文档缺陷。
- **处置**：**已修（0.5）**——把"未实测"改为"Webhook 域名已实测可达（run 42587824934）；开放平台 API 域名（采集侧）仍未实测"，并把该缺口保留在 §6。

### RT-06｜P1｜§6 未决 1 的遗留项未随实测关闭

- **指控**：§6 未决 1 标"已决：GitHub Actions"，遗留"runner 到飞书连通性实测"。既然 3.5 已有实测，这条遗留应改写为"Webhook 已实测 / 开放平台 API 待测"，否则 tasks.md 会把它当开放问题重复排期。
- **回应**：**成立**，与 RT-05 同源。
- **处置**：**已修（0.5）**。

### RT-07｜P1｜日报通道的触发点写成了"或"，等于没定

- **指控**：1.4 触发行写"每日 22:00 本机手动（Q18，自动定时留 v1.1）**或** Actions schedule"。两个互斥方案用"或"并列，读者无法判断本期到底怎么触发；而 §6 又把 ADR-104 引作"定时触发落点已决：GitHub Actions"，与"本机手动"直接冲突。仓库里也只有 `notify.yml`（只监听 push），**没有每日定时的工作流**。
- **证据**：`.github/workflows/` 只有 `notify.yml`（`on: push: branches: [main, dev]`）；`notify.yml` 里没有任何 `schedule`
- **回应**：**成立**。根因是把 ADR-104 的适用范围写宽了：ADR-104 决策的是**实时提醒通道**的触发（push），不是日报汇总通道的定时。日报本期就是本机手动跑，Actions 定时属 v1.1。
- **处置**：**已修（0.5）**——1.4 触发行改为"本期：每日 22:00 本机手动运行（Q18）；Actions 定时为 v1.1，仓库当前无每日工作流"；ADR-104 标题下加适用范围限定语；§6 未决 1 相应收敛。

### RT-08｜P1｜mock 到底在不在降级链，两处相反

- **指控**：1.2 表写 mock"**不参与降级链自动挂载**（仅 `--mock` 显式指定）"；3.1 注写"降级顺序 GitHub → 飞书 → local-git → **mock** 由编排层注入"。实现者按前者写就永远不会在链里见到 mock，按后者写就会在真跑时混进演示数据。
- **回应**：**成立**。1.2 是对的（mock 是演示源，混进真实链路会让"今天 0 条提交"变成"今天 4 条演示提交"，直接破坏 G1 口径）。
- **处置**：**已修（0.5）**——3.1 注改为"默认链 GitHub → 飞书 → local-git；mock 不入默认链，仅 `--mock` 时作为唯一源注入"。

### RT-09｜P1｜引用了一个不存在的 ADR

- **指控**：3.1 注"降级顺序……由编排层注入 `sources` 列表决定（见 **ADR-003**）"。本文档只有 ADR-101～104，且文首写明"编号自 101 起，避开教材编号"——引用 ADR-003 既是悬空引用，也违反自己的约定。
- **回应**：**成立**，纯笔误。
- **处置**：**已修（0.5）**——改为指向 `cli.py` / `orchestrator.py` 的 sources 构造处。

### RT-10｜P2｜"不截断"与"只取首行"不是一回事

- **指控**：3.5 契约 3 要求"`commits[]` 全部列出、原文不截断不摘要；长 message 按 Q4 口径截前 60 字"。实现 `short_title()` 取 message **首行**，多行 body 直接丢弃。首行提取本身就是一种截断，契约用"不截断"描述它与实现不符。
- **证据**：`scripts/notify_push.py:91` → `title = message.strip().splitlines()[0]...`；`:94` 超 60 字加省略号
- **回应**：**部分成立**。"不摘要、不改写"这层是对的（确实原样呈现），"不截断"这层不准（只发首行）。
- **处置**：**已修（0.5）**——契约 3 改为"标题取 message 首行原样呈现、不改写不摘要；超 60 字截断加省略号；完整说明靠 commit 链接回溯"。

### RT-11｜P2｜大 push 的边界行为没定义，20 条上限的说法还带条件

- **指控**：契约 3 承诺"commits 全部列出"，但没定义三种边界：一次 push 超过 N 条、force push（`commits` 可能为空）、删除分支（`ref` 存在但无提交）。另外"GitHub push 载荷最多 20 条提交"这条常见说法，官方文档的措辞带条件——"该上限仅适用于 timeline events，**不适用于 webhook 投递**"，而 Actions 载荷实际按哪种处理**未实测**。文档不能既宣称"全部列出"又不定义超出时怎么办。
- **回应**：**部分成立**。代码对空 `commits` 有兜底（"本次 push 未包含提交记录，可能是分支删除或强制推送"），但契约没写；20 条上限确实不能直接引用，需实测。
- **处置**：0.5 补一条边界约定（空/超长/force push 的处理与可见性），`T-06` 安排实测：构造一次 21 个提交的 push，核对实际列出的条数与 `size` 字段是否一致。

### RT-12｜P2｜ER 图把内存实体画成了表关系

- **指控**：2.1 把 `DailyReport 1 ──── * WorkItem` 画成实体关系，但 2.3 明确说 `record_id` 只存在于内存、`work_items` 表"本期默认不建"。图形会让人以为两者有外键、进而去建表。
- **回应**：**成立**。

### RT-19｜P1｜`code=0` 证明不了签名校验是开着的

- **指控**：3.5 的实测证据把 `code=0` 列为"契约 5（签名）闭合"。这是**肯定后件**：飞书自定义机器人的签名校验是可选项，**没开校验时发什么签名都返回 0**。这条实测最多证明"请求发出去了、被接受了"，不能证明"签名算法正确"。
- **证据**：
  - 3.5 原文："据此本轮闭合的契约：… **5**（`gen_sign` 复用，未被 19021 拦截）"——"未被拦截"本身就是零信息：没开校验也不会被拦截
  - 飞书错误码语义：19021 = 签名校验失败（只有"开了校验且签名错"才可能触发）
  - 仓库内没有任何负向用例（故意错签名 → 期望 19021）
- **回应**：**成立**。这是本次评审对我自己上一版结论的推翻：0.4 里那句"契约 5 闭合"说得太满。可接受的表述是"签名路径已跑通、未触发 19021"，而"算法正确"仍需负向用例。
- **处置**：**0.5 改口径**（把"闭合"降为"正向通过"），并把负向用例列 **T-07**：临时用错误 secret 跑一次，期望 `code=19021` 且 workflow 红灯——**能被红灯拦住，才说明校验真开着**。
