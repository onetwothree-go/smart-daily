## 正文（约 230 字）

**触发描述**写在 `SKILL.md` 的 frontmatter：`Use when implementing any feature or bugfix, before writing implementation code`。一句话只给条件不给步骤，「动实现代码之前」是唯一路由点；正文 When to Use 把新功能、修 bug、重构、行为改动四项全列为 Always，只有一次性原型、生成代码、配置文件三类需问人才能豁免。描述即开关。

**工作步骤**由 Iron Law 钉死顺序：`NO PRODUCTION CODE WITHOUT A FAILING TEST FIRST`。循环为 RED 写一条最小失败测试 → Verify RED 必须**亲眼看见**因功能缺失而失败（不是拼错或报错）→ GREEN 只写刚好让它通过的代码 → Verify GREEN 跑项目全量测试而非单个文件 → REFACTOR 保持绿 → 下一轮。每步都是「一个动作 + 一条可观测结果」，并配 Good/Bad 代码对照。

**配套文件**本包**没有** `references/` 与 `scripts/` 子目录：长尾规则收在同级 `writing-good-tests.md`，按需读取（测试名要能说出改哪段生产代码会让它失败、断言真实行为而非 mock）；易错动作不靠可执行脚本，而靠 `Common Rationalizations` 借口表、`Red Flags` 停止清单与 `Verification Checklist` 三张文本清单固化。对比于悦拆的 `brainstorming`（`scripts/` 五个文件把起本地页面固化为命令），这里没有可固化的路径操作、只有判断，所以全部写成文本而非脚本。

## 一句话结论

它防的不是「忘了写测试」，而是「没亲眼看见测试失败就以为测过了」——先用铁律把顺序变成不可协商，再用借口表逐条堵死绕过路径；这也解释了为什么本技能包不需要 `scripts/`：要固化的是判断，不是命令。
