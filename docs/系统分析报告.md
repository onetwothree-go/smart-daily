## 第1章 分析概述与技术目标

### 1.1 项目背景与问题定义

本项目由 4 人课程小组承担，交付物是一个命令行形态的「智能日报生成器」。现状痛点在四周内被反复确认，可归为四条：

第一，**收集成本高且易漏**。每天下班前需要人工翻看 GitHub 提交记录、飞书任务卡片、飞书群聊消息，把三处散落的事实手工拼成一段日报；成员一旦当天提交较多，翻页与摘抄本身就是半小时以上的机械劳动，且漏掉一条不会有任何提示。

第二，**来源分散、口径不一**。同一个人在不同平台上有不同标识：GitHub 是登录名，飞书是显示名，git 本地配置又是自由文本（实测同一人出现过 `fh` / `20233046方赫` 两种写法）。人工汇总时靠记忆认人，一旦认错，整份日报的归属就错了，而这类错误事后无法自证。

第三，**格式不统一**。每人写法不同：有人按时间列，有人按模块写，有人干脆写成一段散文。团队汇总时无法比较，也难以统计「今天做了多少条」。

第四，**发布动作重复**。日报写完还要一封封发邮件、再往群里贴一条，漏发一个人往往到第二天才被发现。

目标状态因此被定义为：把「代码提交 / 飞书任务 / 群消息」三类事实**自动**汇成每人一份的个人日报与一份团队汇总，**1:1 原样呈现、零手工编排**，在每天 22:00 由一人触发一次，当天 23:59 前送达本人邮箱与团队群；当某个数据源不可用时自动降级而不是中断。系统**不做实时监控**，只做「每日一次汇总 + 每次 push 一次群提醒」两件事——后者是提醒，不是日报条目（proposal N5 / Q16 / Q17）。

## 第2章 系统架构与模块划分

### 2.1 总体架构

系统按四层划分：**主编排入口**（`orchestrator.py` / `cli.py`）、**采集层**（`collectors/`）、**生成层**（`push/generator.py`）、**推送层**（`push/`）；另有一条与主线**物理隔离**的实时提醒支路（workflow → `scripts/notify_push.py` → 飞书 Webhook）。

依赖方向自上而下单向：主编排依赖下三层，**下三层之间互不感知**。这条规则不是形式约束，而是三条实测教训的产物：生成层若知道数据来自哪里，模板就会长出分支；推送层若知道日报怎么生成，就会在推送时做二次加工；采集层若反向依赖推送层，则任何推送改动都会波及采集。

读架构图有三处容易误读的边界，必须先交代：

1. **生成层不联网**。`build_personal_report` / `build_team_report` 是纯函数，相同输入必得相同输出，没有网络、没有文件、没有全局状态。因此「格式统一」这条可以写成断言，而不是靠人检查。
2. **采集层不写库**。写库只发生在编排层的 `save_report()`。采集器只知道「取数据、必要时抛异常」，不知道 SQLite 的存在。
3. **实时支路不落库**。它的输入是 Actions 注入的事件文件，输出是一条群消息，全程不碰 `daily_report.db`，也不触发日报生成。
### 2.2 分层职责与依赖规则

四层各自的职责与「不做什么」列在同一张表里，边界才不会被含糊掉（见表 2-1）。

**表 2-1　分层职责与依赖规则**

| **层** | **职责** | **允许依赖** | **禁止依赖** |
| --- | --- | --- | --- |
| 主编排入口 | 串接采集 → 分组 → 生成 → 落库 → 推送；管理 SQLite 读写；把推送汇总结果映射为进程退出码 | 采集 / 生成 / 推送三层 | 不实现任何采集、渲染、推送细节 |
| 采集层 | 定义 `WorkSource` 协议与降级入口 `collect_with_fallback`；四类数据源实现；归一化 | 标准库、httpx、`identity.py`（映射解析） | 不依赖生成层与推送层；采集器不写库、不重试 |
| 生成层 | `WorkItem 列表 → 个人日报 / 团队日报文本`，纯函数零副作用 | 仅 `models.py` 的数据结构 | 不碰网络、不读文件、不做 AI 摘要 |
| 推送层 | `Notifier` 协议 + 邮件 / 飞书 Webhook 两个实现；`gen_sign()` 签名唯一实现；成员到邮箱映射 | 标准库 smtplib、httpx、`identity.py` | 不抛采集层异常、不参与降级链、不提供多通道聚合 |
| 实时支路 | 读事件文件拼提醒文本、签名、发 1 条群消息 | 推送层 `gen_sign()` 复用 | 不调采集层、不写 SQLite、不计入日报条目 |

一条补充规则在 design 0.5 中被写死：**一个** **`Notifier`** **实例 = 一个通道**。跨通道的聚合与判定属于编排层（3.4 的 `push_status`），推送层不提供聚合实现；已有的 `MultiNotifier` 自 0.5 起声明弃用（见 3.5 与 5.4）。

### 2.4 关键运行路径

系统有两条运行路径，一条是每天 22:00 的日报主线，一条是每次 push 触发的提醒支路。本节分别给出两者的执行次序与数据落点，并在末尾说明为何不能合并。

#### 2.4.1 日报主线

`cli.py` 解析参数 → `DailyReportOrchestrator.run()` → `collect_with_fallback()` 依次尝试数据源（异常切下一个、空列表停止）→ 确定归属日 → `group_by_member()` → 生成团队日报 → 逐人生成个人日报并 `save_report()` 幂等 upsert → 推送（4 封个人邮件 + 1 条群消息）→ 汇总 `push_status` 与 `push_detail` → CLI 映射退出码。

这条路径由**本机手动触发**（`uv run --env-file .env`），落库，并计入 C7 的 5 条送达判定。

![图 2-1](<uml/日报生成主流程（泳道图）.png>)

*图 2-1　日报生成主流程（泳道图）（来源：赵蕊绘制；图源 docs/uml/日报生成主流程（泳道图）.png）*

#### 2.4.2 实时提醒支路

push 事件 → `notify.yml`（`branches: [main, dev]` 过滤）→ `scripts/notify_push.py` 读 `GITHUB_EVENT_PATH` → 取 `github.actor` 查显示名 → 拼「日报」关键词文本（commits 全列）→ `gen_sign()` 签名 → Webhook → `code == 0` 则 `exit 0`，否则打印错误码并 `exit 1` 让 workflow 亮红灯。

这条路径由**平台事件触发**，不落库，不计入 C7。

**两条路径为什么不能合并**（这是本架构最容易被"顺手优化"破坏的地方），逐维度对照见表 2-3：

**表 2-3　两条运行路径对照**

| **维度** | **日报主线** | **实时支路** | **合并的后果** |
| --- | --- | --- | --- |
| 触发源 | 本机手动，每日一次 | GitHub push 事件，频次不可控 | 要么把日报刷成流水账，要么提醒永远等不到 22:00 |
| 数据源 | 三源降级链，按时间窗聚合 | 事件文件内的 `commits[]`，不经 API | 提醒会消耗 API 配额，并引入降级链的失败语义 |
| 失败语义 | 降级、留痕、不中断，退出码 3 提示重跑 | 不重试、不告警，只亮红灯 | 提醒失败会污染日报的 `push_status`，C7 判定失真 |
| 数据落点 | 写 SQLite 快照 | 不写库 | 提醒会破坏「条目 1:1」的计数口径 |
| 计数口径 | 计入 G1 / C7 | 一次都不计入 | G1 与 C7 同时失去可测性 |

## 第3章 对象与类建模

### 3.1 领域对象识别

先识别对象再谈类：五个对象里四个是采集层的记录类型，一个是归一化视图（见表 3-1）。

**表 3-1　领域对象清单**

| **对象** | **类型** | **职责** | **实现位置** |
| --- | --- | --- | --- |
| `RawRecord`（三型联合） | frozen dataclass | 采集器返回值，采集完成即不可变 | `collectors/models.py` |
| `CommitEntry` | frozen dataclass | 一条提交：sha、作者、message、增删行数 | `collectors/models.py` |
| `MessageEntry` | frozen dataclass | 一条群消息：message_id、发送者、文本、提及 | `collectors/models.py` |
| `TaskEntry` | frozen dataclass | 一条任务：task_id、summary、created_at、completed | `collectors/models.py` |
| `WorkItem` | dataclass | 归一化统一视图，生成层唯一输入 | `collectors/models.py` |
| `WorkSource` | Protocol | 数据源契约：`name` + `collect()` | `collectors/base.py` |
| `Notifier` | Protocol | 通道契约：`name` + `send()` | `push/notifiers.py` |
| `DailyReport` | 数据实体 | 日报快照：(report_date, member) 唯一 | `orchestrator.py::_ensure_db` |
| `push_detail` 元素 | dict 结构 | 单条推送回执：channel/scope/ok/at/error | design 3.4.1【0.5 新增】 |

这些对象之所以是「类」，判断依据是**它们要么有独立生命周期、要么有独立契约**：三型 RawRecord 来自三个不同平台，字段集不同，不能合并成一个「万能记录」；`WorkItem` 是归一化的产物，它必须让生成层对来源一无所知；`WorkSource` 与 `Notifier` 是协议而非实现，因为它们的作用是**约束多个实现**（四类源、两类通道），而不是复用代码。

反过来，有些名词只作字段不作类：`repo`、`chat_id`、`additions`、`mentions` 都挂在 `metrics` 里——它们没有独立行为，单独建类只会增加转换成本。`push_detail` 同理，本期是 dict 结构（3.4.1），只有当它需要落库（v1.1 的 `push_receipts`）时才升格为实体。

### 3.3 关键类职责与协作

关键类的职责用一句话写死——写不出一句话，说明职责还没想清（见表 3-2）。

**表 3-2　关键类职责、协作与边界**

| **类 / 模块** | **职责（一句话）** | **协作对象** | **不负责什么** |
| --- | --- | --- | --- |
| `DailyReportOrchestrator` | 串起采集、生成、落库、推送并汇总结果 | 四层全部 | 不实现采集、渲染、推送细节；不决定进程生死 |
| `cli.py` | 解析参数、调用编排、把 `push_status` 映射为退出码 | 编排层 | 不含业务逻辑；不直接读写库 |

| `GitHubCollector` | 拉取时间窗内提交并细分错误语义 | httpx、`WorkSource` | 不写库、不做身份合并 |

### 4.3 唯一约束与幂等策略

写入采用 `INSERT ... ON CONFLICT(report_date, member) DO UPDATE SET content, item_count, source_name, created_at = excluded.*`，即**同日同人重复执行时覆盖而非追加**。

三点必须说清：

1. **覆盖保留最后一次结果**。22:00 触发后若发现某源漏采，补跑一次即可用更全的结果覆盖前一次，不需要删记录。
2. **重复执行不产生重复记录**。幂等性由数据库约束保证，不依赖调用方「先查再写」——后者在并发下存在竞态，且把正确性交给每个调用点。
3. **为什么选覆盖而不选追加**。追加会带来「同一天两份日报哪份算数」的歧义，进而破坏 C1 的 1:1 计数；而本系统的日报是**快照**语义（某天某人的日报只有一份），覆盖与语义一致。
### 4.4 内存数据结构

WorkItem 是生成层的唯一输入，字段定义即生成层可依赖的边界（见表 4-2）。

**表 4-2　WorkItem 字段定义**

| **字段** | **类型** | **可空** | **含义** | **生产者 → 消费者** |
| --- | --- | --- | --- | --- |
| `member` | str | 否 | 归属成员显示名 | `normalize()` → 生成层 |
| `timestamp` | datetime | 否 | 事件时间（统一自三型时间字段） | `record_timestamp()` → 生成层 |
| `title` | str | 否 | 做了什么（message / 消息前 60 字 / 任务 summary） | `normalize()` → 生成层 |
| `source` | str | 否 | `commit` / `message` / `task` | `normalize()` → 生成层 |
| `detail` | str | 是 | 补充说明（变更统计 / 全文 / 任务描述） | `normalize()` → 生成层 |
| `url` | str | 是 | 关联链接 | 采集器 → 生成层 |

### 4.5 数据生命周期

日报快照写入后**不自动清理**。理由：本系统按 4 人 × 每日 1 份计，一年约 1460 行、每行数百字，体积在数 MB 量级，SQLite 完全无压力；而「历史可查」是隐含需求 I7，清理由人工按需执行更安全。实时提醒**不落库**：它的价值在「即时看到」，一旦落库就要处理去重、保留期与个人数据边界三件事，本期不值得。

任务归属的时间口径在本版被写死：**归属日 =** **`local_date(created_at)`**，一条任务只在其创建日计入一次。跨天任务（昨晚创建、今早完成）归创建日，完成日不重复计入——否则同一任务会在两份日报里各出现一次，破坏 C1 的 1:1。

### 4.6 数据安全与个人信息

成员真实邮箱属于个人信息，与 token 同级管理：**只存** **`.env`** **与 Actions Secrets，绝不进仓库**；仓库内示例一律用 `example.com` 占位。`MEMBER_DISPLAY_NAMES`（登录名到显示名）不含敏感信息，反而必须入库，以保证 Actions 与全员环境读到同一份映射。日志只打数据源名与错误摘要，不打 token、不打完整 Webhook URL。本报告正文亦不含任何真实邮箱、token 或 Webhook 地址。

### 5.2 采集层接口

WorkSource 协议只有六条约定，但每条都有对应断言，改一条就要改断言（见表 5-2）。

**表 5-2　WorkSource 协议**

| **项** | **约定** |
| --- | --- |
| 属性 | `name: str`，用于日志与降级提示 |
| 方法 | `collect(*, since=None, until=None, author=None) -> list[RawRecord]` |
| 顺序 | 返回记录按时间**倒序** |
| 窗口 | `since` / `until` 为**闭区间** |
| 空结果 | 源可用但无数据 → 返回 `[]`，**不抛异常** |
| 失败 | 凭证缺失 / 网络失败 / 仓库为空 → 抛 `SourceUnavailableError` |

`collect_with_fallback()` 内部已完成 `normalize()`，**编排层不可二次归一化**。这条约束的理由很实际：二次归一化会把已经是 `WorkItem` 的对象再走一遍转换，轻则重复映射成员名，重则在 `metrics` 上叠加旧值——而生成层无从发现。

### 5.3 生成层接口

四个纯函数，签名与行为如下：

- `group_by_member(items) -> dict[str, list[WorkItem]]`：按成员分组，组内按时间倒序；成员名即 `WorkItem.member`，不再做归属判断。
- `format_item(item) -> str`：单条渲染为 `- [HH:MM] （标签）标题 —— 详情`；**标题不改写、不摘要**（N1），详情只补事实性统计（文件数、增删行数）。
- `build_personal_report(member, items, day=None) -> str`：个人日报；`items` 为空时仍输出「今日无工作记录」的空模板，**不返回空串**——空串会让「确实没干活」与「采不到数据」无法区分（C8）。
- `build_team_report(groups, day=None) -> str`：团队日报，统计头 + 贡献降序；零记录成员也列出，不压缩不截断（C4）。
`day=None` 时由编排层用 `local_date()` 决定归属日，生成层不自己取系统时间——这是纯函数可测的前提。

### 5.4 推送层接口

- `Notifier.send(subject, body, recipients) -> bool`：`True` 成功、`False` 失败；**永不抛异常**。失败的原因（异常类名、HTTP 状态、飞书错误码）由实现内部捕获并交给编排层记入 `push_detail.error`。
- `Notifier.from_env()`：凭证缺失抛 **`ValueError`**（含义是「该通道没配好」），**不抛**`SourceUnavailableError`——推送层不依赖采集层异常；调用方捕获后不挂载该通道、静默跳过。
- `gen_sign(timestamp, secret) -> str`：`base64(hmac_sha256(f"{timestamp}\n{secret}"))`，时间戳距当前不得超过 1 小时；**全项目唯一实现**，Actions 脚本必须复用，不得另写一遍。
- 回执契约：每次分发（每人 1 封邮件、团队 1 条群消息）**恰好产生 1 条**`push_detail`；`ok=False` 也必须有记录。
`MultiNotifier` 自 design 0.5 起**声明弃用**：它的布尔返回值无法承载分通道回执，其 `any()` 语义与 `pushed = all(...)` 直接相抵，且聚合职责属于编排层。

### 5.5 编排层接口

`DailyReportOrchestrator.run(since=None, until=None, day=None, notify=True) -> dict`，返回 `{date, source, members, items, saved_reports, pushed, push_status, push_detail, team_report}`。

内部次序固定为：采集 → 定归属日 → 分组 → 生成团队日报 → 逐人生成并落库 → 推送 → 汇总。**先落库后推送**的理由是：日报文本一旦生成就是可交付成果，落库失败应是硬错误（退出码 1），而推送失败只是可观测的软失败（退出码 3）；若先推送后落库，推送成功但落库失败时用户已收到一份没有留档的日报，重跑会重复打扰。

`run()` 只返回 `pushed` / `push_status`，**不调用** **`sys.exit()`**；进程退出码由 CLI 映射，编排层不决定进程生死。

## 第6章 测试方案

### 6.1 测试策略与分级

测试分四级，每级只回答一个问题：

1. **单元（纯函数）**：生成层与归一化是否给出确定的输出。判据是「相同输入必得相同输出」，不依赖网络与时钟。
2. **契约（签名与返回）**：每层对外的函数签名、返回值类型、异常类型是否符合第 5 章。这一级防的是「实现悄悄改了语义」——例如 `send()` 改成抛异常，上层仍按返回 `False` 处理。
3. **集成（多源降级）**：注入失效凭证、空仓库、网络异常，验证降级链的切换与停止语义，以及 `[]` 与异常的区分。
4. **端到端（真发）**：真实 Actions 触发一次 push，验证 1 条消息、`code=0`、不落库。
**为何不做性能压测**：规模假设是 4 人、每日条目小于 200，单次运行秒级完成，压测没有决策价值；且 C6 已被 proposal 0.4.2 §6.2 降为观察项，不建计时断言。若将来条目量级变化，先补 fixture 与固定计时口径，再谈压测。

C1–C10 逐条挂到用例编号上，挂不上的如实标「不进硬验收」（见表 6-1）。

### 6.3 测试环境与数据

三类数据源按用途分工：**mock** 是固定数据集，含四人样例记录，可反复跑、结果确定，用于单元与回归；**local-git** 读取本机仓库的真实提交，离线可用，用于验证「降级到本地源」这条路径；**真实源**（GitHub / 飞书）只做冒烟，不在 CI 中日常运行。

真实源不进 CI 的理由有三：凭证在 CI 中会形成泄露面；平台频率限制会让随机失败污染结论；真实数据每天变化，无法作为回归基线。所有断言必须能在 mock / local-git 上复现，真实源只用于「今天确实发得出去」这类一次性确认。

### 6.6 失败注入设计

失败要能被看见才算可测，因此注入手法与可观测现象成对写（见表 6-4）。

**表 6-4　失败注入手法与可观测现象**

| **失败类别** | **注入手法** | **期望的可观测现象** |
| --- | --- | --- |
| GitHub 凭证失效 | `.env` 中把 `GITHUB_TOKEN` 改为无效值 | 日志出现降级原因，数据源变为 local-git，退出码 0 |
| 飞书租户资质不足 | 用未过审的 app 凭证 | 错误码转中文提示后降级，不中断 |
| 仓库为空（409） | 指向不存在或空仓库 | 判定不可用，切下一源，不误判为「无数据」 |
| 推送通道未配置 | 移除 SMTP 或 Webhook 环境变量 | 该通道不挂载，`push_detail` 记 `no_channel`，退出码 3 |
| 实时通道签名错 | 故意用错签名密钥 | Actions 日志出现 19021，workflow 亮红灯，群内无消息 |
