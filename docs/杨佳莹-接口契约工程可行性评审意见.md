三条分工单指定必核项，逐条结论：

1. **`collect_with_fallback` 内部已完成 `normalize()`，编排层不可二次归一化** —— **一致**。`collectors/base.py` L100 为 `return normalize(raw), src.name`；`orchestrator.py::collect()` 注释明确「内部已做 normalize，此处不可二次归一化」，实际只做一次转发。无重复归一化风险。
2. **归属键用 `github.actor`，不用 `commits[].author.name`（ADR-104）** —— **实时通道一致，采集链路需调整**。`scripts/notify_push.py` L169 读 `ACTOR`（workflow 注入 `${{ github.actor }}`），不读 `commits[].author.name`；`collectors/github.py` 采集侧用 `author_login`，与 ADR-104「采集器内部字段保持登录名」同源。但 2.2 约定的 `identity.py::lookup_display_name` 尚未建立，两条链路各自解析：`github.py` L44 是大小写敏感的 `key.strip() == login`，`notify_push.py` L74/L80 用 `.lower()`，与 RT-06 要求的 `strip + casefold` 同规不符。
3. **C6 性能为观察项、不作验收断言** —— **一致**。`proposal.md` 0.4.2 §6.2、`design.md` 5.4、`tasks.md` TK-705 三处口径一致，均写「只作观察、不进硬验收」。实现未加计时断言，与设计相符。

## 二、逐条三段式评审（§3.1 采集层）

### C3.1-1　`WorkSource` 协议与 `collect(since, until, author)` 五条行为约束

- **能不能实现**：能。`collectors/base.py` L26-61 用 `@runtime_checkable` 的 `Protocol` 定义了 `name` 与 `collect()`，四个采集器均满足协议形状。
- **缺什么**：缺**证据**。design §3 前言与 TK-701 指向的 `scripts/verify_collectors.py`（34 项断言）在仓库中不存在，实测 `scripts/` 只有 `make_icon.py`、`notify_push.py`、`run_daily.ps1`。倒序、闭区间、空列表不抛异常、源不可用抛 `SourceUnavailableError`、未配仓库地址不误打 API 这五条目前只有代码路径、没有可复跑断言。
- **建议**：TK-701 维持 P0 优先级；断言脚本由采集层组员补提交后，C3.1-1 才具备验收证据。

### C3.1-2　`collect_with_fallback(sources) -> tuple[list[WorkItem], str]`

- **能不能实现**：能。`base.py` L72-102 按列表顺序尝试，遇空列表 `return` 停止（L100）、遇 `SourceUnavailableError` 切下一个（L94-96）、全失败抛聚合异常（L102）。
- **缺什么**：**异常语义比契约宽一点**——L97-99 还捕获了 `except Exception`，把所有异常都当成「源不可用」继续降级；design 只约定 `SourceUnavailableError` 触发降级。程序 bug（如 `TypeError`）会被静默降级掩盖。
- **建议**：由架构师裁定是收窄代码还是放宽契约；若收窄，改动点在 `base.py` L97-99，属 TK-203 范围。

### C3.1-3　四个采集器工厂 `from_env()`

- **能不能实现**：能。`GitHubCollector.from_env()`（`github.py` L81-87，缺 `GITHUB_TOKEN`/仓库地址即抛 `SourceUnavailableError`）、`FeishuCollector`（`feishu.py` L94 自管 `tenant_access_token`，过期前 300 秒刷新）、`LocalGitCollector(repo_path)` 无凭证、`MockCollector()` 内置四人样例。
- **缺什么**：`FeishuCollector` 的 `tenant_access_token` 缓存计数断言、真实窗口数据实测记录缺失（TK-302 ✅ 但 TK-303/304 仍 ☐）；`MockCollector` 不挂默认降级链这一点靠编排层 `sources` 注入保证，无独立断言。
- **建议**：TK-303/304 保留 ☐，真实凭证窗口实测由测试工程师于悦出具记录，不在本意见里代填。

### C3.1-4　归一化工具 `normalize()` / `local_date()` / `record_timestamp()`

- **能不能实现**：能。`models.py` L229/L242/L263 三函数齐备，`local_date()` 用 `ts.astimezone().date()`（东八区边界正确），`normalize()` 对已是 `WorkItem` 的原样放行、未知类型抛 `TypeError`。
- **缺什么**：无代码缺口；缺 34 项断言中的 [1][4][12] 证据，同 C3.1-1。
- **建议**：随 TK-701 一并补。

### C3.1-5　2.2【本期约定】`identity.py::lookup_display_name(login, mapping_raw=None)`

- **能不能实现**：**需调整**。仓库 `src/smart_daily/` 下**没有 `identity.py`**；`github.py::_display_name`（L32-46）与 `notify_push.py::resolve_display_name`（L74-80）各写一套解析循环，且前者大小写敏感、后者用 `.lower()`，均非 `casefold()`。
- **缺什么**：包顶层唯一实现、`strip + casefold` 同规、两条链路共用一份映射解析；RT-06 要求的「两条链路必须同规」目前未落地。
- **建议**：新增 `src/smart_daily/identity.py`，两处改为调用它；理由同 design 2.2（不能放 `members.py`，否则采集层反向依赖推送层，违反 1.1 单向依赖）。此项属开发工程师实现范围，已列入第三节差异清单。

### C3.1-6　3.6 出站接口清单（8 行）

- **能不能实现**：能，逐条对得上：`github.py` `/repos/{owner}/{repo}/commits`、`/repos/{owner}/{repo}/collaborators`（L159）；`feishu.py` `/auth/v3/tenant_access_token/internal`（L104）、`/task/v1/tasks`（L183）、`/im/v1/messages`（L220）、`/contact/v3/users`（L234）、`/im/v1/chats`（L249）；Webhook 在 `notifiers.py`。
- **缺什么**：清单里「主要错误码」一列是文档归纳，`feishu.py` 只把 HTTP 层与 `code != 0` 转中文提示，未逐码映射；GitHub 429 限频未单独处理。
- **建议**：清单保留为「口径对照」即可；若要求逐码可测，需在 TK-301/302 补错误码注入用例，由测试工程师认领。

## 三、逐条三段式评审（§3.2 生成层 / §3.3 推送层）

### C3.3-2　`MultiNotifier` 已弃用（RT-09）

### C3.3-3　两条分发硬规则（RT-04）与回执契约（RT-07）

- **能不能实现**：**需调整**。团队日报走 `orchestrator.py` L276 `{"channel": n.name, "scope": "team", "ok": bool(ok)}` 且 `send(..., [])` 显式空列表，个人日报只经 `EmailNotifier`——这部分一致；但 `_push_personal_reports()` 对 `resolve_recipients()` 返回空的成员直接 `continue` 跳过（L245-248），**不产生任何 `push_detail` 记录**。
- **缺什么**：design 3.4「应送达集合」要求的每人恰好 1 条、无邮箱/无通道时记 `ok=False, error="no_recipient"/"no_channel"`。现状下「4 人里 2 人没配邮箱」会被算成「2 条全 ok → 送达成功」，与 C7 相抵。
- **建议**：这是 TK-707 ②，仍为 P0；`any→all` 已在 `3f2b3ee` 修掉，但分母问题未修，见第五节。

### C3.3-4　飞书两条硬约束（关键词「日报」、`gen_sign` 单点复用）

- **能不能实现**：能。`notifiers.py` L29 是 `gen_sign` 唯一实现；`notify_push.py` L39 直接 `from smart_daily.push.notifiers import gen_sign`，L127 调用，未复制算法；关键词校验在实时通道脚本内，实测 run `42587824934` 返回 `code=0`（未被 19024 拦截）。
- **缺什么**：无代码缺口。
- **建议**：可作为验收依据；签名负向用例（TK-803）实验记录仍 ⏳，由测试侧补。

### C3.3-5　`members.py` 三段匹配与「未知成员跳过」

- **能不能实现**：能。`load_member_emails()`（L25）/ `resolve_recipients()`（L48）齐备，未配置返回 `{}`、未命中返回 `[]`。
- **缺什么**：同上 C3.3-3——「跳过」与「应送达集合必须记账」冲突，需在编排层补失败回执，不是 `members.py` 的问题。
- **建议**：不改 `members.py`，改编排层记账。

## 四、逐条三段式评审（§3.4 主编排 / 3.4.1 明细 / 3.5 实时通道）

### C3.4-1　`run()` 返回字段与 `push_status` 五态

- **能不能实现**：**需调整**。`orchestrator.py` L217-225 返回 8 个字段（`date/source/members/items/saved_reports/pushed/push_detail/team_report`），**没有 `push_status`**；`ok/partial/failed/no_channel/skipped` 五态与 `pushed == (push_status == "ok")` 不变量均未实现。
- **缺什么**：五态枚举、应送达集合计数、`all([])==True` 真空真值防护（现用 `bool(push_detail) and all(...)` 只防住空列表，未防「跳过不记账」）。
- **建议**：TK-707 范围，P0；本意见不擅改 `specs/`，由架构师决定是否调整 0.5.1 的落地版本。

### C3.4-2　CLI 六个参数与退出码 0/1/2/3

- **能不能实现**：**已实现（本次提交，按 design 3.4 四码表）**。`--day` 改用 `type=_day_arg` 由 argparse 校验，非法日期退出码 `2`；`_exit_code(push_status)` 把 `ok/skipped` 映射为 `0`、`partial/failed/no_channel` 映射为 `3`；`orch.run()` 外层 `except (SourceUnavailableError, OSError, sqlite3.Error)` 转 `1`；`--list` 恒返回 `0`。验证：`--no-notify` 退出码 0、`--day 2026-11-99` 退出码 2、五态映射 `[0, 0, 3, 3, 3]`。
- **缺什么**：四码已补齐；TK-707 ②③④ 仍未落地——应送达集合、无邮箱成员跳过不记账、`push_detail` 的 `at`/`error`。因此 `push_status="ok"` 目前只代表「已产生的回执全 ok」，不代表应送达集合的每一条都有回执。
- **建议**：本次提前于 TK-707 落地退出码表，`push_status` 五态作为支撑一并实现；应送达集合与回执 `at`/`error` 仍按 TK-707 推进。

### C3.4-3　3.4.1 `push_detail` 五字段（`channel/scope/ok/at/error`）

- **能不能实现**：**需调整**。实际写入只有 3 个字段（个人 L256、团队 L276 均为 `{"channel", "scope", "ok"}`），**缺 `at` 与 `error`**。
- **缺什么**：`datetime.now().astimezone().isoformat(timespec="seconds")` 记账、失败原因（异常类名 / HTTP 码 / 19024 / `no_recipient` / `no_channel`）；C7 重判口径「5/5 ok 且 `at <= 23:59:59+08:00`」因此无法判定。
- **建议**：`at` 由编排层在 `send()` 返回后统一取，不改 `Notifier` 协议（design 3.4.1 已写死），实现成本低；归 TK-707。

### C3.4-4　`pyproject.toml` 入口点（TK-101 已记录的缺陷）

- **能不能实现**：**需调整**。`[project.scripts] smart-daily = "smart_daily:main"`，而 `cli.py` 才是 `main()` 所在模块，`smart_daily:main` 不存在；design 3.4 的 CLI 契约以 `python -m smart_daily.cli` 为准，两者不一致。
- **缺什么**：入口点应指向 `smart_daily.cli:main`。
- **建议**：TK-101 一字之改，随下次代码提交一并修；当前实际运行方式（`uv run --env-file .env python -m smart_daily.cli`）不受影响。

### C3.5-1　实时提醒通道 7 条契约

- **能不能实现**：能，且契约 1/3/4/5/6 已有实测证据（design 3.5，run `42587824934`：HTTP 200 / `code=0` / 1.48s / 1 条含 2 个 commit）。`.github/workflows/notify.yml` 只有 `on.push.branches: [main, dev]`，无 `schedule`，符合 TK-802 验收；`permissions: contents: read`、两条 Webhook 凭证只从 Secrets 注入。
- **缺什么**：契约 2「映射未命中打告警」与契约 7「失败不重试、不发群告警」的负向注入实验记录（design 3.5 自列「仍待验证」）；TK-803 签名负向、TK-804 大 push 边界均 ⏳。另 `notify_push.py` L74/80 用 `.lower()` 而非 `casefold()`，同 C3.1-5。
- **建议**：负向实验由测试工程师于悦记录；`.lower()` → `identity.py` 收敛随 C3.1-5 一起做。
