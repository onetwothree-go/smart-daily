## 一、评审方法

对 39 条任务的验收标准逐条过三问：

| 问 | 不合格的表现 |
|---|---|
| ① 有没有可观测的判定对象？ | 只说「正常」「合理」「完善」，没说看什么 |
| ② 有没有判定阈值或明确状态？ | 有对象但没数值、没通过/不通过的分界 |
| ③ 换个环境能不能复现？ | 依赖一次性人工动作、真实凭证或尚不存在的基础设施，且未写明退路 |

三条里任一不成立，记为「写不出用例」，需回填。

## 三、必须重写的两条（写不出用例）

### 3.1 TK-404 ③「与个人日报模板骨架逐字一致」

原文：

> ③ 与个人日报**模板骨架逐字一致**（去成员名/条目/计数后比对，C4）

**问题**：实测已证该验收标准不成立（证据 `docs/testing/证据/E-07-C4骨架diff与去重探测-2026-11-10.txt`）：

| 对比项 | 个人日报 | 团队日报 | 结果 |
|---|---|---|---|
| 分组维度 | 按来源（代码提交 / 任务进展 / 群内消息） | 按成员 | 结构不同，去变量后仍不同 |
| 条目行格式 | `- [HH:MM]（类型）标题` | 同左 | ✅ 逐字一致 |
| 汇总行 | 末尾「共 N 条工作记录…」 | 标题下「共 N 位成员、M 条」+ 末尾另一句 | 位置与文案均不同 |

不是实现写错了，是这条标准把「条目行格式一致」写成了「模板骨架逐字一致」。两份日报的信息组织维度本来就不同，逐字比对必然不为空。

**建议改写为**：

> ③ 条目行格式与个人日报逐字一致（`- [HH:MM]（类型）标题`），用剥离函数去成员名/条目正文/计数后，**逐行比对条目行**而非整篇；团队日报的分组维度为成员、个人为来源，不参与骨架逐字比对。

改完后本条可判定，且与 C4 的实测结论对齐。

### 3.2 TK-706「采集遗漏人工对账流程」

原文：

> ① 每次发布前用 CLI 汇总 / `--list` / 群消息三处对照；② 差异逐条记录并注明原因

**问题**：产出物是 `docs/testing/对账记录模板.md`，但验收标准描述的是「人怎么用它」，不是「这个文件长什么样、填成什么样算合格」。「每次发布前」也没有判定点——什么算一次发布，谁认定，什么时候检查，均未定义。按此标准无法写出断言，也无法判断交付物是否达标。

**建议改写为**：

> ① `docs/testing/对账记录模板.md` 含三栏：CLI 汇总条数 / `--list` 条数 / 群消息条数，及一栏「差异原因」；② 模板中至少有 1 次真实对账的填写样例（填本仓库 v1 的实际数字），差异栏写「无差异」也须填；③ 发布动作的触发点写在 BRANCHING.md 或本模板抬头，明确「谁在什么时点填」。

## 五、流程与位置不符实际：TK-903

原文：

> ① `git show v1-sdd` 的 tag message 列出 proposal 0.4.2 / design 0.5.1 / tasks 0.1.3
> ② tag 落在 **main 的发布提交**上

**现状**：`v1-sdd` 已于 2026-11-10 打在 dev 的 `b7656c7` 上，tag message 只写了测试结论与已知缺陷，**未列三份规范的版本号**；且主干侧 `main` 当前 `specs/` 仅有 `README.md` 与 `proposal.md`，缺 `design.md` 与 `tasks.md`，dev 领先 main **137 个提交**，TK-902（dev→main 发布合并）状态仍为 ⏳ P0。

**判定**：本条现阶段**必然判不通过**，但原因不在执行人，在依赖顺序——TK-903 依赖 TK-902，而 TK-902 尚未完成。这不属于「验收标准写错」，属于「标准正确、前置未达成」，故不列入需重写条目，仅提示：**TK-902 完成并合并后，须在 main 的发布提交上重打 `v1-sdd`**，并把 ① 的版本号补进 tag message。
