# Proposal 成功标准（可度量指标）初稿 v0.1

> 起草人：方赫（测试工程师）
> 状态：初稿，待组内评审
> 日期：2026-11-09

## 一、目的

proposal 立项时即约定"怎样才算做成了"：所有成功标准必须**可度量、可验收**，避免"做完了吗"的主观争论。

## 二、成功标准（按维度）

### 1. 功能完整性（权重 40%）

| 编号 | 指标 | 度量方式 | 目标值 |
|---|---|---|---|
| F1 | 核心功能清单全部实现 | 验收清单逐项勾选，无 P0/P1 级缺失 | 100% |
| F2 | 端到端场景可用 | 按 specs/requirements/ 中的用户故事逐条走查 | 全部通过 |

### 2. 质量指标（权重 30%）

| 编号 | 指标 | 度量方式 | 目标值 |
|---|---|---|---|
| Q1 | 自动化测试覆盖率 | pytest --cov | ≥ 70%（核心模块 ≥ 80%） |
| Q2 | 静态检查通过 | ruff / eslint 零 error | 0 error |
| Q3 | 缺陷收敛 | 迭代末期新增 vs 关闭缺陷比 | < 0.5 |
| Q4 | 关键路径响应时间 | 手工秒表/API 计时 | P95 < 2s |

### 3. 工程过程（权重 20%）

| 编号 | 指标 | 度量方式 | 目标值 |
|---|---|---|---|
| P1 | 代码经 PR 合入 main | git 统计直接 push 到 main 的次数 | 0 次 |
| P2 | 规格先行 | 每个 feature 分支合入前，specs/ 中有对应文档 | 100% |
| P3 | 全员提交 | git shortlog 各成员均有合并记录 | 全员 |
| P4 | AI 使用日志归档 | docs/ai-usage-log/ 每周一份 | 12/12 周 |

### 4. AI 工具链可用性（权重 10%）

| 编号 | 指标 | 度量方式 | 目标值 |
|---|---|---|---|
| A1 | 组员 AI CLI 就绪率 | 凭证登记表（只记可用性） | 100% |
| A2 | 环境可复现 | 新成员按 README 从零搭建 ≤ 30 分钟 | 实测达标 |

## 三、度量约定

- 数据来源以 git 仓库、CI 输出、测试报告为准，不接受口头声明
- 每周例会核对一次仪表盘数据，偏差 > 20% 的指标须在周报中说明原因
- 指标变更须组内全员同意并记录于本文件的变更记录
