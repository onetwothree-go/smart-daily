## 二、处置口径（二选一中的 B 变体）

> 原先给出的两条路：A「确认提前落地 v1.1」＝把 N8 从排除项改成范围条目并全量升版；B「回退自动触发」＝撤掉计划任务。本记录采用 **B 的轻量变体：不撤代码，明确标注为 v1.1 预研、不计入 v1 验收**。

| 决定 | 内容 |
| --- | --- |
| ① 本期 v1 验收口径 | **不变**：S7 / N8 / I4 仍为「22:00 本机手动触发，自动定时汇总列入 v1.1」；`tasks.md` §12.3 的 N8 守卫继续有效 |
| ② `SmartDaily-2200` 计划任务 | 定性为 **v1.1 预研实现**，保留在仓库与 README 中作为「已提前实现的能力」，**不计入 v1 功能演示与验收**，也不作为 N8 守卫失效的证据（GitHub Actions 侧仍无 `schedule`） |
| ③ C7 `all()` / CLI 四码 | 属于对 design 3.4 契约的闭环修正，**计入 v1**，见 `3f2b3ee` / `67bd661`；已同步进用例模板、对照表与需求分析报告 |
| ④ 升版方式 | 只在 `specs/proposal.md` **变更记录**新增一行「0.4.2 补记（不升版）」（说明轮换、维护权与预研定性），**不改 S/N/C 条目正文、不改 0.4 历史签字行**；`specs/tasks.md` §12.3 补一句守卫说明 |
| ⑤ 为什么不用 A | 把 N8 从排除项改成范围条目等于改变本期范围，须重走需求澄清与组内评审、重编 C 表与用例；距 11-15 评审会不足一周且会连带改动他人已签字材料，风险远大于收益 |
| ⑥ 为什么不用 B 原式 | 计划任务是开发工程师的既有提交，撤回会破坏其 v1.1 预研成果并制造新的合并冲突；保留代码、在规范侧说明边界即可 |
