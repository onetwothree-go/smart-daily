> 素材来源：本地副本 `D:\SDD-env\superpowers`；`SKILL.md` 294 行，另有 `visual-companion.md`、`builder-check-prompt.md` 与 `scripts/` 下 5 个文件

## 正文（约 200 字）

**触发描述**在 `SKILL.md` 的 frontmatter：`You MUST use this before any creative work - creating features, building components, adding functionality, modifying behavior, or planning anything new, in software or out of it (a talk, a business, a renovation)`。用 MUST 起头，把范围从写代码扩到"软件之外"，且钉死在"动手之前"——描述本身就是强制路由，不靠人自己判断该不该用。

**工作步骤**：先自问"关键信息是不是都在需求里"，都在就直接做，缺才开对话；缺则按死顺序走——铺开两三个方案让人选 → 写设计文档 → 拿到批准 → 交给 `writing-plans`。问之前先读材料；每理解一块就回述 200–300 字，把"你说的"和"我补的提案"分开，结尾问缺什么。文档按工作量定长短，但必须有 Approaches：考虑过哪几种、各吃什么亏、选了哪个、为什么。

**配套**：`visual-companion.md` 管"何时该开网页看"；`builder-check-prompt.md` 是验收装置——文档写完派一个不知上下文的子代理照文档出计划，出不来即说明文档不自足；`scripts/` 五个文件把"起本地页面看方案"固化成命令：`server.cjs` 是带 WebSocket 的服务，`start-/stop-server.sh` 管随机端口起停，`frame-template.html` 加 `helper.js` 出页面骨架与断线重连，省去手搓端口。

## 一句话结论

它治的不是"不会问"，而是**问完之后什么都没留下**：先用回述让人确认理解，再用设计文档把理解固定下来，最后派个不知情的子代理验证文档能不能独立支撑建造——三道校验，一道比一道硬。
