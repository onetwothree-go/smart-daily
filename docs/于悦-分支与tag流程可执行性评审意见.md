## 一、分支流程：可执行 ✅

**规范侧**（`BRANCHING.md` 第 1–27 行）定义了完整的四层模型（main / dev / feature / fix / docs）、受保护分支、PR 合并、命名规则与提交信息格式，判定标准明确，无歧义。

**执行侧**（`git branch -r` 实测）：

| 证据 | 说明 |
|---|---|
| `origin/dev` | 集成分支在用，领先 main 137 个提交 |
| `origin/feature/connectivity-test` | 按 `feature/*` 命名规则建的，规范被真实使用 |
| `origin/docs/design-redteam-review`、`origin/docs/tasks-md` | 按 `docs/*` 规则建的 |
| `origin/main` | 只接受合并，历史上是 PR 合并记录 |

**结论**：分支流程规范齐备、已被实际执行，**可执行**。

**一处偏差须记录**（不属流程缺陷，属执行滞后）：`main` 落后 `dev` 137 个提交，且 `main` 的 `specs/` 只有 `README.md` 与 `proposal.md`，**缺 `design.md` 与 `tasks.md`**。规范第 3 条要求「dev 验证稳定后由维护者合并到 main」，这一步至今未做（即 TK-902 状态 ⏳ P0）。后果是：`main` 无法作为 v1 的发布基线，TK-903 要求的「tag 落在 main 的发布提交上」也无处可落。

## 二、tag 流程：规范缺失，当前不可执行 ❌

**`BRANCHING.md` 全文没有任何 tag 章节**——`grep -niE "tag|标签|发布|版本号"` 只命中第 6 行「稳定发布分支」一句，那是分支注释，不是 tag 规则。

缺失的具体内容：

| 应有规则 | 现状 |
|---|---|
| 何时打 tag（对应哪个里程碑） | 未定义 |
| 打在哪个分支（main / dev） | 未定义；只在 tasks.md TK-903 里出现过一次，未进规范 |
| tag 命名规则（`v1-sdd` / `v2-*` 之类） | 未定义 |
| tag message 必含内容（版本号、基线、已知缺陷） | 未定义 |
| 谁有权打、是否可移动已发布的 tag | 未定义 |

**已发生的实际后果**：2026-11-10 已按指导书要求创建 `v1-sdd`，但位置在 `dev` 的 `b7656c7`，message 也未列三份规范版本号——与 tasks.md TK-903 的两条验收标准均不符。原因不是执行人擅自决定，而是**规范里没写，执行时只能凭指导书字面「v1 版源码打 tag」自行判断**。

## 三、建议补充的 tag 规范（~~草案，待组内确认后写入 BRANCHING.md~~ 已于 2026-11-11 由配置管理员写入 `BRANCHING.md`，并附过渡条款处理既有 dev 标签）

```markdown
## 标签（tag）规范

1. 里程碑标签只在 main 的发布提交上打，dev 上的临时标签须以 `-rc` 结尾（如 `v1-sdd-rc1`），且不进发布记录
2. 命名：阶段一用 `v1-sdd`，阶段二用 `v2-superpowers`；补丁版加 `.1`（如 `v1-sdd.1`）
3. tag message 必须含四项：日期 / 基线提交号 / 三份规范的版本号（proposal / design / tasks）/ 已知缺陷或限制
4. 已推送的标签不得删除重打；确需修正时新建补丁标签并在说明中注明被替代的旧标签
5. 打标签由配置管理员执行，打之前在群里公告一次基线提交号
```

上述第 1 条若被采纳，则当前 `dev` 上的 `v1-sdd` 应改名为 `v1-sdd-rc1`（或删除），待 TK-902 合并后在 `main` 上重打 `v1-sdd`。
