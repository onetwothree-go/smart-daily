| 通道 | 干什么 | 需要企业租户吗 | 现在能通吗 |

**所以推荐的打法是：先把推送通道跑通（今天就能完成），采集通道等团队建好再接。**

## 🔐 安全设置：三个选项怎么选

添加机器人的页面下方有「安全设置」区，官方文档说「**强烈建议**添加安全设置，
以提高安全性」。三个选项可以叠加，也可以只开一个：

| 选项 | 作用 | 勾了之后代码要不要改 | 建议 |
|---|---|---|---|
| **自定义关键词** | 只有含该关键词的消息能发出去 | 不用改，但要保证正文含该词 | ✅ **推荐，填「日报」** |
| **签名校验** | 请求必须带正确签名才放行 | 代码已支持，填 `FEISHU_WEBHOOK_SECRET` | ✅ 推荐（多一层） |
| **IP 白名单** | 只有名单内 IP 能调用 | 不用改，但换网络就发不出 | ⚠️ 校园网/家宽 IP 会变，慎开 |
| 仅群主和添加者可编辑 | 防止组员改机器人配置 | 不用改 | ✅ 建议勾上 |

### 为什么关键词可以放心填「日报」

代码里**所有**走 Webhook 的推送文本都含「日报」二字，已逐条核对：

| 推送路径 | 实际文本 | 含「日报」 |
|---|---|---|
| 个人日报 | `个人日报 2026-11-03` | ✅ |
| 团队日报 | `团队日报 2026-11-03` | ✅ |
| 连通性测试 | `智能日报生成器 · 连通性测试` | ✅ |

> 所以关键词填「日报」不会挡住任何一条正常推送。
> 如果填了别的词（比如「智能日报生成器」），测试消息能过但正式日报可能被拒（19024）。

### 签名校验：代码已经支持

勾选「签名校验」后飞书会生成一串密钥，**复制它**填进 `.env`：

```
FEISHU_WEBHOOK_SECRET=粘贴那串密钥
```

代码会自动在每次请求里带上 `timestamp` + `sign` 两个字段（算法见
`src/smart_daily/push/notifiers.py` 的 `gen_sign()`，已用官方示例值
`secret="demo"` / `timestamp=1599360473` 交叉验证三方一致）。

**不填也能跑** —— 密钥留空时请求体不带 sign，适配未开启签名校验的机器人。
但**勾了签名校验就必须填**，否则返回 `19021 sign match fail`。

> ⚠️ **密钥必须用「复制」按钮取，不能从界面截图认读。**
> 飞书在页面上显示的是**掩码**（实测界面显示 21 位，真实密钥 22 位），
> 抄下来的掩码会被服务端拒绝，报 19021。

### 怎么确认安全设置真的生效了（而不是"看着像生效了"）

勾选并点「完成」之后，跑这一条：

```bash
cd /d/pro/smart-daily && uv run --env-file .env python scripts/verify_security.py
```

它用**反向探测**逐层验证，每一层都主动发一个「本该被拒」的请求：

| 探测 | 发什么 | 期望结果 | 证明什么 |
|---|---|---|---|
| 签名层 | **错误**密钥 + 含关键词 | `19021` 被拒 | 签名校验真的启用了 |
| 关键词层 | **正确**签名 + **不含**关键词 | `19024` 被拒 | 关键词校验真的启用了 |
| 正常通路 | 正确签名 + 含关键词 | `0` 成功 | 推送没被误伤 |

**为什么不能只看"推送成功"**：配置页勾了但没点「完成」保存时，
飞书服务端**根本不做校验**，推送照样成功 —— 看起来一切正常，安全设置形同虚设。
实测记录：点「完成」前用错误密钥发送返回 `code=0`（放行），点「完成后返回 `19021`（拦截）。

> **探测顺序的坑**：飞书的校验顺序是**先签名、后关键词**。
> 测关键词层时必须带**正确的签名**，否则请求被签名层先拦掉，
> 永远测不到关键词（实测踩过：探测报 19021，看起来像"关键词坏了"，其实是探测方法错了）。

### 三项全开的效果

| 勾选 | 不填对应配置的后果 |
|---|---|
| 关键词「日报」 | 19024 —— 消息正文必须含「日报」 |
| 签名校验 | 19021 —— 签名匹配失败或时间戳超 1 小时 |
| IP 白名单 | 19022 —— 当前出口 IP 不在名单里 |

检查脚本 `scripts/check_webhook.py` 会把这三个错误码的处置方式直接打印出来。

> **本项目当前状态（2026-11-03 实测）**：关键词 ✅ 签名 ✅ IP 白名单 ❌（未勾，IP 会变）。
> 三层探测全绿，日报推送正常。

> 建议在机器人「安全设置」里加一个**自定义关键词**（比如「日报」），避免 Webhook 地址泄露后被恶意调用发垃圾消息。
> 但注意：加了关键词后，消息正文必须包含该关键词，否则返回 19024 拒绝。

## 第 2 步：批量开通权限（2 分钟，最省事）

飞书支持粘贴 JSON 一次开通，不用一个个搜着勾。

1. 左侧导航 → **开发配置 → 权限管理**
2. 点「**批量导入导出权限**」
3. 把下面这段 JSON **整个复制进去**：

```json
{
  "scopes": {
    "tenant": [
      "im:message",
      "im:message:readonly",
      "im:chat",
      "task:task",
      "contact:contact.base:readonly",
      "contact:user.base:readonly"
    ],
    "user": []
  }
}
```

4. 点「下一步」→「确认导入」

> 完整文件也存了一份在项目里：`scripts/feishu_permissions.json`

### 这几个权限分别管什么

| 权限 | 管什么 | 对应代码里调用的接口 |
|---|---|---|
| `im:message` | 发送和接收消息 | `/im/v1/messages` |
| `im:message:readonly` | 读取历史消息 | 同上（只读版，配合 `im:message` 一起开） |
| `im:chat` | 获取与更新群组信息 | `/im/v1/chats` |
| `task:task` | 查看、创建、编辑和删除任务 | `/task/v1/tasks` |
| `contact:contact.base:readonly` | 获取通讯录基本信息 | `/contact/v3/users` |
| `contact:user.base:readonly` | 获取用户基本信息 | 同上 |

> **全是应用身份权限（`tenant_access_token`）**，所以 `"user": []` 留空 —— 你代码里用的是应用身份，不需要用户授权那一套。

### 如果批量导入失败（权限名报错）

说明飞书调整过某个权限名。改成手动开：权限管理页 → 搜索框输入下面任意一个 → 勾上带**「免审权限」**或**「高级」**标记的那一项 → 确认开通权限：

```
im:message          → 发送和接收消息
im:chat             → 获取与更新群组信息
task:task           → 查看、创建、编辑和删除任务
contact:user.base:readonly → 获取用户基本信息
```

## ⚠️ 已知问题：错误码 21001（租户身份限制）

**症状**：后台配置全对、权限全开，但调任何 OpenAPI 都返回：

```
code: 21001
msg:  Access denied due to platform policy
```

**这不是配置错误。** 用三种密钥状态实测，可以把每一层都隔离验证：

| 填进去的密钥 | 返回 | 判定 |
|---|---|---|
| 随便改错的（截断 / 加乱码） | `10014 app secret invalid` | 密钥本身无效 |
| **正确的 App Secret** | **`21001 Access denied due to platform policy`** | **密钥正确，被平台策略拒** |
| 无效 token 调业务接口 | `99991663 Invalid access token` | 接口可达，服务端正常 |

**根因**：开发自建应用的前提是「**已成为飞书企业用户**」。**个人版租户不具备开放平台 OpenAPI 调用资质**，请求在策略层被直接拒绝。

### ⚠️ 先做这一步再下结论：发布应用版本

**当前应用状态是「待上线」，即从未发布过版本。** 飞书官方有一条专门公告
《[未发版自建应用能力变更](https://open.feishu.cn/document/platform-notices/breaking-change/Call_OpenAPI_without_Auditing)》：

> 「请前往开发者后台检查**从未发布过且状态为"待上线"**的自建应用……
> 开发者如未在生效时间前发布版本，则**可能导致应用无法成功调用 OpenAPI**。」

所以 21001 有**两个候选原因**，需要先把「未发版」这条排除掉：

| 候选原因 | 怎么验证 |
|---|---|
| ① 未发布版本 | 发布一版后重测 —— **2 分钟，成本最低** |
| ② 个人版租户无资质 | 建免费团队 → 在新团队下重建应用 |

**先做①**：左侧「**版本管理与发布**」→ 创建版本 → 版本号填 `1.0.0` →
「**可用范围**」点编辑把**全部组员**加进去 → 申请发布 → 确认发布。

发布后重跑 `scripts/check_feishu.py`：
- 返回 `code: 0` → 根因是①，**到此为止，不用建团队**
- 仍返回 `21001` → 根因是②，继续走下面的建团队流程

> ⚠️ 注意：如果后续**补加了权限**，必须**重新发一个新版本** ——
> 旧版本不会带上新加的权限。

### 确认是②之后：处置方式

## ❌ 你不需要做的事（别浪费时间）

网上很多教程会让你配「事件与回调 → 长连接 → 订阅 `im.message.receive_v1`」。**那是给「机器人被动响应消息」用的。**

你的采集器是**拉模式** —— 定时调 `GET /im/v1/messages` 拿历史消息，不需要监听事件、不需要 WebSocket 长连接、不需要回调地址。**这一整块跳过。**

## 错误码对照表（排查用）

| 报错 | 含义 | 怎么办 |
|---|---|---|
| `code 99991663` | App ID / App Secret 不正确 | 重抄第 3 步的 Secret，注意别带空格 |
| `code 99991661` | 应用不存在 | 核对 App ID 是否写错 |
| `code 99991672` | 应用未发布 / 版本未生效 | 回第 4 步发布版本 |
| `HTTP 403` | 权限不足 | 权限没开全 / 没发布 / 不在可用范围 |
| `HTTP 401` | token 过期 | 采集器会自动强制刷新一次；持续报错说明 Secret 不对 |
| 采到 0 条消息 | 机器人不在群里 | 回第 5 步拉机器人进群 |
| 采到 0 条任务 | 本应用没创建过任务 | `tenant_access_token` 只能读到**本应用创建**的任务；要读全队任务需 `user_access_token` |

| 变量 | 用途 | 什么时候要 |
|---|---|---|
