## ① 执行环境说明

- **运行机**：本机 Windows；Python 3.13 + uv + `.env`（凭证走环境变量注入，严禁入仓库）。
- **启动方式**：`uv run --env-file .env`（直接 `python -m` 不读 .env 会静默降级）；主流程经 CLI 触发。
- **数据库**：SQLite，路径经 `DB_PATH` 配置；本核对一律用**临时库**（`DB_PATH` 指向临时文件、`--day` 固定日期），不污染真实历史库；核对用 `sqlite3` 查询断言（如 C5 的 COUNT）。
- **数据来源与注入**：生成类用例用 `--mock` 或 fixture 注入构造数据（3 CommitEntry+2 TaskEntry 等）；身份归并数据集经 `.env` 的 `MEMBER_DISPLAY_NAMES` 注入；时区用例注入 UTC aware 时间戳、本机时区固定 Asia/Shanghai。
- **采集类（C2/G5）**：假 token/假凭证直接注入环境变量，repo 指向真实仓库触发 401/降级路径；实时通道（C10）由 GitHub Actions 按 push 事件触发，两条 Webhook 凭证放 Secrets。
- **现有已实测证据**：2026-11-06（token 未加载降级、方赫三身份合并、四人 19 条一次生成、4 邮件+群全 OK）与 2026-11-09 实时连通（`72155d0`：HTTP 200/code=0/1.48s/1 条含 2 commit）——按评审意见，C2 证据不算数、C4/C10 只算一半，**已于 2026-11-10 全部补测完毕**，结果见 `docs/testing/用例执行记录-第2周.md`（10 通过 / 6 不通过，16 行无未执行项）。

## ② 执行顺序建议（按依赖关系分三批）

1. **采集类先行**：C2（假 token 注入→降级链路）→ G5（凭证失效/源故障不中断+留痕）——先验证数据能不能稳定取到，是后续生成/推送的前提；G2 为观察项、不入判定范围，不参与本批。
2. **生成类次之**：C1（条目数/1:1）→ C8（两种空）→ C9（跨时区归属）→ C5（落库幂等）→ C3 / G3（身份归并，同 G3 数据集、与 C1 可复用数据集）——生成层纯函数确定性最高，先行闭环；C1 同时验证实时提醒不计入计数。
3. **推送类最后**：C4（团队+个人骨架比对，依赖生成稳定）→ C7（送达判定，按 CLI 推送明细 5 通道 ok 状态判 5/5，不验时间）→ C10（实时提醒，含失败注入，独立通道）→ G4（骨架一致+送达时间，复用 C4 骨架比对结果）。
4. **观察项（G2/C6）不进入本执行序列**，实测列标「不适用」，本轮不建计时用例；**C7 已恢复可测**，归入第 3 批推送类执行，按 CLI 推送明细 5 通道 ok 状态判 5/5，不验「23:59 前」（该要求为运营约定、人工核对）。
