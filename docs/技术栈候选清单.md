## 三、按技术关注点的候选清单

### 3.1 CLI 参数与子命令

**候选 A：argparse（标准库，现状）**
① CPython 自带，随解释器维护，无独立版本节奏。② cli.py 现用 `build_parser()` 平铺 flag（--mock/--source/--no-notify/--day/--list），零改动即现状。③ 零成本。④ 训练语料最全，报错直白。⑤ 零新增依赖。⑥ 中文资料海量。

**候选 B：typer**
① 第三方，FastAPI 同作者（tiangolo）维护，社区活跃（当日数据未核实）。② 需把 cli.py 的 flag 注册改成装饰器风格，入口函数签名要适配；采集/编排层不受影响。③ 需理解「类型注解 → 参数」映射规则，成本中低。④ 语料多，API 现代，AI 生成的参数定义较可靠。⑤ 新增 typer 及其依赖 click。⑥ 中文资料较多。

**候选 C：click**
① 第三方，Pallets 组织（与 Flask/Jinja2 同门）维护，成熟（当日数据未核实）。② 与候选 B 同样要重写 cli.py 的参数注册。③ 装饰器加 Context 概念，成本中等。④ 语料非常多。⑤ 新增 1 包。⑥ 中文资料多。

竞品做法：Aiscribe 对外提供 daily/weekly/sources/mcp/ui 等八个子命令（见 docs/同类竞品调研记录.md 方案一）；本项目现阶段 flag 数量少，是否子命令化取决于功能面增长。

### 3.2 GitHub 数据采集

**候选 A：httpx 直连 REST（现状）**
① httpx 由 encode 组织维护（与 FastAPI 生态同源），活跃（当日数据未核实）。② 已落地：collectors/github.py 用 httpx.Client(base_url) 封装了认证头、API 版本头、409/401/403/404 的细分错误语义（409 判空仓库、401/403 判凭证）、iter_commits 手动翻页，并实现 WorkSource 协议，零改动。③ 已过学习期。④ httpx 语料充足，异常栈清晰。⑤ 零新增。⑥ 中文资料多；但 GitHub API 在国内网络可达性有波动——仓库已备 docs/GitHub访问诊断报告.md 与代理指引，属已识别风险。

**候选 B：PyGithub**
① 老牌第三方，社区维护（当日数据未核实）。② 与 github.py 是替代关系：省去手写分页与字段映射，但要为降级契约重新包一层错误翻译（409=空仓库这类项目自定义语义 SDK 并不感知），并引入 requests 系传递依赖，与 httpx 并存两套 HTTP 栈。③ 中等。④ 语料多。⑤ 新增 PyGithub 及 requests 等一组传递依赖。⑥ 中文资料中等。

**候选 C：调 gh CLI（子进程）**
① gh 是 GitHub 官方 CLI，官方维护（当日数据未核实）。② collectors/base.py 协议不变，新增一个 subprocess 封装实现；代价是把 Python 依赖换成「运行机器必须装 gh 且已登录」的外部依赖。③ 学习成本低，工程细节要防坑（编码、超时、stderr 解析）。④ 子进程编排语料中等。⑤ Python 侧零新增，负担转移到环境。⑥ gh 本体在国内的下载与登录需网络条件。

竞品做法：gh-daily-report 的采集端直接调 gh CLI 而不用任何 SDK，支撑起了完整的日报流水线（见 docs/同类竞品调研记录.md 方案二）。

### 3.3 飞书数据采集

**候选 A：httpx 自签直连（现状）**
① 同 3.2 候选 A。② 已落地：collectors/feishu.py 自管 tenant_access_token 缓存（过期前 300 秒刷新）、任务/群消息/通讯录/群列表四组接口、页码翻页、21001 等错误码的中文提示，零改动。③ 已过学习期。④ 排查成本在「对照飞书错误码文档」而非代码本身。⑤ 零新增。⑥ 飞书是国内服务，直连无障碍；官方中文文档即一手资料。

**候选 B：官方 SDK（lark-oapi）**
① 飞书官方维护（当日数据未核实）。② 替代 feishu.py 手写的 token 管理与请求封装，WorkSource 协议外壳保留、内部替换；SDK 是否封装 user_access_token 授权流程未读其文档（见证据缺口）。③ 需读官方文档，成本中等。④ 官方中文文档完备，SDK 迭代快，AI 生成的调用代码容易过时。⑤ 新增 1 个 SDK 包。⑥ 官方中文文档，国内可用。

竞品做法：三竞品均不涉及飞书生态——Aiscribe 采本机 AI 会话、gh-daily-report 采 GitHub、Teambition 数据不出自家系统（见 docs/同类竞品调研记录.md 方案一/二/三），无现成对照。

### 3.4 LLM 调用（AI 摘要备用）

边界先说清：push/generator.py 模块注释明确「本期范围明确排除智能摘要，将来要加 AI 摘要，是在这层外面加一个可选实现，而不是改这层」。以下仅登记。

**候选 A：httpx 直调 REST（DeepSeek/通义等兼容接口）**
① 同 3.2 候选 A。② 与现有 HTTP 栈统一，作为 generator 外挂的可选实现接入 orchestrator；各家接口的鉴权与报文差异由自己维护。③ 低。④ 各家 REST 均有公开文档，语料充足。⑤ 零新增。⑥ DeepSeek/通义等国内端点直连可用；海外模型需代理。

**候选 B：openai 兼容 SDK**
① OpenAI 官方维护（当日数据未核实）。② DeepSeek/通义等国内服务商普遍提供 openai 兼容端点，改 base_url 即可复用；其底层据既有知识使用 httpx（具体版本行为未核实），与现有栈同源。③ 低到中。④ 语料非常多。⑤ 新增 1 包。⑥ 国内兼容端点可用，OpenAI 官方端点需代理。若第 2 周确认对接 Claude，再评估 anthropic 官方 SDK，形态与本候选同类。

**候选 C：litellm 统一网关**
① 社区项目 BerriAI 维护，迭代快（当日数据未核实）。② 提供多模型路由、重试、用量统计；接入点同样是 generator 外的可选实现，但要审视其抽象与本项目降级链思路是否重复建设。③ 中到高，概念多、版本更新快。④ 语料量大但时效性差，AI 生成代码易过时、排查要翻源码。⑤ 依赖重，引入自身一组传递依赖。⑥ 官方中文资料有限。

竞品做法：Aiscribe 把 AI 归纳做成可插拔——LLM 非必需，无 Key 或请求失败一律退回模板并如实记录原因（见 docs/同类竞品调研记录.md 方案一）；这与本项目「推送失败不阻断主流程」的契约同构。

### 3.5 报告渲染

**候选 A：f-string 拼接（现状）**
① 标准库。② 已落地：push/generator.py 用 lines 列表加 join 拼出个人与团队日报，纯函数无副作用，测试友好，零改动。③ 零。④ 零门槛。⑤ 零新增。⑥ —。

**候选 B：Jinja2**
① Pallets 组织维护，模板领域事实标准（当日数据未核实）。② 把 generator.py 的拼装逻辑抽成模板文件，格式调整不动代码；渲染仍是纯函数，生成层性质可保留。③ 低，模板语法半天内可上手。④ 语料极多。⑤ 新增 Jinja2 与 MarkupSafe。⑥ 中文资料海量。

**候选 C：python-docx（Word 输出）**
① 社区维护（当日数据未核实）。② 仅当「日报需要 Word 版」成为真实需求才有意义，与 Markdown 主流程是并列输出格式的关系，不替换现状。③ 中等。④ 语料中等，中文字体等样式细节易踩坑，出错要查 XML 层。⑤ 新增 python-docx 与 lxml（含 C 扩展，安装体积明显增大）。⑥ 中文资料中等。

竞品做法：Aiscribe 出 Word 不用 python-docx，用纯标准库手写 WordprocessingML，把零三方依赖贯彻到导出层（见 docs/同类竞品调研记录.md 方案一）；gh-daily-report 则是纯手拼 Markdown 三节（见方案二）。

### 3.6 配置与密钥管理

**候选 A：os.getenv + .env + uv --env-file（现状）**
① 标准库加 uv 内建能力。② 已落地：README 载明 11 个环境变量，github.py 与 feishu.py 均以 from_env() 工厂读环境并抛 SourceUnavailableError，加载靠 `uv run --env-file .env`；零改动。③ 零。④ 零门槛。⑤ 零新增。⑥ —。

**候选 B：pydantic-settings**
① pydantic 团队维护（当日数据未核实）。② 集中声明配置项类型与默认值，自动校验；但现有 11 个变量的校验已分散在两个 from_env() 工厂里且被断言覆盖，迁移属于重构而非增量。③ 中，需学 BaseSettings 与嵌套模型。④ 语料多。⑤ 新增 pydantic-settings 与 pydantic（含 Rust 编译的 pydantic-core）。⑥ 中文资料较多。

**候选 C：标准库 tomllib**
① CPython 3.11+ 自带，只读解析 TOML。② 若配置改走 TOML 文件可与 pyproject 同源；但密钥类配置按仓库纪律「严禁写入代码或提交仓库」，TOML 与 .gitignore 的边界要重划，且只读不写、生成配置模板还得另想办法。③ 低。④ 语料中等。⑤ 零新增。⑥ —。

竞品做法：gh-daily-report 配置全靠环境变量，无配置文件（见 docs/同类竞品调研记录.md 方案二）；Aiscribe 是 JSON 配置文件加环境变量覆盖的混合（dingtalk_config、projects.json 及其环境变量，见方案一）。

### 3.7 日志与终端输出

**候选 A：print 直出（现状）**
① 标准库。② 现状即 print（cli.py 与 orchestrator.py 的 [source]/[push] 前缀行），logging 尚未引入，零改动。③ 零。④ 零门槛。⑤ 零新增。⑥ —。

**候选 B：logging 结构化升级**
① 标准库。② 在 print 不撤的前提下补文件日志，定时任务无人值守时的失败才有据可查；与 base.py 降级链聚合 errors 字符串的做法天然衔接。③ 低。④ 语料极多。⑤ 零新增。⑥ —。

**候选 C：第三方终端库（loguru / rich）**
① loguru 为社区维护，rich 由 Textualize 维护（当日数据未核实）。② loguru 的 API 更直白，rich 可把 cli.py --list 输出与推送明细表格化；两者都会与既有 print 风格并存，需要输出约定。③ 低。④ 语料均多。⑤ 各新增 1 包。⑥ 中文资料较多。

竞品做法：Aiscribe 在降级路径上如实记录 last_error 并打印提示，不静默吞错（见 docs/同类竞品调研记录.md 方案一）；本项目 base.py 的 errors 聚合是同一思路。

### 3.8 测试

**候选 A：pytest**
① 社区事实标准（当日数据未核实）。② 现有验证是 scripts/verify_collectors.py 的脚本式断言，迁到 pytest 可获得逐用例报告、fixture 与参数化；WorkSource 四个实现可直接参数化跑同一组契约断言。③ 低。④ 语料极多。⑤ 新增 pytest 及少量传递依赖（仅开发依赖）。⑥ 中文资料海量。

**候选 B：标准库 unittest**
① CPython 自带。② 不加依赖即可组织用例；fixture 与参数化表达能力弱于 pytest，契约断言写起来更啰嗦。③ 低。④ 语料多。⑤ 零新增。⑥ —。

**候选 C：respx（httpx 请求 mock）**
① 社区维护，专为 httpx 设计（当日数据未核实）。② 可在不真发请求的前提下测 github.py 与 feishu.py 的错误码分支（409/401/403、飞书 21001 等），与降级契约的断言一一对应；依赖恰好是已有的 httpx。③ 低到中。④ API 面小，语料中等偏小众。⑤ 新增 1 包。⑥ 中文资料少。LLM 调用的录制回放与这是同一思路（把 HTTP 层钉死），第 2 周若接 AI 摘要再评估具体工具。

竞品做法：gh-daily-report 配独立测试脚本与 test-data/ 测试数据，回归不依赖真实 API（见 docs/同类竞品调研记录.md 方案二）；Aiscribe 仓库含 tests/ 目录（见方案一）。

### 3.9 定时触发

**候选 A：操作系统计划任务（Windows 任务计划程序）**
① 系统组件。② 与 `uv run --env-file .env smart-daily` 一行命令直接对接，零代码改动；组员机器以 Windows 为主。③ 低。④ 无代码可谈语料。⑤ 零新增。⑥ 系统自带。

**候选 B：GitHub Actions cron**
① GitHub 官方。② 免本机开机，产出直接在仓库里留痕；境外 runner 出网到飞书开放平台已于 2026-11-09 实测连通（见本节末尾实测记录），凭证仍需配成 Actions Secrets。③ 低到中（YAML 工作流）。④ 语料多。⑤ 对 Python 包零新增。⑥ 跨境可达性问题已由实测消除，剩余风险集中在凭证管理与 Secrets 维护。

**候选 C：APScheduler**
① 社区维护（当日数据未核实）。② 进程内常驻调度；本项目是「跑一次就退出」的 CLI，常驻形态与现状不匹配，除非演化成后台服务。③ 中。④ 语料多。⑤ 新增 1 包。⑥ 中文资料较多。

实测记录（2026-11-09，赵蕊，第 1 周分工单）：在 feature/connectivity-test 分支提交最小连通性测试（commit 72155d0，含 `.github/workflows/connectivity-test.yml` 与 `scripts/connectivity_test.py`，仅测试分支触发，不刷 main/dev）。Actions runner 向飞书 Webhook 发送签名消息：HTTP 200、飞书业务返回 code=0、step 约 2 秒。本节此前「出网到飞书开放平台的可用性未验证」的表述自即日起被实测结果取代。

竞品做法：Aiscribe 不内置调度，仓库只给 automation_example.json 定时任务示例，把「何时跑」留给外部（见 docs/同类竞品调研记录.md 方案一）。

### 3.10 分发安装

**候选 A：uv tool install**
① uv 官方能力，Astral 维护。② 支持从私有 Git 仓库直接安装为全局 CLI，虚拟环境自动管理；前提是组员机器都装了 uv。③ 低。④ 语料在增长。⑤ 工具链层面零新增。⑥ Astral 文档英文为主，中文社区资料在增长。

**候选 B：pipx**
① 社区维护，成熟（当日数据未核实）。② 与候选 A 同类能力，前提是机器有 Python 与 pipx；与已选 uv 的路线重叠。③ 低。④ 语料多。⑤ 零新增。⑥ 中文资料多。

**候选 C：PyInstaller 单文件**
① 社区维护（当日数据未核实）。② 对零 Python 环境的接收方友好；代价是产物体积大、与 uv 管理的 3.13 解释器组合未实测，且脱离 uv 运行后 .env 加载需要 python-dotenv 一类方案补位（联动 3.6）。③ 中，打包配置与杀软误报排查费时。④ 语料多，但 3.13 相关问题在训练语料里可能滞后。⑤ 打包工具本身依赖重，产物大。⑥ 中文资料多。

竞品做法：Aiscribe 以「内核零三方依赖」从源头降低安装门槛（见 docs/同类竞品调研记录.md 方案一）。

## 六、留给第 2 周 ADR 的开放问题

1. **LLM 调用要不要引入统一网关层**：用 litellm 这类网关还是各家直调，取决于是否要多模型切换——这一点产品需求还没澄清。要定它，需先明确支持哪些模型、是否要求运行时切换。
2. **AI 摘要的挂载点**：generator.py 已声明 AI 是「这层外面加的可选实现」，但外层是 orchestrator 里的可选步骤还是独立模块未定；要不要引入 Aiscribe 式「AI 只改条目文字、程序校验排版、不过退模板」的约束（见 docs/同类竞品调研记录.md 方案一）也未定。要定它，需第 2 周接口契约评审先划清生成层边界。
3. **GitHub 采集维持 httpx 直连还是换 SDK/gh CLI**：直连已实现并带降级语义，换实现必须有明确收益；收益取决于是否扩采 PR 评审等字段、以及代理环境下的稳定性结论。要定它，需读 docs/GitHub访问诊断报告.md 的结论并明确第 2 周采集字段范围。
4. **飞书 user_access_token 授权链路**：feishu.py 模块注释写明 tenant_access_token 只能读应用自建的任务，读全队任务需每个成员授权一次；是否引入该授权、SDK 能否省掉这部分工作（见 3.3），直接影响飞书采集候选的取舍。要定它，需确认产品上「任务」数据采谁的，以及飞书免费团队重建后的资质实测结果。
5. **配置加载方式与分发形态联动**：uv --env-file 依赖 uv 运行；若 3.10 选 PyInstaller，必须补 python-dotenv 一类加载方案；若全组统一 uv tool install，现状够用。要定它，需先定分发形态并摸底组员机器环境。
6. **测试框架迁移与 HTTP 层 mock 策略**：verify_collectors.py 的脚本式断言与 pytest 是迁移还是并存、respx 覆盖哪些错误码分支，均未定；README 进度表显示单元测试尚未开始。要定它，需第 2 周 TDD 任务对测试记录格式的具体要求。
7. **定时触发落点**：本机计划任务、GitHub Actions 还是常驻服务，取决于部署形态与「谁全天开机」；Actions 到飞书的连通性已于 2026-11-09 实测通过（见 3.9 实测记录）。要定它，还需明确 Actions Secrets 的凭证管理方式，并做出部署决策。
