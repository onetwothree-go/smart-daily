### 第 1 问 · 为什么 ADR 必须记录「被否决的备选项」？

**结论先说**：ADR 记的不是「我们选了什么」，而是「在当时的约束下，为什么别的路走不通」。只写结论的决策不可审计——后来人分不清某个方案是**没考虑到**，还是**考虑过并否决了**；这两者对后续维护的含义完全相反。

**第一，备选项让决策过程可被评审。** 本组 `specs/design.md` 的 ADR-101~104 在 0.1 版只有状态、背景、决策、论证、后果，0.5.1 的变更记录（第 643 行）专门补了一句「ADR-101~104 各增『备选项』行」，理由写的是「按交付项自检补齐文档结构」。也就是说，这一栏原本是缺的，是红队与自检把它挑了出来。补完之后才看得见：ADR-101 在 httpx 直连 / PyGithub / `gh` CLI 子进程 / lark-oapi SDK 四者中选了直连；ADR-102 在标准库 sqlite3 / JSON 文件 / MySQL 中选了 sqlite3；ADR-103 在「采集器内重试 / 静默跳过 / 中断全流程 / 异常驱动降级」中选了最后一项；ADR-104 在本机计划任务 / GitHub Actions / 常驻服务中选了 Actions。没有这张候选表，评审者只能判断「现在的代码能不能跑」，无法判断「有没有漏掉更合适的路」。

**第二，被否决项不写清楚，会以「新功能」的形式悄悄回流。** 本项目正在发生一个例子：ADR-104 把「本机计划任务（cron / Windows 任务计划程序）」列为被否决备选项，但它的决策范围其实是**实时提交通知**那条通道；每天 22:00 的汇总日报是 design 1.4 明确分开的另一条独立通道，ADR 里没写「这条通道的定时触发是否同样被否」。11-10 的提交 `3f2b3ee` 新增 `scripts/run_daily.ps1` 并注册本机计划任务 `SmartDaily-2200`，把 22:00 汇总改成自动触发，而 `specs/proposal.md` 的 S7 / N8 / I4 都写着「本期本机手动触发，定时任务列 v1.1」，`specs/tasks.md` §12 也写「无 schedule」，proposal 并未升版——规范与实现就此分叉。备选项如果连同「适用范围、否决理由、触发重议的条件」一起写清，遇到这种情况就能立刻判断：是约束变了、该走 ADR 升版 + 变更记录 + 同步 tasks / 用例 / 报告，还是压根没考虑、该补论证；而不是两边各说各话。

**第三，约束会变，备选项是判断「该改」还是「该守」的基准。** 四条 ADR 每条都带「触发重议的条件」，例如 ADR-104 写「runner 到飞书连通性实测不可用 → 回退本机计划任务」。design 0.4.1 的变更记录里，把 ADR-104 后果从「连通性未实测」改成「实测已闭合」（run `42587824934`，HTTP 200 / code=0），就是约束变化后留痕更新的实例。若只留结论，后来人既不知道当初为什么否，也不知道什么条件下可以重启讨论，容易把「条件已满足、可以重议」误当成「一直都可以」，或把「已验证」再争论一遍。

**所以**：备选项把 ADR 从「结论公告」变成「可审计的决策记录」。它服务于三类人——红队审的是决策过程而非结果，后来人判断约束是否已变，实现者不会把被否方案当新点子捡回来。指导书第八部分要求技术调研报告第 2 章写「候选技术对比（含备选项表格）」、第 4 章「选型结论与 design.md 中 ADR 对应」，也是同一条逻辑：先留候选，再谈选择。

### 第 2 问 · 接口契约为什么比实现更重要？

**结论先说**：契约定义「什么算对」，实现只是「这一次做成了什么」。实现可以换语言、交给 AI 重写、甚至逐行改掉；契约一改，用例、测试、验收标准、报告要全部跟着改。所以契约是基准，实现是被检验的对象，二者重要性不在一个量级。

**第一，没有契约，「对」无从定义。** `specs/design.md` 3.4 把「推送成功」翻译成可观测的约定：`push_status` 五态（ok / partial / failed / no_channel / skipped）、不变量 `pushed == (push_status == "ok")`、Python 的 `all([]) == True` 真空真值不得产生 `pushed=True`、CLI 退出码 0/1/2/3，以及五条不变量（例如 `notify=True` 时 `pushed=False` 当且仅当退出码为 3）。proposal 的 C7 只说「全部 ok 才算成功」，是契约把它变成能观测、能判定的输出。

**第二，本组三个真实缺陷，全靠「对照契约与实现」才抓得出来。** 于悦《红队评审意见清单》RT-01 指出：实现 `orchestrator.py` L215 是 `pushed = any(...)`，任一通道成功即算已推送，与 C7「全部 ok」相抵，意见原文判「按现状实施 C7 验收必失败」，定级高；RT-02 指出 `cli.py` L110 恒 `return 0`，即使全通道 FAIL，成败无法从进程退出码观测；RT-09 又记下 `notifiers.py::MultiNotifier.send()` 用 `any(results)`，若编排改用它就会重演判定漂移。这三条的共同点是——**代码都能跑、语法都没错**，错在偏离契约。只盯实现的话，`any()` 和 `all()` 看起来都「说得通」，没有任何依据判定哪个是 bug；正因为契约白纸黑字写了「全部 ok」，红队才能定级、指出落点、要求 design 0.5 补齐 3.4 契约。

**第三，契约决定验收的方向，倒过来会掩盖规范缺陷。** 本组的闭环顺序是：design 0.5 因 RT-01/02 补 `push_status` 五态与退出码契约 → `tasks.md` 的 TK-103 / TK-604 / TK-707 承接 → 提交 `3f2b3ee` 把 `any()` 改成 `all()` → `67bd661` 落地 0/1/2/3 四码 → 杨佳莹《接口契约工程可行性评审意见》逐条按「能不能按现有代码实现 / 缺什么 / 建议」复核，给出「12 条一致、4 条缺证据、8 条需调整、3 条需架构师裁定」，并明确实现侧差异按 tasks 推进、不在评审意见里改 `specs/`。也就是**实现被契约校正，而不是契约被实现倒推**。若从代码反推验收标准，`any()` 会被写成「预期行为」，C7 将永远通过，规范里的漏洞再也暴露不了——这也正是第 3 周思考题「从验收标准生成测试 vs 从代码生成测试」要先埋伏笔的原因。

**第四，契约还能把「还没做」和「做歪了」分开。** design 2.2 / RT-06 约定映射解析收敛到 `identity.lookup_display_name()` 并统一 `strip() + casefold()`，但 `src/smart_daily/identity.py` 至今未建，采集链 `github.py` 大小写敏感、实时通道 `notify_push.py` 用 `.lower()`。杨佳莹评审意见第 2 条据此写「实时通道一致，采集链路需调整」。有契约，才能把这种「两条链路各自能跑、口径却不一致」标成待收敛项；没有契约，它只会被当成代码风格差异放过。

**落到我这周的工作**：我做的「需求可追溯对照表」把 C1–C10 映射到**可观测输出**、再经用例落到 TK 与代码，而不是从代码路径倒推标准；用例模板里每个 UC 的后置条件与扩展异常流也都先按 design 3.x 的契约写。原因就是上面四条：验收标准必须从契约导出，否则「测试通过」只证明代码和自己一致，不证明它符合需求。
