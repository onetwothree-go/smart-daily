## 二、U1 裁定详情（空列表语义）

### 2.1 三方表述对照

| 出处 | 原文表述 | 空列表的含义 |
| --- | --- | --- |
| `v1/specs/design.md` ADR-103 ②（0.5.1，第 5 节） | 「降级链**异常驱动**——捕获异常即切下一个源，**遇空列表即停止**」 | 空列表 = **合法结果**（该源当天无数据），停止降级 |
| `v2/README.md` §2 第 2 条 | 「`collect_with_fallback()` 降级语义：**采集失败时返回空列表**，不中断流程」 | 把「失败」等同于「返回空列表」——与 §4 坑 1 自相矛盾 |
| `v2/README.md` §4 坑 1 | 「采集器吞异常返回空列表 → 跳过兜底、产出 0 条空日报」 | 空列表代表**异常被吞**，是缺陷 |
| `v2/specs/tasks.md` TK-V2-104 ② | 「给定第一源返回 `[]` → **继续切下一源**（不把空列表当成"当天无数据"）」 | 空列表触发**继续降级** |
| `proposal.md` C8 | 三源全失效必须抛明确异常 | 只约束「全失败」，未要求空列表降级 |

### 2.2 裁定：按 v1 ADR-103，空列表即停止

**结论**：`collect_with_fallback()` 的语义定为——

1. 某一源**抛 `SourceUnavailableError`** → 继续切下一个源（异常驱动降级）；
2. 某一源**正常返回 `[]`** → **停止降级**，返回 `(空列表, 该源名)`，代表「该源可用、但当天确实没有数据」；
3. 全部源均抛异常 → 抛 `AllSourcesUnavailableError`（聚合各源原因），**不返回空列表**（proposal C8）。

**理由（五条，均可回原文验证）**：

1. **坑 1 的教训针对的是「吞异常」，不是「空列表不降级」。** v1 的缺陷是飞书采集器把异常吞掉、返回 `[]`，导致降级链误判第一源成功、跳过 local-git 兜底。修法是「异常要显式抛」，而不是「空列表也要降级」。把两者混为一谈会改错病根。
2. **空列表降级会导致数据源口径漂移（已实测）。** v1 在 2026-11-09 / 11-10 曾用 local-git 源（`git log --all` 抓全部分支），11-11 起切到 GitHub 源（只抓 `main`），同一项目两天的条目数口径完全不同。若 v2 规定「GitHub 返回空 → 继续切飞书 → 再切 local-git」，那么**无提交的日子会自动落到 local-git，把别的分支的历史提交当成当日产出**，直接污染日报。ADR-103 的「遇空列表即停止」正是为了避免这个。
3. **`proposal.md` C8 只要求「全源失效抛异常」。** 「空列表继续降级」在 proposal 中找不到依据，属 tasks.md 起草时新增的口径，应回到基线。
4. **v1 有四处独立表述，口径完全一致，不是孤例。** ① `design.md` 1.3「三条固化的数据流契约」第 1 条：「空列表是合法返回值——源可用但窗口内无数据返回 `[]`，降级链据此**停止**而非继续切换（否则"今天没提交"会被误判为"源坏了"）」；② ADR-103 决策②「遇空列表即停止」；③ ADR-103 论证②「把"没数据"报成异常会导致无提交的日子（缺勤/纯会议日，隐含需求 I5）误触发降级，浪费配额且日志失真」；④ 3.1 `collect_with_fallback` docstring「遇空列表 → 停止（返回空结果 + 该源名）」。v2 若反着写，等于推翻四条已定稿结论，须有明确理由，而 tasks.md 未给出。
5. **`tasks.md` §8-U1 自己登记的口径其实是对的，偏离只在 TK-V2-104 验收②。** U1 原文写「本表 TK-V2-104 / 602 / 603 按 ADR-103 + C8 写成『**部分失败**切下一源、全失败抛聚合异常』」——「部分失败」在 ADR-103 语境里指**抛异常**，与 v1 一致。真正多出来的是 104 验收② 那句「给定第一源返回 `[]` → **继续切下一源**」，它把「失败」偷换成「返回空列表」，才造成语义反转。**所以这次修订范围很小：改 104 验收② 一句 + README §2 第 2 条一句，U1 登记的口径本身不用改。**

### 2.3 须同步修订的两处文字（逐字）

**① `v2/specs/tasks.md` TK-V2-104 验收标准 ②**

- 现文：`② 给定第一源返回 [] → **继续切下一源**（不把空列表当成"当天无数据"）；`
- 改为：`② 给定第一源返回 []、第二源有数据 → 返回 (空列表, 第一源名)，**不切第二源**（空列表 = 该源当天无数据，属合法结果；与"异常"严格区分）；`

**② `v2/README.md` §2 第 2 条**

- 现文：`- collect_with_fallback() 降级语义：采集失败时返回空列表，不中断流程。`
- 改为：`- collect_with_fallback() 降级语义：源抛 SourceUnavailableError → 切下一源；源返回空列表 → 停止降级并返回空结果（空列表 ≠ 失败）；全部源抛异常 → 抛 AllSourcesUnavailableError，不返回空列表（C8 / ADR-103）。`

> 注：以上两处为**文字修订建议**，本记录只出结论，不改他人文件。`tasks.md` 归需求分析师（第 3 周：于悦）维护，`README.md` 归配置管理员（第 3 周：赵蕊）（TK-V2-000 交付物）维护，修订须由对应责任人执行并留痕。

### K2 · `run()` 缺 `push_status`

- 要求：TK-V2-501 的 Interfaces 改为

  ```
  run(day: date, *, sources: Sequence[WorkSource], notify: bool = True) -> dict
  # 返回键：date / source / members / items / saved_reports / pushed / push_status /
  #        push_detail / team_report（与 v1 design 3.4 的 9 键对齐）
  ```

  并在验收标准中补一条：`⑤ 给定 notify=True 且全部通道成功 → push_status="ok"、pushed=True；任一失败 → push_status="partial"/"failed"、pushed=False；notify=False → "skipped"（五态与不变量沿用 v1 design 3.4）`。
- 依据：`v1/specs/design.md` 3.4「`push_status` 五态与判定不变量（RT-01）」+ 不变量「`pushed == (push_status == "ok")`」，以及 `all([]) == True` 的真空真值禁令。

### K6 · 团队日报必须发教师邮箱（口径已确认，冲突已于 2026-11-17 全部回填）

### K8 · 全失败异常类与旧异常类的继承关系未定义

- 现状：v1 的 `collect_with_fallback` docstring 与 ADR-103 论证④ 都写「全部失败 → 抛 `SourceUnavailableError`，聚合各源错误信息」，即**只有一个异常类**。v2 的 TK-V2-103 新增了独立的 `AllSourcesUnavailableError(errors: list[SourceUnavailableError])`，但**没有写它和 `SourceUnavailableError` 是什么关系**。
- 风险（按最坏情况推演）：若 `AllSourcesUnavailableError` 不继承 `SourceUnavailableError`，所有按旧类兜底的代码都会**静默穿透**——
  - **业务层**：若有 `except SourceUnavailableError: 走下一源 / 走 mock 兜底` 之类分支，全源失效时抓不到，直接跳到 `main()` 之外。
  - **CLI 层**：TK-V2-504 退出码 `1`（采集或落库失败）若按 `SourceUnavailableError` 判断，全源失效**不会走进 `return 1` 的友好分支**，而是带着 traceback 冒到进程顶层——进程退出码虽然也是 `1`，但用户看到的是堆栈而不是「采集失败：三个源均不可用」这句提示，`602` 里「stdout 无『今日无工作记录』」的断言也拦不住这堆噪音。
  - **测试层**：TK-V2-602 验收② 用 `pytest.raises(AllSourcesUnavailableError)` 能绿，但它**测不出上层能否捕获**——单测绿、集成挂，是最难查的一类。
- 要求（二选一，须在 TK-V2-103 写明）：
  - **方案甲（推荐）**：`class AllSourcesUnavailableError(SourceUnavailableError)`，保证所有旧兜底逻辑继续生效，`errors` 作为附加属性承载各源原因。注意父类签名是 `(source, reason)`，子类需自己实现 `__init__(errors)` 并调 `super().__init__(...)`，这条也要在 103 写清，否则实现者会卡在构造参数上。
  - 方案乙：两者并列，但必须在 501 与 504 中**同时列出两个异常类**捕获，并在 602 补一条「上层捕获」用例（`with pytest.raises(SourceUnavailableError)` 也要能抓到）。
- 顺带一条同源问题：v1 的 `collect_with_fallback` 正常返回第二元素是 `str`（生效源名），全失败时抛异常；v2 改成 `list[str]`（降级原因列表）后，**「无降级时返回什么」没写**——见 K3，须补 `[]`，否则实现者可能塞 `[""]` 或 `None`，`602` 的「日志含降级原因」断言会误判。

## 五、须澄清与建议项

### K3 · `collect_with_fallback` 返回 `list[str]`

认可该变更：v1 只返回生效源名（`str`），v2 返回降级原因列表（`list[str]`），信息量更大、可支撑 602 的「日志含降级原因」断言。**补一条文字**：`未发生降级时第二元素返回空列表 []`，避免实现者误塞占位字符串。

### K4 · 归一化单点位置

- 冲突：`README.md` §2 第 3 条「`normalize` 只执行一次，下游禁止二次归一化」 vs `tasks.md` 104 ④「返回的条目已是 `WorkItem`，编排层二次 `normalize()` 有断言/文档双保险」——前者说禁止，后者说允许带断言重跑。
- **更硬的一处**：`tasks.md` **自己文件内**就矛盾——§1 全局约束 **G7** 写「归一化**只执行一次**（`normalize()`），**下游禁止二次归一化**」，而 104 ④ 说编排层二次 `normalize()` 可以「有断言/文档双保险」。这两句同在一个文件里，且 G7 声明「每条任务的验收标准隐含包含本节」，于是 104 ④ 直接违反 G7。**不用等别人，需求分析师自己就能改这一处。**
- 建议口径（二选一，须在 102/104 中写明）：
  - **方案甲（推荐，贴 v1）**：采集器产出 `RawRecord`，`collect_with_fallback` 统一 `normalize()` 一次后返回 `WorkItem`；`normalize()` 对 `WorkItem` 输入原样放行（幂等），供单测直接用。
  - 方案乙：采集器各自 `normalize()` 后返回 `WorkItem`，fallback 不再归一化；此时 104 ④ 的「二次 normalize 断言」改为「断言编排层**未调用** normalize」。
- 推荐甲的理由：归一化规则（时间字段收敛、类型判别、排序）集中一处，三源不会各写一遍；乙会让 `normalize` 的「未知类型抛 `TypeError`」在三处重复实现，与 G7「纯函数、单点」相抵。

### K5 · keyword-only 丢失

v1 的 `collect(*, since, until, author)` 用 `*` 强制关键字传参，目的是防止 `collect(since, until)` 与 `collect(until, since)` 顺序传错（两参数同为 `datetime`，**顺序错不会报错、只会静默取错窗口**）。v2 改成位置参数后，这类错误无法被类型检查拦住。建议 103 / 104 / 201–203 统一恢复为 `(*, since, until, author=None)`。
