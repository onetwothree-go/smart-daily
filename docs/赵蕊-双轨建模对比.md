UML 图擅长表达「有谁参与、能做什么、结构怎样」，Markdown 规范擅长表达「做到什么程度算对、出错怎么办」。

本项目 `docs/uml/用例图-智能日报生成器.puml`（2026-11-10 重画版）用 3 个业务角色加 1 个外部系统参与者、13 个用例（UC1–UC12 与可选分支 UCX）一屏划定系统边界，且每个用例名内直接标注所回指的 `specs/proposal.md` 范围条目与成功标准，评审时不必读代码就能判断「采集哪些源、生成什么、推给谁、哪条本期不验收」。但图里写不下判据：什么叫「条目与原始记录 1:1 且 commit message 原文不改写」、零记录日发不发、实时提醒算不算日报条目，这些只能落在 `specs/proposal.md` 里，以 S1–S9、C1–C10、Q/I 编号条目固化，供逐条验收。`specs/design.md` 则用 mermaid 画四层依赖（编排→采集/生成/推送），紧接函数级接口契约与 ADR 论证——图给结构，表给约束，两者缺一不可。

配合的关键是**单一事实源**：图与文互不复制。用例图只定边界与角色，条目细节一律回指 proposal 编号；架构图只画依赖方向，函数签名与降级语义写进设计表。PlantUML 源文件与 PNG 一同入库，改图必同步改引用。这条纪律不是形式——我们曾出现 README 文档表与 `docs/` 实际文件对不上的情况，正是图文各写一份的后果。

一句话：UML 用来对共识，Markdown 用来做验收。前者给全组看，后者给评分和回归看。
