## RT-01 · `pushed = any(...)` 与 C7「全部 ok」相抵

### 意见原文（于悦，2026-11-09，未改写）

> **挑错对象**：design 1.4「送达」行 · 3.4 主流程顺序
> **AI 红队意见**：原文「4 封个人邮件 + 1 条群消息，全部 ok 才算成功（C7）」；主文未点破现状。实现 `orchestrator.py` L215 是 `pushed = any(r["ok"] for r in push_detail)`——任一通道成功即算「已推送」，与 C7「全部 ok」相抵，design 主文没有任何一句警示该差距（仅 tasks TK-707 兜 P0）。按现状实施 C7 验收必失败。建议 design 主文标注现状语义并约定 `pushed=all(...)` 的判定落点。
> **严重度**：高
> **本人回应**：采纳（与本人可测性评审 C7 判定同源，实为同一病根）
> **处理结果**：待转交架构师，design 0.5 主文标注现状语义并约定 pushed=all() 判定

### 核对确认

- design 0.4.1 **1.4 通道隔离表「送达」行**（L104）原文：`4 封个人邮件 + 1 条群消息，全部 ok 才算成功（C7）`；**3.4 主流程**（L314）原文：`任何推送失败不影响落库结果`。两处均只写目标语义，未写现状实现语义——意见属实。
- `orchestrator.py` L207 初始化 `pushed = False`，L215 确为 `pushed = any(r["ok"] for r in push_detail)`——意见属实，与 C7 相反。
- 复核另发现**两处同源缺口**（同一病根，随本条一并修）：
  1. `_push_personal_reports` 在 `MEMBER_EMAILS` 未配置时于 L235-238 **提前 return 空列表**，在成员无邮箱映射时于 L245-248 **continue 不记账**——`push_detail` 的分母是「实际尝试集合」，不是 C7 的「应送达集合」。即使把 `any` 改成 `all`，只要少几条记录，`all()` 仍会给出假的 `True`。
  2. Python 的 `all([]) == True`：`--no-notify` 或未配置任何通道时 `push_detail=[]`，若直接写 `all(...)` 会把「根本没推送」判成送达成功。

### 1. 处置结论

**采纳**。理由：C7 是 proposal 的验收口径，design 主文却只写目标、不写现状，导致按 design 实施必与 C7 相反；且仅改 `any→all` 不足以修复，必须同时把判定分母定义为「应送达集合」，并显式排除空集合的真空真值。

### 2. design 落点（0.5）

**(a) 1.4 通道隔离表「送达」行**改为：

> 日报汇总：应送达 `len(groups) + 1` 条（本期 4 名成员即 4 封个人邮件 + 1 条群消息），**全部 ok 才算成功（C7）**；判定式 `pushed = (push_status == "ok")`。实时提醒 1 条群消息，`code=0` 即成功，**不计入 C7 的 5 条**。

并在表下补一段**现状警示**（这是本条要求的「主文点破」）：

> 【0.5 现状标注】0.4.1 及以前 `orchestrator.py::run` 用 `pushed = any(...)`（L215），且 `push_detail` 只记录实际尝试项（L235-238 / L245-248 会跳过无邮箱成员而不记账），两处均与 C7 相抵。0.5 起以本表判定式为准；代码修正由 TK-707 承接。**在修正落地前，`pushed=True` 不得作为 C7 送达证据。**

**(b) 3.4 `run()` 返回结构与主流程**新增「应送达集合」规则：

- 新增返回字段 `push_status`，取值与语义：

  | 取值 | 含义 | `pushed` |
  | --- | --- | --- |
  | `ok` | 应送达集合内**每一条**都 ok | `True` |
  | `partial` | 有成功也有失败 | `False` |
  | `failed` | 全部失败 | `False` |
  | `no_channel` | `notify=True` 但无任何可用通道 | `False` |
  | `skipped` | `--no-notify` 显式不推送 | `False` |

  不变量：`pushed == (push_status == "ok")`；`all([])` 的真空真值**不得**产生 `pushed=True`。

- **应送达集合**的定义（`notify=True` 时）：
  1. **个人**：`groups` 中**每个成员恰好 1 条** `{"scope": f"personal:{member}"}` 记录。成员无邮箱映射、或没有邮件通道时，**仍必须产生记录**，记 `ok=False` 并带 `error`（`"no_recipient"` / `"no_channel"`），不得像现状 L235-238、L245-248 那样跳过不记账。
  2. **团队**：恰好 1 条 `{"scope": "team"}` 记录；无群渠道时记 `ok=False, error="no_channel"`。
  3. `notify=False`：不产生记录，`push_status="skipped"`。
- 主流程末句「任何推送失败不影响落库结果」保留，并补一句：「推送判定只决定 `push_status` 与 CLI 退出码，不影响已完成的落库。」

**(c) 5.3 异常与重试策略「推送」行**补：

> 汇总判定：应送达集合全部 ok 才算送达（C7）；`any()` 语义自 0.5 起弃用（见 1.4 现状标注）。失败明细仍不抛出，由 `push_status` 与 CLI 退出码（3.4）暴露。

**(d) 附录 A**：`C7（4 邮件 + 1 群消息全 ok 才算送达）` 的落点由「3.3 分发规则、3.4 推送明细」改为「**3.4 应送达集合与 `pushed=all` 判定**、3.4.1 推送明细（RT-07）」。

### 3. 计划版本

**design 0.5**。1.4、3.4、5.3、附录 A 同批修订；变更记录 0.5 行注明「回应 RT-01：主文标注 any() 现状并约定应送达集合 + `all()` 判定；代码修正 TK-707」。0.5 提交时须同步 tasks TK-707 验收①（`pushed=all(...)`）与验收③（`push_detail` 指出失败项）。

## RT-02 · CLI 恒 `return 0`，推送失败无法从进程退出码观测

### 意见原文（于悦，2026-11-09，未改写）

> **挑错对象**：design 3.4 CLI 契约表 · 5.3 异常表
> **AI 红队意见**：原文「任何推送失败不影响落库结果」「send() 返回 False / 捕获一切异常记入 push_detail，不抛出」。实现 `cli.py` L110 **恒 `return 0`**，即使 pushed=False、全通道 FAIL。design 未对 22:00 主编排定义「推送存在失败项」的进程退出码；而 tasks TK-103 承诺退出码表、TK-707 要求「任一通道失败→CLI 退出码非 0」——design 没接住，C7 成败无法从 CLI 返回值观测。建议 3.4 补退出码契约。
> **严重度**：高
> **本人回应**：采纳
> **处理结果**：待转交架构师，3.4 补推送失败时的 CLI 退出码契约

### 核对确认

- design 0.4.1 **3.4**（L314）原文：`任何推送失败不影响落库结果`；**5.3 推送行**（L443）原文：`send() 返回 False / 捕获一切异常记入 push_detail，**不抛出**`。两处都只定义了「不抛出」，确实没有定义「怎么被观测」——意见属实。
- `cli.py` L110 确为 `return 0`，且 `main()` 的返回值在 L114 由 `sys.exit(main())` 透传为进程退出码——无论 `result["pushed"]` 为何值，进程恒成功，意见属实。
- 补充：`--list` 分支 L64/L72 也返回 0；argparse 参数错误由 argparse 自身以退出码 2 终止（L53 `parse_args`），现有代码已隐含该行为，0.5 只需把它写进契约。

### 1. 处置结论

**采纳**。理由：5.3 的「不抛出」是**内部**失败语义（不阻断落库），与**外部**可观测性不矛盾；退出码是 CLI 对外的结果契约，属于 3.4 缺失的一格。不补则 tasks TK-103/TK-707 无设计依据，C7 只能靠人眼看日志。

### 2. design 落点（0.5）

**(a) 3.4 CLI 契约表**下新增「**进程退出码**」子表：

| 退出码 | 含义 | 触发条件 |
| --- | --- | --- |
| `0` | 成功 | 采集与落库均成功，且 `push_status ∈ {"ok", "skipped"}` |
| `1` | 采集或落库失败 | 降级链耗尽抛 `SourceUnavailableError`（C8）；或 DB 路径不可写 |
| `2` | 参数错误 | argparse 拒绝（`--day` 格式非法、`--source` 取值非法等），由 argparse 默认行为给出 |
| `3` | 推送存在失败项 | `notify=True` 且 `push_status ∈ {"partial", "failed", "no_channel"}` |

**不变量**（写进 3.4，作为 TK-707 的验收依据）：

1. `notify=True` 时，`pushed=False` **当且仅当**退出码为 `3`（C7 成败可从 CLI 观测）；
2. `--no-notify` 时 `push_status="skipped"`，退出码 `0`，**不得**因「没有推送」报错；
3. `notify=True` 但未配置任何通道 → `push_status="no_channel"`、退出码 `3`（区别于显式 `--no-notify` 的 `0`）；
4. 退出码不改变 5.3 的失败语义：推送失败**仍不抛出**，落库**仍已完成**；退出码只是把结果暴露给调用方（22:00 手动触发者据非 0 判断是否需要人工重跑，重跑幂等，见 2.3）；
5. `--list` 恒返回 `0`（无记录也返回 0，属于正常结果而非错误）。

**(b) 3.4 主流程**末句补：「`run()` 只返回 `pushed` / `push_status`；**由 CLI 在 3.4 退出码表中完成到进程退出码的映射**，编排层不调用 `sys.exit()`。」（保持层级职责：编排层不决定进程生死。）

**(c) 5.3「推送」行**补：「失败不抛出、不阻断落库；汇总结果经 `push_status` 交 CLI 映射为退出码 3（3.4）。」

**(d) 代码落点（供 TK-707 执行，非本文件改动）**：`cli.py` L110 的 `return 0` 改为按 `result["push_status"]` 返回 `0/3`；采集/落库异常在 `main()` 外层转为 `1`；`sys.exit(main())`（L114）保持不变。

### 3. 计划版本

**design 0.5**。3.4 新增退出码子表与不变量、5.3 补一句；变更记录 0.5 行注明「回应 RT-02：补 CLI 退出码契约（0/1/2/3）」。0.5 提交时同步 tasks TK-103 的退出码表（1=采集/落库、2=参数、3=推送失败项）与 TK-604 验收④。

## RT-04 · 架构图把个人/团队两条输出画成同一路径，与 3.3 分发规则矛盾

## RT-05 · 采集层与推送层的「凭证缺失」异常类型被合并成一条纪律

> **处理结果**：待转交架构师，分层写明两层凭证缺失的异常类型

### 核对确认

- design 0.4.1 **5.2 纪律 1**（L430）原文：`凭证缺失 = 源不可用，不是程序错误：from_env() 工厂读到空值即抛 SourceUnavailableError，由降级链接手——凭证问题永远不会以崩溃栈的形式暴露给使用者。`——该句把两层工厂合并表述，意见属实。
- `notifiers.py` L94 确为 `raise ValueError("SMTP_USER / SMTP_PASSWORD 未设置")`；L166 确为 `raise ValueError("FEISHU_WEBHOOK_URL 未设置")`。
- `orchestrator.py` L84、L89 确为 `except ValueError:`（推送通道）；同一文件 L59、L64 为 `except SourceUnavailableError:`（采集源）——**同一个编排类对两层使用两种异常**，意见提示的「订阅方要同时 catch 两种异常」属实。
- 补充：`collectors/github.py` L83/L87 确抛 `SourceUnavailableError`；采集层与推送层的工厂契约已经事实上分家，design 只是没写。

### 1. 处置结论

**采纳**（按意见给出的「**分层写明**」方案；**不**统一异常类型）。理由有三：

1. **依赖方向**：`notifiers.py` 若改抛 `SourceUnavailableError`，推送层就必须 `import` 采集层的异常，违反 1.1「下三层互不感知、依赖单向」的分层约束；反之把异常下沉到公共模块也等于承认两层同一语义，而它们并不相同。
2. **语义不同**：采集层缺凭证是**运行时可降级**的源故障（切成下一个源），推送层缺凭证是**部署时未配置**（该通道根本不挂载、静默跳过）。合并成一个类型会诱导编排层把推送通道当采集源纳入降级链，制造新的语义漂移。
3. **现状即正确**：代码已经按两种异常分工（两处 `from_env` + 编排层分别捕获），0.5 只需把事实写进契约，无需改代码，风险最低。

### 2. design 落点（0.5）

**(a) 5.2 纪律 1** 拆成 1a / 1b：

> **1a. 采集层：凭证缺失 = 源不可用**。`Collector.from_env()` 读到空值即抛 `SourceUnavailableError`（`github.py` L83/L87），由降级链接手——采集凭证问题不以崩溃栈形式暴露。
> **1b. 推送层：凭证缺失 = 通道未配置**。`Notifier.from_env()` 读到空值即抛 `ValueError`（`notifiers.py` L94/L166），含义是「该通道没配好」，**不是源坏了**；调用方捕获后**不挂载该通道、静默跳过**（`orchestrator.py` L84/L89），异常不得逃逸到 CLI。
> **调用方约束**：调用 `Collector.from_env()` 的代码捕获 `SourceUnavailableError`；调用 `Notifier.from_env()` 的代码捕获 `ValueError`。**两种异常不可互换、不可合并捕获后再按字符串区分**。

**(b) 5.2 补一段「为什么不统一异常类型」**：写明上述三条理由（依赖方向、语义不同、现状一致），并明确这不是历史包袱，而是分层设计。

**(c) 3.3 推送层**在 `Notifier` 协议后补一行契约：

> `Notifier.from_env()`：凭证缺失抛 `ValueError`（**不抛** `SourceUnavailableError`，推送层不依赖采集层异常）；`send()` 永不抛异常，失败返回 `False`。

**(d) 5.3 异常表**新增一行：

| 环节 | 失败语义 | 重试 |
| --- | --- | --- |
| 推送通道工厂（`from_env`） | 凭证缺失抛 `ValueError`，由编排层捕获并不挂载该通道；不视为程序错误、不中断主流程 | 不适用（部署配置问题，重试无意义） |

**(e) 1.2 职责表** `push/notifiers.py` 行「不做什么」补「不抛采集层异常、不参与采集降级链」。

### 3. 计划版本

**design 0.5**。5.2 纪律 1 拆分并补理由段、3.3 补工厂契约、5.3 增一行；变更记录 0.5 行注明「回应 RT-05：分层写明采集/推送两层凭证缺失异常（SourceUnavailableError vs ValueError），不统一类型」。

**(b) 3.5 契约 2**（L343）改为：

**(c) ADR-104 ③** 末尾补一句：「匹配大小写不敏感、去首尾空白（见 2.2），两条链路共用同一实现。」

**(d) 新增「唯一实现」约定（写入 3.5 与 2.2 交叉引用）**：

## RT-08 · 跨天任务归哪一天未定义

### 意见原文（于悦，2026-11-09，未改写）

> **挑错对象**：design 2.2（TaskEntry 归属时间）

> **本人回应**：采纳（低危）
> **处理结果**：待转交架构师，随 0.5 顺手写明跨天任务归属规则

### 核对确认

- design 0.4.1 **2.2**（L141）原文：`TaskEntry 同时保留 created_at 与 completed_at，日报关心"当天有什么进展"，用哪个时间做归属由归一化规则统一决定（当前取 created_at，见 WorkItem.from_task）`——只写「当前取」未写跨天规则，意见属实。

- tasks **TK-303**（L125）验收②只写「时间归属用 `created_at`（与 design 2.2 一致）」，无跨天用例，意见属实。
- proposal **C1**（L99）的计数示例是「当日 3 次提交 + 2 个任务」，未说明「任务」按创建还是完成计，歧义确实存在。

### 1. 处置结论

**采纳**（低危）。理由：口径含糊会让测试在跨天构造数据上各写各的断言；而且此处的选择会牵动采集窗口过滤与跨日去重，必须在 design 层写死，不能留给实现者。

**选择的规则：维持 `created_at` 归属，并明确「一条任务只在其创建日计入一次」**。理由：
1. 采集窗口按 `record_timestamp`（= `created_at`）闭区间过滤（3.1、models.py L257），沿用现规则不需要改采集与过滤逻辑；
2. 若改按 `completed_at` 归属，未完成任务将永远不进任何日报，且任务在创建日/完成日两侧都可能进入不同窗口，重跑时容易在两天各记一次，违背 C1 的 1:1；
3. `work_items` 去重键是 `(report_date, record_id)`（2.3），跨报告日不构成同一主键，更需要在规则层禁止同一任务跨日重复。

### 2. design 落点（0.5）

**(a) 2.2 设计要点**（L141）改写为：

> `TaskEntry` 同时保留 `created_at` 与 `completed_at`。**归属日 = `local_date(created_at)`**，与 `WorkItem.from_task`（`models.py` L215）及 `record_timestamp`（L257）保持一致；`completed_at` 只写入 `metrics` 供追溯（L223），**不参与归属、不参与计数**。
> **跨天规则**：一条任务**只在其创建日计入一次**。昨晚创建、今早完成的任务归**创建日**（D-1）；完成日（D）的日报条目不因该任务增加，也不补发提示（N6 已排除历史补采）。同一任务在任意两份日报中最多出现一次。

**(b) proposal C1 对照说明**（写入 2.2 该段末尾，避免与需求侧口径打架）：

> 本规则下 C1 的「当日任务数」= **当日新建任务数**，不等于「当日完成任务数」。完成情况通过条目 `detail` / `metrics.completed_at` 可追溯。若需求方需要「完成日视图」，属新口径，列 6 节未决问题（v1.1），不在 0.5 范围。

**(c) 验收边界（写给 TK-303，0.5 提交时同步 tasks）**：

> 构造任务：`created_at=2026-11-09T22:30+08:00`、`completed_at=2026-11-10T09:00+08:00`、`completed=True`。
> ① `--day 2026-11-09` 运行：该任务出现在日报中，`item_count` 含 1；
> ② `--day 2026-11-10` 运行：该任务**不出现**；

## RT-09 · `MultiNotifier` 未记载、未声明弃用，可能重演判定漂移

### 意见原文（于悦，2026-11-09，未改写）

> **挑错对象**：design 3.3 未记载 MultiNotifier
> **AI 红队意见**：design 自述「已有实现的部分照实描述（每条注明出处）」。`notifiers.py` L211 已实现 `MultiNotifier`，语义「任一通道成功即视为成功」（`any(results)`）——若编排改用它，会重演 RT-01 的判定漂移；design 3.3 只列 Email/Feishu 两个实现，未记载也未声明弃用。建议明确记载或废弃。
> **严重度**：低
> **本人回应**：记为已知风险
> **处理结果**：待转交架构师，在 3.3 记载 MultiNotifier 或声明弃用

### 核对确认

- design 0.4.1 **3.3 实现表**（L272-275）只列 `EmailNotifier.from_env()` 与 `FeishuWebhookNotifier.from_env()`，**全文检索无 `MultiNotifier`**——「未记载」属实。
- `notifiers.py` L211-232 确有 `MultiNotifier`，L232 `return any(results)`，docstring 原文「组合多个通道，任一成功即视为成功」——「语义 `any`」属实。
- `orchestrator.py::_default_notifiers` L71-93 **当前未使用** `MultiNotifier`，即现状无运行时风险；风险在于后续维护者「顺手」用它聚合通道时会引入与 RT-01 相反的判定。
- 补充：`MultiNotifier.send()` 只返回单个 `bool`，按 `Notifier` 协议无法携带分通道回执，**即使改造也无法满足 C7 的 5 条逐项对账**——这是结构性不兼容，不只是「语义不符」。

### 1. 处置结论

**采纳，且处置强于意见给出的两个选项：声明弃用**（不是仅记载为可用实现）。理由：它与 0.5 的 `pushed = all(应送达集合)` 判定在结构上不可共存；保留为「可用实现」只会给未来留下漂移入口。现状未被编排使用，弃用无迁移成本。

### 2. design 落点（0.5）

**(a) 3.3 推送层**在实现表下新增「**已知实现 · 弃用声明**」：

> `MultiNotifier`（`notifiers.py` L211-232）实现「任一通道成功即成功」（L232 `any(results)`）。**0.5 起声明弃用**，原因：
> 1. 其布尔返回值无法承载 C7 的分通道回执（一个 `bool` 表达不了「4 邮件 + 1 群」的逐项成败），与 3.4.1 的 `push_detail` 结构不兼容；
> 2. 其 `any()` 语义与 3.4 的 `pushed = all(...)` 判定相抵，编排若误用即重演 RT-01；
> 3. 聚合通道的职责属于**编排层**（`notifiers` 列表 + 3.4 判定），不属于推送层。
> **约束**：编排层 `_default_notifiers()`（`orchestrator.py` L71-93）不得实例化 `MultiNotifier`、不得放入 `notifiers` 列表；代码保留期间在类 docstring 标注「已弃用，勿用」，v1.1 删除或改造为返回逐通道明细。

**(b) 3.3 `Notifier` 协议**后补一句：

> 一个 `Notifier` 实例 = **一个通道**；跨通道聚合与判定由编排层负责（3.4），推送层不提供聚合实现。

**(c) 1.2 分层职责表** `push/notifiers.py` 行「不做什么」补「**不提供多通道聚合**（`MultiNotifier` 已弃用，见 3.3）」。

**(d) 5.4 或 6 节**不新增内容；本条不改协议、不改代码，仅记载与约束。

### 3. 计划版本

**design 0.5**。3.3 增弃用声明与「单实例=单通道」约束、1.2 职责表补一句；变更记录 0.5 行注明「回应 RT-09：记载 `MultiNotifier` 并声明弃用，禁止编排使用」。
