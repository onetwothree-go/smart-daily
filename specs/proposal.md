## 1. 项目名称

智能日报生成器（Smart Daily Report Generator）

## 2. 目标

> 每条目标必须能转化成一条测试。禁止出现"体验良好""性能较优"这类表述。

| # | 目标 | 度量方式 | 确认 |
| --- | --- | --- | --- |
| G1 | 日报条目从真实工作数据自动生成，个人日报的手工新增条目数为 0 | 个人日报条目数 = 当日该成员提交数 + 任务数 + 消息数，人工新增条目计数 = 0 | ☐ |
| G2 | 单成员单次采集 100 条 GitHub 提交耗时 < 30s | 计时断言（待补测试） | ☐ |
| G3 | 协作成果自动归属，跨成员关联提交识别准确率 ≥ 95% | 用构造数据集统计（待补测试） | ☐ |
| G4 | 团队日报格式统一（同一模板），每日截止时间前送达全员 | 模板哈希一致 + 送达时间戳 | ☐ |
| G5 | 凭证失效或数据源故障时主流程不中断，自动降级并留痕 | 失效注入测试 | ☐ |

## 3. 背景

指导书第一部分列出的五个痛点，逐条说明本系统如何接住（解法均已在当前工程中实现并有实测记录）：

| # | 痛点 | 系统解法 | 实现位置 |
| --- | --- | --- | --- |
| ① | 下班时回忆"今天到底干了什么"，全靠记忆翻找 | 采集层按自然日自动归集当日全部痕迹，日报从数据中"自动长出来"，不依赖记忆 | `collectors/` 四数据源 |
| ② | 工作痕迹散落在 GitHub 提交、飞书任务、群聊消息等多个平台，逐个复制粘贴 | 四源采集（GitHub API / 飞书开放平台 / 本地 git / mock 演示源）归一化为统一数据模型，一处配置全量归集 | `collectors/github.py`、`collectors/feishu.py`、`collectors/local_git.py`、`collectors/mock.py` |
| ③ | 忙起来必有遗漏，写进去的都是"记得住的"，不是"做了的" | 按数据源全量拉取，漏一条 = 采集缺陷（可测试）；实测 2026-11-06 真实模式下 5 条提交全部捕获、零遗漏 | 采集层 + SQLite 对账 |
| ④ | 小组成员协作成果经常谁都没写进日报 | 成员身份映射（MEMBER_EMAILS）+ 登录名显示名映射（MEMBER_DISPLAY_NAMES）：同一成员的多个平台账号归并为一人；实测 2026-11-06 方赫的三个 GitHub 身份（jchdhidhsh / fh / 20233046方赫）自动合并为"方赫"一份日报 | `push/members.py`、`collectors/github.py` |
| ⑤ | 每人格式不一，组长还得手工汇总成团队日报 | 主编排模块用同一模板生成全组成员的个人日报并汇总为团队日报，组长零手工；实测 2026-11-06 四人个人日报 + 团队日报一次生成、全部送达 | `pipeline.py`、推送层 |

**差异化定位（业务调研结论）**：对 daily-report、DevDiary、Teambition AI 智能周报三个同类方案的调研显示——三者验证了"自动归集 + 摘要"路线成立，但**没有一个同时做到：代码提交 + 任务 + 群聊三源采集、个人日报 + 团队日报双形态、开源可配置**（详见 `docs/同类方案调研底稿.md`）。这正是本项目的定位空间；商业成品（Teambition）不采集代码提交，研发真实工作量反而不可见。

## 8. 术语定义

| 术语 | 定义 |
| --- | --- |
| 原始记录（RawRecord） | 采集层从各平台原样取回、未做归一化的记录，联合类型 `CommitEntry \| MessageEntry \| TaskEntry` |
| 工作项（WorkItem） | 归一化后的日报条目，字段统一，供生成层消费 |
| 降级链 | 采集源不可用时的 fallback 顺序：GitHub → 飞书 → local-git → mock |
| 协作成果 | 由多名成员共同产生的提交或任务，按关联关系归属到全部贡献者 |
| 日报截止时间 | 当日日报的统计边界（`DAILY_CUTOFF`），见 `.env` |
| 成员映射 | `MEMBER_EMAILS` 环境变量：成员名/登录名 → 收件邮箱，一人多邮箱用分号分隔 |
| 显示名映射 | `MEMBER_DISPLAY_NAMES` 环境变量：GitHub 登录名 → 团队显示名，用于归并多账号身份 |
