## 1. 项目名称

智能日报生成器（Smart Daily Report Generator）

## 2. 目标

> 每条目标必须能转化成一条测试。禁止出现"体验良好""性能较优"这类表述。

| #  | 目标                                                                                                                       | 度量方式                                                                                                                     | 确认     |
| -- | ------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------ | ------ |
| G1 | 日报条目从真实工作数据自动生成，个人日报的手工新增条目数为 0；**条目与原始记录严格 1:1**（不按主题聚合、不做语义过滤）；**实时提交通知只作「提醒」，不落库、不拼进日报、不计入本条 1:1 计数**（Q4/Q14/Q16/Q17） | 个人日报条目数 = 当日该成员提交数 + 任务数 + 消息数，人工新增条目计数 = 0；**同一个 commit 只在 22:00 汇总计一次，实时提醒一次都不算**（Q4/Q14/Q17）                          | ☐      |
| G2 | 单成员单次采集 100 条 GitHub 提交耗时 < 30s（**本期列为性能观察项，不进硬验收**，见 C6）                                                                | **本行为观察项、不作验收断言**（回应于悦可测性评审 `9f8caf0`：proposal 自降「不进硬验收」即不成立为硬验收标准）；若日后要计时，须 fixture 注入 100 条、不走真实网络、固定计时起止口径，重判后才可升为验收项 | —（观察项） |
| G3 | 同一成员多个 GitHub 登录名**归并为一人一份日报**，身份归并准确率 100%（构造多账号数据集）；**多人协作成果归属本期不验收**（Q5/Q12）                                          | 构造数据集统计（待补测试）                                                                                                            | ☐      |
| G4 | 团队日报与个人日报**条目行格式逐字一致**（`- [HH:MM]（类型）标题`）；两份日报按各自维度分组（团队按成员、个人按来源），整体模板骨架因维度不同不适用逐字比对；每日截止时间前送达全员（Q11） | 条目行格式逐字比对 + 送达时间戳 | ☐ |
| G5 | 凭证失效或数据源故障时主流程不中断，自动降级并留痕；**实时提醒通道发送失败不影响 22:00 汇总主流程，但不得静默失败**（错误码进 Actions 日志 + workflow 亮红灯，Q21）                      | 构造假 token 注入测试（待建）；实时通道失败留痕按 C10 判定                                                                                      | ☐      |

## 3. 背景

指导书第一部分列出的五个痛点，逐条说明本系统如何接住（解法均已在当前工程中实现并有实测记录）：

| # | 痛点                                      | 系统解法                                                                                                                                            | 实现位置                                                                                         |
| - | --------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| ① | 下班时回忆"今天到底干了什么"，全靠记忆翻找                  | 采集层按自然日自动归集当日全部痕迹，日报从数据中"自动长出来"，不依赖记忆                                                                                                           | `collectors/` 四数据源                                                                           |
| ② | 工作痕迹散落在 GitHub 提交、飞书任务、群聊消息等多个平台，逐个复制粘贴 | 四源采集（GitHub API / 飞书开放平台 / 本地 git / mock 演示源）归一化为统一数据模型，一处配置全量归集                                                                                | `collectors/github.py`、`collectors/feishu.py`、`collectors/local_git.py`、`collectors/mock.py` |
| ③ | 忙起来必有遗漏，写进去的都是"记得住的"，不是"做了的"            | 按数据源全量拉取，**条目与原始记录 1:1，不聚合、不过滤**，漏一条 = 采集缺陷（可测试）；实测 2026-11-06 真实模式下 5 条提交全部捕获、零遗漏                                                              | 采集层 + `normalize()` + SQLite 对账                                                              |
| ④ | 小组成员协作成果经常谁都没写进日报                       | 成员身份映射（MEMBER_EMAILS）+ 登录名显示名映射（MEMBER_DISPLAY_NAMES）：同一成员的多个平台账号归并为一人；实测 2026-11-06 方赫的三个 GitHub 身份（jchdhidhsh / fh / 20233046方赫）自动合并为"方赫"一份日报 | `push/members.py`、`collectors/github.py`                                                     |
| ⑤ | 每人格式不一，组长还得手工汇总成团队日报                    | 主编排模块用同一模板生成全组成员的个人日报并汇总为团队日报，**自动生成统计头「共 M 位成员、N 条记录」并按贡献条数降序排列**，组长零手工；实测 2026-11-06 四人个人日报 + 团队日报一次生成、全部送达                                   | `pipeline.py`（生成层 `push/generator.py`）、推送层                                                   |

**差异化定位**（2026-11-09 依据《业务调研报告（初稿）》6.2 回填，证据为于悦《同类竞品调研记录》15 张截图与三源核验记录；本人补采截图待定稿前完成）：面向 4 人学生小组的课程仿真场景，本项目以 GitHub 提交、飞书任务、飞书群消息三处真实工作痕迹为唯一正式数据源，按自然日 0:00 至生成那一刻全量归集，条目与原始记录严格 1:1、原样呈现，按成员身份归并后以同一模板生成个人日报并汇总为团队日报，经邮件与飞书群推送，SQLite 只存成品快照。与 Aiscribe 的差异是「外部多源＋团队汇总＋代码提交」，与 gh-daily-report 的差异是「多源＋团队汇总＋自动推送」，与 Teambition 的差异是「开源可配置＋采集代码提交＋日报粒度」。本期明确不做智能摘要、Web 界面、考勤数据、人工后编辑、历史补采、自动重试与服务化。

## 8. 术语定义

| 术语 | 定义 |
| --- | --- |
| 原始记录（RawRecord） | 采集层从各平台原样取回、未做归一化的记录，联合类型 `CommitEntry \| MessageEntry \| TaskEntry` |
| 工作项（WorkItem） | 归一化后的日报条目，字段统一，供生成层消费；**与原始记录严格 1:1**，带 `record_id`（sha / message_id / task_id）便于对账 |
| 降级链 | 采集源不可用时的 fallback 顺序：GitHub → 飞书 → local-git → mock；**本地 git 与 mock 非正式数据源** |
| 协作成果 | **本期不做多人归属**：一条成果只归提交人/任务创建人/消息发送人。已实现的是「身份归并」（一人多账号合并为一份日报），多人协作归属留第 2 周 |
| 日报截止时间 | 东八区本地自然日 0:00 起、**到日报生成那一刻止**（本期约定每天 22:00 手动触发），不是 24:00，也不是 `DAILY_CUTOFF` 之类固定配置 |
| 条目行格式 | 每条工作记录的固定行格式 `- [HH:MM]（类型）标题`；G4 / C4 比对的是它，不是整份成品文本、也不是整体模板骨架（个人与团队日报按各自维度分组） |
| 成员映射 | `MEMBER_EMAILS` 环境变量：成员名/登录名 → 收件邮箱，由配置管理员维护；**属个人信息，绝不进仓库** |
| 显示名映射 | `MEMBER_DISPLAY_NAMES` 环境变量：GitHub 登录名 → 团队显示名，用于归并多账号身份；未命中回落原始登录名并须告警；**实时提醒用事件自带 `github.actor` 查这张表**，不用 `commits[].author.name`（那是各人本机 git config 姓名） |
| 单机运行 | 本期只在一台开发机跑 CLI；真实推送仅限持有 `.env` 的运行者，其他人用 `--no-notify`；实时提醒由 GitHub 托管 runner 承担，不引入第二台常驻机器 |
| **实时提醒** | 每次 push 立刻在飞书群发出的**告知性消息**，只用于说明「谁提交了什么」；**不是日报条目**，不落 SQLite、不进 G1 计数、不拼进日报正文；只在 `main`/`dev` 触发，一次 push 合并 1 条并列全 commit；与 22:00 团队日报汇总是**两条独立通道**（Q16–Q21、S9） |
